# 優化算法實驗系統需求基線

本頁的算法錯誤處置已同步系統重構 D79–D80；詳細決策與未定技術以 [系統重構文件](../../analysis/system_redesign/README.md) 及其 [設計決策紀錄](../../analysis/system_redesign/design_decisions.md) 為準。[v2 實作前提案](implementation-plan.md) 是較早的凍結候選，引用的是 [v2 discuss](discuss.md) 的 D 編號，與目前系統重構 D01–D80 分屬不同紀錄；其中 checkpoint、資料庫或 managed RNG 框架不因此成為有效需求。

## 快速檢索卡

- 核心問題：在決定重構方式或採用第三方執行框架以前，先明確描述研究者如何使用優化算法實驗系統。
- 當前結論：Python 管理實驗，傳統問題朝 C++ 求解模組遷移；跨問題分組、組內配對與拒絕不支援／重複 task 的政策已確認，正式展開與支援 API 待實作。架構候選已有 [19 的證據](../../analysis/system_redesign/19_architecture_candidate_experiments.md)，尚未選新方案。
- 關鍵爭點：Server／遠端叢集、資料庫與檔案的分工、共享資料正式交接、統計格式、效能門檻及 GPU／分散式 evaluator 尚待細化；已確認共享需求與原交接機制見 [08](../../analysis/system_redesign/08_cpp_invocation_and_shared_memory.md#不變需求與原交接基線)。
- 適用於：MKP、TSP、CVRP，以及未來的連續型最佳化和 AI 模型最佳化研究實驗。
- 不適用於：目前尚未確認的線上服務、多人平台、算法內部 checkpoint 恢復或特定第三方 scheduler 選型；本版亦不處理磁碟滿／磁碟故障等硬體／資源層情境。
- 待驗證：高併發的量化指標、記憶體上限、統計模組支援範圍、資料保存策略及跨硬體執行邊界。

## 核心問題

目前專案需要從支援少數優化算法的實驗流程，擴充成可支援多種優化問題與研究方向的通用實驗系統。若先決定模組或框架，再回頭猜測使用方式，可能造成系統流程與實際研究工作不一致。

本基線先定義一次研究實驗的使用方式與必要結果，作為後續評估核心模組、scheduler、資料保存及效能設計的共同前提。

## 形成的知識

以下內容是本輪由使用者確認的需求，不是外部查證結果。

### 1. 實驗範圍

- 現有問題註冊包括 MKP、TSP、CVRP、SCVRP 與 continuous；有註冊不等於每種類型都有完整題庫。
- 未來需要以優化算法提升 AI 模型效能的研究；先檢查共同責任邊界，傳統問題先細化。
- 一次實驗可跨不同問題類型，算法須支援；D41–D47 已定 YAML 分組、一組一種問題、組內全部配對及啟動前拒絕不支援／重複 task，正式 API／完整 schema／展開實作仍待完成，不能以「永遠只能同一種類型」限制新架構。
- 同一次實驗可以包含多組算法參數。

### 2. 使用流程

研究者提供問題類型、算法、參數組合、問題資料及重複次數等實驗設定後，系統應自動完成：

1. 載入問題資料與算法設定。
2. 展開問題實例、重複次數及參數組合形成任務。
3. 自動分派並執行任務。
4. 接收求解任務已驗證的結果，保存並彙整；實驗管理不重新做數學驗證。
5. 產生原始結果與統計輸出。

研究者不需要逐步手動控制資料載入、任務分派或平行執行。

### 3. 比較與可重現性

- 不同參數組合應使用同一批問題實例。
- 不同參數組合應使用相同的重複次數。
- 隨機種子必須可追蹤且可重現。
- 流程重現以相同輸入、參數、seed 與固定迭代為前提；addAct 不評估、不消耗 RNG，不改變搜尋結果。不對按時間停止作同樣承諾。
- 這些條件的目的是讓參數組合之間可以公平比較。

### 4. 失敗與恢復

- 算法執行的非預期錯誤，包括可捕捉錯誤與原生致命崩潰，依系統重構 D79–D80 停止整場實驗，涵蓋其他算法及正在求解的 task；不再啟動新 task，保留已成功保存結果，不自動重跑。
- 求解異常保留 task 的實際有效輸入，以便日後單獨從頭重跑；不要求 Python 查明 C++ 內部根因。輸入須在求解開始前保留，不依賴崩潰 worker 回傳。
- Python 保存錯誤依 D40 留原因與 task 對應；清理成功且環境可信才重用，否則不再使用不可信環境。舊基線可替換程序；候選的實體範圍／時機及同 host 同伴影響依 [14 名詞表](../../analysis/system_redesign/14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍) 待確認，不只換 thread／物件當恢復、不一律全場停。健康且整場未停止時同鏈才接新題，不自動重試；路徑／權限／格式等軟體問題在範圍內，硬體／資源故障及獨立保存媒介不納入。
- 未知原因退出依 D38 保留已收到的完整回報、現有文件及最後已知事實，不猜算法根因、不自動核對文件或補登成功；其原因分類與停止處置仍待細化。
- 算法錯誤停止整場已確認，但停止時點及正在執行工作如何安全收尾仍待架構細化，不代表已能立即安全中止所有工作。正常不可行、輸入預檢與 Python 保存錯誤不混入算法錯誤。
- 實驗中斷後保留已完成且成功保存的任務；需要另行重跑時，未完成任務從頭開始，不恢復算法中間狀態。整場重啟後辨識／跳過完成任務的續跑機制在核心重構驗證後處理，核心交付與異常紀錄仍須先依 D38–D40 實現。
- 第一版不要求從算法內部的中間狀態恢復，因為算法內部狀態恢復被認為過於不可控。

正常完成但最終解不可行，不屬於執行失敗。算法錯誤停止整場、Python 保存錯誤後的清理／重用、事後診斷重跑及整場中斷後續跑是不同要求；核心錯誤分類、紀錄與停止不能跟整場自動續跑一起延後。細節見 [task 異常與結果保存](../../analysis/system_redesign/15_task_failures_and_result_storage.md)。

D25 的保存原因強需求與未定機制依 [15](../../analysis/system_redesign/15_task_failures_and_result_storage.md#保存錯誤原因的留存界線)：範圍內 Python 軟體保存失敗，原因與 task 必須事後可查，不只記失敗或降為最佳努力。產生原因／通知／持久保存分開，正式責任方／時點／位置及完成判定待確認；二次軟體失敗或落盤前退出的保障也待確認，不默選 worker-first artifact、不宣稱全保證，亦不自動排入 D26。錯誤 artifact 不等於結果交付，D38 不掃檔／補登／重試，D40 及 D79–D80 不變。

### 5. 結果與統計

- 必須能取得每一個問題實例、每一次重複執行的詳細結果。
- 所有任務每次實際 addAct 的編碼、真實適應值及實際提供的外部狀態全部保留；每 task 完整計算及最終驗證後一次交付，算法及 addAct 不做文件 I/O，保存屬實驗／輸出責任。
- D34 已定同一邏輯工作鏈同步保存、交接及清理後才接下一題，主管只收摘要／路徑，不重開主程序收全量保存。這不要求同 host 其他健康鏈等保存，也不預設鏈永久綁某 thread／程序；舊基線一個 worker 對應一個程序，名詞依 [14](../../analysis/system_redesign/14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍)。完整返回 Python 與 Python 輸出器仍是有效舊基線；候選語言／返回／所有權及錯誤映射差異依 [07](../../analysis/system_redesign/07_history_return_and_storage.md#已確認交付需求與保存基線) 待確認。
- 呼叫架構方面，D35 曾選定隔離 Python worker 內同程序 C++ 呼叫的完整方案，現在作重新評估基線，尚未選定新組合；狀態與比較維度見 [14](../../analysis/system_redesign/14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度)。
- 此版不分批、不用背景 writer／Redis，接受單任務完整歷史可能耗盡記憶體的已知風險，後續另議。
- 最終不可行仍保存該解、真實目標與不可行標記；搜尋罰分分開。不可行結果的平均、排名與成功率規則尚未定案。
- 最終通常會彙整成各參數組合的統計表。
- 不同論文投稿可能需要不同統計格式，因此原始資料應保留，或至少能依設定重新產生所需統計資料。
- 實驗 YAML 應能設定輸出格式。
- 統計模組需要明確確認是否支援研究者需要的統計參數。

### 6. 效能與資源

- 系統需要滿足高併發需求。
- 同題固定資料避免重複準備，全部選中題目備妥才正式求解；求解端須有唯讀保護，可變種群、RNG 與工作緩存屬各自任務，資料仍被 task／結果／保存方使用時不可回收。
- D74–D77 確曾選定隔離預處理、先算搬 SHM、主程序持有及每 task 連接／解除，仍是有效原交接基線。新候選偏離具體機制須列差異待確認，不自動換方案；分層對照及正式交接待細化內容見 [08](../../analysis/system_redesign/08_cpp_invocation_and_shared_memory.md#不變需求與原交接基線)。
- 高併發不能只以增加 worker 數量表示；還需要同時考慮資料共享、任務排程、記憶體占用及算法本身的執行成本。

### 7. 目前架構可延續的方向

現有流程已具備「實驗設定 → 問題資料 → RunTask → Solver.solve → SolveResult → 彙整」的雛形。後續設計應優先檢查這條流程能否擴充到上述需求，而不是預設必須整套重寫。

## 討論的演化

1. 原先討論集中在 RNG、checkpoint、資料庫、第三方 scheduler 及插件邊界，容易在尚未確定實際使用方式前先行決定技術。
2. 使用者指出專案首先需要確認定位與使用需求，否則後續系統設計可能偏離研究工作的實際流程。
3. 最早以一種問題類型、一個算法、多組參數討論，後續擴充為一次實驗可涵蓋不同問題類型的需求；不能把早期範例當成新架構永久限制。
4. 較早曾要求失敗時整個實驗停止；2026-10-21 當時改為單一 task 軟體異常後記錄並繼續新 task，必要時替換 worker。算法錯誤分支後由第 8 項取代；算法中途 checkpoint 仍不納入。
5. 最後補充高併發及共享快取是系統級要求，不能只視為單一算法的功能。
6. 後續確認 Python 實驗管理／C++ 求解的責任、算法狀態、增量評估及 addAct。2026-10-21 確認所有實際提交全量保留、每個任務完成一次回傳，記憶體改善延後。
7. 同日進一步區分求解異常與寫檔異常的留存要求，明確排除磁碟滿／磁碟故障等資源層處理，不導入跨儲存媒介錯誤備援。
8. 2026-10-24 系統重構 D79–D80 確認算法錯誤停止整場，包含可捕捉錯誤、原生致命崩潰及其他算法正在求解的 task；不再啟動新 task，已成功保存結果保留，不自動重跑。Python 保存錯誤仍依 D40，正常不可行不算算法錯誤；停止收尾與未知退出判定仍待細化。

## 邊界與未解問題

以下項目尚未形成需求決定，因此不可在架構設計中假設已經確定：

- 是否需要 Server／API，以及是否支援多人或遠端叢集。
- 高併發的量化目標，例如任務數、worker 數、節點數及可接受的排程開銷。
- 固定資料的正式描述、持有／映射／回收實作及新候選相對原交接基線的機制差異，依 [08](../../analysis/system_redesign/08_cpp_invocation_and_shared_memory.md#不變需求與原交接基線) 細化或列差異待確認；共用唯讀、task 狀態私有及使用期間有效性不是未定需求。
- 額外共享快取的失效策略及記憶體上限。
- 檔案保存與資料庫保存的最終分工。
- YAML 可設定的輸出格式，以及統計模組必須支援的完整統計量清單。
- 是否需要 GPU 或分散式 evaluator。
- 不同問題類型是否需要不同的資料表示、評估介面及結果欄位。
- 算法錯誤停止整場時的停止時點、在途任務安全收尾、未知退出原因分類與處置；不自動重跑。Python 保存錯誤的清理／重用或替換依 D40，不因本輪擴大成算法錯誤停止。
- 輸出器語言與相對 D18 完整返回 Python、D19／D34 保存基線的所有權差異，依 07 比較待確認；D34 同步 task 保存位置及主管只收摘要／路徑已定，不重開。DTO／摘要、正式保存／通知格式仍待細化，D38 不自動核對文件、補登或重跑的政策保留。
- 多參數組合是否需要動態增加、取消或優先執行。
- 現有本機 `MachinePool` 與第三方 scheduler 的效能分界。

## 交接資訊

可以安全採用的內容是「一次實驗的使用流程、比較條件、失敗與恢復邊界、結果需求、高併發及共享快取」這組需求基線。

不可假設的內容包括最終 scheduler、Server／API、資料庫方案、GPU 支援方式、共享快取實作及完整統計欄位。

最新研究進度與原始證據見 [19](../../analysis/system_redesign/19_architecture_candidate_experiments.md)：七單元中的 1／2／4 有候選證據但未選型，3 設定政策已定待正式 API／交付，5／6／7 仍待討論。後續依 [待議清單](../../analysis/system_redesign/13_open_questions.md) 及 [14 的三個維度](../../analysis/system_redesign/14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度) 確認組合，按 [08](../../analysis/system_redesign/08_cpp_invocation_and_shared_memory.md#不變需求與原交接基線)／[07](../../analysis/system_redesign/07_history_return_and_storage.md#已確認交付需求與保存基線) 列交接與保存基線差異；同程序擴充模組不排除多執行緒。此次封存只讀核對後停止，不重新執行原型、不自動採用候選，也不宣稱正式 G2／G3 或真 CDELS 併發已驗收。
