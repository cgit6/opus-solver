# 優化算法實驗系統需求基線

本頁按後續已確認的責任與紀錄需求同步更新。詳細決策與未定技術見 [系統重構文件](../../analysis/system_redesign/README.md)；本頁不批准較早實作提案中的 checkpoint、資料庫或 managed RNG 框架。

## 快速檢索卡

- 核心問題：在決定重構方式或採用第三方執行框架以前，先明確描述研究者如何使用優化算法實驗系統。
- 當前結論：系統由 Python 管理實驗，傳統問題朝 C++ 求解模組遷移；支援多參數與多題，並納入一次實驗跨問題類型的需求，前提是算法支援。跨問題設定與展開方式待定。
- 關鍵爭點：Server／遠端叢集、資料庫與檔案的分工、共享快取範圍、統計格式、效能門檻及 GPU／分散式 evaluator 尚未定案。
- 適用於：MKP、TSP、CVRP，以及未來的連續型最佳化和 AI 模型最佳化研究實驗。
- 不適用於：目前尚未確認的線上服務、多人平台、算法內部 checkpoint 恢復或特定第三方 scheduler 選型；本版亦不處理磁碟滿／磁碟故障等硬體／資源層情境。
- 待驗證：高併發的量化指標、記憶體上限、統計模組支援範圍、資料保存策略及跨硬體執行邊界。

## 核心問題

目前專案需要從支援少數優化算法的實驗流程，擴充成可支援多種優化問題與研究方向的通用實驗系統。若先決定模組或框架，再回頭猜測使用方式，可能造成系統流程與實際研究工作不一致。

本基線先定義一次研究實驗的使用方式與必要結果，作為後續評估核心模組、scheduler、資料保存及效能設計的共同前提。

## 形成的知識

以下內容是本輪由使用者確認的需求，不是外部查證結果。

### 1. 實驗範圍

- 現有問題註冊包括 MKP、TSP、CVRP、SCVRP 與 continuous；有註冊不等於每種類型都有完整題庫。
- 未來需要以優化算法提升 AI 模型效能的研究；先檢查共同責任邊界，傳統問題先細化。
- 一次實驗跨不同問題類型是新需求，算法須支援；正式組合規則與設定格式尚未定案，不能沿用「永遠只能同一種類型」作新架構限制。
- 同一次實驗可以包含多組算法參數。

### 2. 使用流程

研究者提供問題類型、算法、參數組合、問題資料及重複次數等實驗設定後，系統應自動完成：

1. 載入問題資料與算法設定。
2. 展開問題實例、重複次數及參數組合形成任務。
3. 自動分派並執行任務。
4. 接收求解任務已驗證的結果，保存並彙整；實驗管理不重新做數學驗證。
5. 產生原始結果與統計輸出。

研究者不需要逐步手動控制資料載入、任務分派或平行執行。

### 3. 比較與可重現性

- 不同參數組合應使用同一批問題實例。
- 不同參數組合應使用相同的重複次數。
- 隨機種子必須可追蹤且可重現。
- 流程重現以相同輸入、參數、seed 與固定迭代為前提；addAct 不評估、不消耗 RNG，不改變搜尋結果。不對按時間停止作同樣承諾。
- 這些條件的目的是讓參數組合之間可以公平比較。

### 4. 失敗與恢復

- 單一 task 發生系統軟體流程異常時，留下紀錄、必要時恢復／替換 worker，再處理下一個新 task，不因此中斷整場；不默認重試原 task。這取代較早的任務失敗即停止要求。
- 求解異常保留 task 的實際有效輸入，以便日後單獨從頭重跑；不要求 Python 查明 C++ 內部根因。輸入須在求解開始前保留，不依賴崩潰 worker 回傳。
- Python 寫檔異常須保存原因及 task 對應；軟體輸出流程的路徑、權限、格式或資料轉換問題在範圍內。磁碟滿／磁碟故障等硬體／資源層異常不處理，也不新增獨立保存媒介或服務。
- 實驗中斷後，保留已完成且成功保存的任務，未完成任務從頭重跑；保存／完成判定及續跑機制在核心重構驗證後處理。
- 第一版不要求從算法內部的中間狀態恢復，因為算法內部狀態恢復被認為過於不可控。

正常完成但最終解不可行，不屬於執行失敗。異常後繼續新 task、故障診斷重跑及整場中斷後續跑是不同功能；核心任務的異常紀錄與恢復不能跟整場自動續跑一起延後。細節見 [task 異常與結果保存](../../analysis/system_redesign/15_task_failures_and_result_storage.md)。

### 5. 結果與統計

- 必須能取得每一個問題實例、每一次重複執行的詳細結果。
- 所有任務每次實際 addAct 的編碼、真實適應值及實際提供的外部狀態全部保留；每個 C++ 任務完成與最終驗證後一次返回 Python 保存。
- Python worker 呼叫共用輸出器保存、主程序只收摘要與檔案位置仍是候選；尚未選定保存位置，也不代表 A／B 呼叫方式已選定。
- 此版不分批、不用背景 writer／Redis，接受單任務完整歷史可能耗盡記憶體的已知風險，後續另議。
- 最終不可行仍保存該解、真實目標與不可行標記；搜尋罰分分開。不可行結果的平均、排名與成功率規則尚未定案。
- 最終通常會彙整成各參數組合的統計表。
- 不同論文投稿可能需要不同統計格式，因此原始資料應保留，或至少能依設定重新產生所需統計資料。
- 實驗 YAML 應能設定輸出格式。
- 統計模組需要明確確認是否支援研究者需要的統計參數。

### 6. 效能與資源

- 系統需要滿足高併發需求。
- 適合共用的固定問題資料應避免重複載入；可變種群、RNG 與工作緩存仍屬各自任務。具體 SHM／傳值方式尚待確認。
- 高併發不能只以增加 worker 數量表示；還需要同時考慮資料共享、任務排程、記憶體占用及算法本身的執行成本。

### 7. 目前架構可延續的方向

現有流程已具備「實驗設定 → 問題資料 → RunTask → Solver.solve → SolveResult → 彙整」的雛形。後續設計應優先檢查這條流程能否擴充到上述需求，而不是預設必須整套重寫。

## 討論的演化

1. 原先討論集中在 RNG、checkpoint、資料庫、第三方 scheduler 及插件邊界，容易在尚未確定實際使用方式前先行決定技術。
2. 使用者指出專案首先需要確認定位與使用需求，否則後續系統設計可能偏離研究工作的實際流程。
3. 最早以一種問題類型、一個算法、多組參數討論，後續擴充為一次實驗可涵蓋不同問題類型的需求；不能把早期範例當成新架構永久限制。
4. 較早曾要求失敗時整個實驗停止。2026-10-21 後續明確改為單一 task 軟體異常後記錄並繼續新 task，必要時替換 worker；算法中途 checkpoint 仍不納入。
5. 最後補充高併發及共享快取是系統級要求，不能只視為單一算法的功能。
6. 後續確認 Python 實驗管理／C++ 求解的責任、算法狀態、增量評估及 addAct。2026-10-21 確認所有實際提交全量保留、每個任務完成一次回傳，記憶體改善延後。
7. 同日進一步區分求解異常與寫檔異常的留存要求，明確排除磁碟滿／磁碟故障等資源層處理，不導入跨儲存媒介錯誤備援。

## 邊界與未解問題

以下項目尚未形成需求決定，因此不可在架構設計中假設已經確定：

- 是否需要 Server／API，以及是否支援多人或遠端叢集。
- 高併發的量化目標，例如任務數、worker 數、節點數及可接受的排程開銷。
- 共享快取的生命週期、共享範圍、失效策略及記憶體上限。
- 檔案保存與資料庫保存的最終分工。
- YAML 可設定的輸出格式，以及統計模組必須支援的完整統計量清單。
- 是否需要 GPU 或分散式 evaluator。
- 不同問題類型是否需要不同的資料表示、評估介面及結果欄位。
- worker 隔離／重建及在途任務處理方式；單一 task 軟體異常後繼續新 task 已確認，不預設自動重試原 task。
- worker／主程序保存、DTO／摘要格式及保存完成但通知未達的確認方式。
- 多參數組合是否需要動態增加、取消或優先執行。
- 現有本機 `MachinePool` 與第三方 scheduler 的效能分界。

## 知識範圍與前提

### 使用者陳述

本文件的需求內容來自本次對話中使用者對問題類型、實驗流程、比較方式、失敗行為、恢復邊界、輸出資料、高併發及共享快取的確認。

### 本輪實際讀取的專案來源

- `simulator/core.py`：目前 Simulator 的 sequential／batch 流程。
- `machine/core.py`：Machine、MachinePool、ProcessPool 任務分派及 worker 執行流程。
- `engine/models.py`：ExperimentSpec、RunTask、SolveResult 資料模型。
- `engine/assembly.py`：SimulationBundle 與 Engine 組裝流程。
- `solver/registry.py`：Solver 協定及 SolverRegistry。
- `solver/BSMA.py`：後續命名調整後的 MKP solver 路徑。
- `problem/registry.py`：問題類型註冊及共享記憶體封裝介面。
- `engine/builders.py`：內建 solver 建構子註冊。

這些程式碼只用來確認目前流程雛形，不代表現有實作已滿足本文件的全部需求。

## 交接資訊
