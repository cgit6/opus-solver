# 優化算法實驗系統需求基線

## 快速檢索卡

- 核心問題：在決定重構方式或採用第三方執行框架以前，先明確描述研究者如何使用優化算法實驗系統。
- 當前結論：系統應由實驗設定驅動，自動執行同一問題類型與算法的多組參數實驗，支援高併發、可重現及任務級恢復。
- 關鍵爭點：Server／遠端叢集、資料庫與檔案的分工、共享快取範圍、統計格式、效能門檻及 GPU／分散式 evaluator 尚未定案。
- 適用於：MKP、TSP、CVRP，以及未來的連續型最佳化和 AI 模型最佳化研究實驗。
- 不適用於：目前尚未確認的線上服務、多人平台、算法內部 checkpoint 恢復或特定第三方 scheduler 選型。
- 待驗證：高併發的量化指標、記憶體上限、統計模組支援範圍、資料保存策略及跨硬體執行邊界。

## 核心問題

目前專案需要從支援少數優化算法的實驗流程，擴充成可支援多種優化問題與研究方向的通用實驗系統。若先決定模組或框架，再回頭猜測使用方式，可能造成系統流程與實際研究工作不一致。

本基線先定義一次研究實驗的使用方式與必要結果，作為後續評估核心模組、scheduler、資料保存及效能設計的共同前提。

## 形成的知識

以下內容是本輪由使用者確認的需求，不是外部查證結果。

### 1. 實驗範圍

- 目前問題類型包括 MKP、TSP、CVRP。
- 未來需要擴充到連續型最佳化問題，以及以優化算法提升 AI 模型效能的研究。
- 一次實驗只處理一種問題類型與一個算法。
- 同一次實驗可以包含多組算法參數。

### 2. 使用流程

研究者提供問題類型、算法、參數組合、問題資料及重複次數等實驗設定後，系統應自動完成：

1. 載入問題資料與算法設定。
2. 展開問題實例、重複次數及參數組合形成任務。
3. 自動分派並執行任務。
4. 驗證及彙整每個任務的結果。
5. 產生原始結果與統計輸出。

研究者不需要逐步手動控制資料載入、任務分派或平行執行。

### 3. 比較與可重現性

- 不同參數組合應使用同一批問題實例。
- 不同參數組合應使用相同的重複次數。
- 隨機種子必須可追蹤且可重現。
- 這些條件的目的是讓參數組合之間可以公平比較。

### 4. 失敗與恢復

- 任一任務執行失敗時，整個實驗立即停止。
- 不採用自動跳過失敗任務的預設行為。
- 實驗因手動停止、程式錯誤或機器重啟而中斷時，恢復應從最後一個已完成的任務重新開始。
- 第一版不要求從算法內部的中間狀態恢復，因為算法內部狀態恢復被認為過於不可控。

### 5. 結果與統計

- 必須能取得每一個問題實例、每一次重複執行的詳細結果。
- 最終通常會彙整成各參數組合的統計表。
- 不同論文投稿可能需要不同統計格式，因此原始資料應保留，或至少能依設定重新產生所需統計資料。
- 實驗 YAML 應能設定輸出格式。
- 統計模組需要明確確認是否支援研究者需要的統計參數。

### 6. 效能與資源

- 系統需要滿足高併發需求。
- 任務執行時應有共用的快取狀態，避免相同資料或中間資源被大量重複載入而消耗記憶體。
- 高併發不能只以增加 worker 數量表示；還需要同時考慮資料共享、任務排程、記憶體占用及算法本身的執行成本。

### 7. 目前架構可延續的方向

現有流程已具備「實驗設定 → 問題資料 → RunTask → Solver.solve → SolveResult → 彙整」的雛形。後續設計應優先檢查這條流程能否擴充到上述需求，而不是預設必須整套重寫。

## 討論的演化

1. 原先討論集中在 RNG、checkpoint、資料庫、第三方 scheduler 及插件邊界，容易在尚未確定實際使用方式前先行決定技術。
2. 使用者指出專案首先需要確認定位與使用需求，否則後續系統設計可能偏離研究工作的實際流程。
3. 需求收斂後，主要使用情境被明確化為：一種問題類型、一個算法、多組參數，自動完成高併發實驗並輸出可重新統計的詳細結果。
4. 使用者進一步確定失敗時整個實驗立即停止，恢復以已完成任務為界線，而非保存和恢復算法內部狀態。
5. 最後補充高併發及共享快取是系統級要求，不能只視為單一算法的功能。

## 邊界與未解問題

以下項目尚未形成需求決定，因此不可在架構設計中假設已經確定：

- 是否需要 Server／API，以及是否支援多人或遠端叢集。
- 高併發的量化目標，例如任務數、worker 數、節點數及可接受的排程開銷。
- 共享快取的生命週期、共享範圍、失效策略及記憶體上限。
- 檔案保存與資料庫保存的最終分工。
- YAML 可設定的輸出格式，以及統計模組必須支援的完整統計量清單。
- 是否需要 GPU 或分散式 evaluator。
- 不同問題類型是否需要不同的資料表示、評估介面及結果欄位。
- 任務重試策略；目前已確認的預設是任務失敗即停止整個實驗。
- 多參數組合是否需要動態增加、取消或優先執行。
- 現有本機 `MachinePool` 與第三方 scheduler 的效能分界。

## 知識範圍與前提

### 使用者陳述

本文件的需求內容來自本次對話中使用者對問題類型、實驗流程、比較方式、失敗行為、恢復邊界、輸出資料、高併發及共享快取的確認。

### 本輪實際讀取的專案來源

- `simulator/core.py`：目前 Simulator 的 sequential／batch 流程。
- `machine/core.py`：Machine、MachinePool、ProcessPool 任務分派及 worker 執行流程。
- `engine/models.py`：ExperimentSpec、RunTask、SolveResult 資料模型。
- `engine/assembly.py`：SimulationBundle 與 Engine 組裝流程。
- `solver/registry.py`：Solver 協定及 SolverRegistry。
- `solver/BSMA_numba.py`：現有 Numba solver 的完整求解呼叫路徑。
- `problem/registry.py`：問題類型註冊及共享記憶體封裝介面。
- `engine/builders.py`：內建 solver 建構子註冊。

這些程式碼只用來確認目前流程雛形，不代表現有實作已滿足本文件的全部需求。

### LLM 背景知識

已啟用，但只用於說明一般的系統設計概念。未使用它作為第三方框架效能、功能或外部專案成熟度的證據；本文件也沒有外部查證來源。

## 交接資訊

可以安全採用的內容是「一次實驗的使用流程、比較條件、失敗與恢復邊界、結果需求、高併發及共享快取」這組需求基線。

不可假設的內容包括最終 scheduler、Server／API、資料庫方案、GPU 支援方式、共享快取實作及完整統計欄位。

後續若繼續討論，應先從未解問題中選一項收斂；建議優先確認共享快取的範圍與生命週期，因為它會同時影響問題資料載入、worker 架構、記憶體模型及高併發設計。
