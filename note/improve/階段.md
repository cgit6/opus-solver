目前最重要的是把工作切成有停損點的階段；每一階段驗證通過才進下一階段。

## 討論大綱與目前進度

1. 單次任務輸入輸出：責任與必要資訊已確認，正式型別仍待細化。
2. C++ 求解模組內部組裝：責任已確認。
3. 呼叫、資料交接及設定位置：部分待議；D35 曾選定的完整拓撲現在作重新評估基線，依 [14 的三個維度](../analysis/system_redesign/14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度) 比較架構組合。全量歷史一次交付、算法錯誤停止整場及 D34 同步 task 保存已確認，主管只收摘要／路徑，不重開主程序保存。
4. 多問題任務展開、算法支援與統計：需求已提出，細節未定。
5. 遷移順序與驗證：小步驗證原則已確認，具體執行方案尚待批准。

對照系統重構的七單元索引：第 1／2／4 單元已有 [19 的候選證據](../analysis/system_redesign/19_architecture_candidate_experiments.md)，未選新架構；第 3 單元設定政策已定待正式 API／交付；第 5／6／7 單元仍待討論。以下「階段」是未批准的正式實作路線，不表示原型還完全沒做，也不表示候選研究已通過正式 G2／G3。

共享資料方面，D74–D77 已確認的不變需求與原交接機制依 [08 的分層對照](../analysis/system_redesign/08_cpp_invocation_and_shared_memory.md#不變需求與原交接基線) 區分；新架構候選若改隔離準備、搬 SHM 或持有／連接／解除安排，須列差異待確認，不把整體共享需求重新當成未定。

保存方面，D18–D19、D34 已選的完整返回 Python 與 Python 輸出器仍是有效舊保存基線；Python-only 與 C++ 獨立輸出元件的候選差異依 [07](../analysis/system_redesign/07_history_return_and_storage.md#已確認交付需求與保存基線) 核對待確認，不能把輸出器語言等同算法的文件責任。

執行名詞及 D40 替換範圍依 [14](../analysis/system_redesign/14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍)：task 不等於程序／thread；同一邏輯工作鏈同步保存、交接及清理後才接下一題，不要求同 host 其他健康鏈等保存，也不預設永久綁 thread／程序。舊基線一 worker 對一程序，候選不能無條件沿用；實體替換時機／同伴影響仍待確認。

先用傳統與 AI 情境檢查共同邊界，再集中細化傳統問題。以下是實作路線草案，不和上述五項討論議題編號混用。

## 實作路線草案

```text
釐清責任
  ↓
定義資料契約
  ↓
拆開比較排程責任、執行拓撲與呼叫邊界，銜接資料與實驗安排；必要時用現有 Python 作契約原型
  ↓
製作最小 C++ 求解原型
  ↓
依原型證據收斂呼叫與並行架構組合
  ↓
完成含 addAct、最終驗證、完整歷史一次回傳及算法／保存錯誤分開處理的垂直流程
  ↓
加入整場實驗重啟後辨識／跳過已完成任務的續跑能力
  ↓
最後才做記憶體改善、目錄整理與 ML/HPO 正式整合
```

## 第一階段：只確定責任，不改程式

以下責任已確認：

- 實驗系統負責：
  - 展開任務
  - 分派任務
  - 接收結果
  - 保存結果
  - 統計分析
- 求解模組負責：
  - 依傳入數值準備問題；固定資料準備與交接依 [08](../analysis/system_redesign/08_cpp_invocation_and_shared_memory.md#不變需求與原交接基線) 的不變需求、原交接基線及候選差異核對
  - 執行算法
  - 驗證 objective、constraints 和 solution
  - 保存每次實際 addAct 快照，完成後一次回傳已驗證結果與全部紀錄
- 實驗系統只檢查通訊契約，不重算數學結果。
- 中斷後若另行重跑，未完成任務從頭開始，不恢復算法中間狀態。
- 算法執行的非預期錯誤，包括可捕捉錯誤與原生致命崩潰，依 D79–D80 停止整場實驗，包含其他算法及正在求解的 task；不再啟動新 task，保留已成功保存結果，不自動重跑。
- 求解異常所需的實際輸入須在求解開始前保留，出錯後保留可取得的資訊，不要求 Python 診斷 C++ 根因。
- Python 保存錯誤依 D40 留原因與 task 對應，清理成功且環境可信才重用，否則不再用不可信環境。舊基線可換程序；候選實體範圍／時機依 14 待確認，不只換 thread／物件當恢復、不一律全場停，也不自動重求解／重試。健康且整場未停止時同鏈才可接新題。
- 正常不可行是正常結果，不觸發算法錯誤停止。實體 host 退出按 D38 逐 task 處理已交付通知／完整回報，已交付不撤銷，缺回報者保留文件與事實、記未確認，不猜根因、不掃檔補登；未知退出處置待議。
- 算法錯誤停止整場的政策已確認；停止時點、正在執行工作如何安全收尾與未知退出如何判定仍待細化，不代表已能立即安全中止所有工作。
- 不處理磁碟滿／磁碟故障等硬體／資源層非預期行為，不為錯誤紀錄增加獨立儲存媒介。

保存原因依 [15 的單一留存界線](../analysis/system_redesign/15_task_failures_and_result_storage.md#保存錯誤原因的留存界線)：範圍內 Python 軟體保存失敗，實際原因與 task 必須事後可查，不能只記失敗、只靠通知或降為最佳努力。正式誰／何時／何處保存、完成判定及二次軟體失敗／落盤前退出的保障待確認，不默選 artifact、不宣稱全保證，也不自動列為 D26 排除。D38 不掃檔補登／重試，錯誤 artifact 不是結果交付，D40 及算法錯誤全場停止不變。

這階段的產物只是一份有效需求文件，並同步移除現有文件中衝突的 checkpoint 設計。

此責任分層已獲確認，不再要求重複確認；實作仍待後續議題收斂。

## 第二階段：定義三個資料契約

只討論資料，不修改算法。以下名稱與欄位是資訊範例，不是已固定的 schema；詳見 [任務與結果契約](../analysis/system_redesign/03_task_and_result_contract.md)。

### `RunTask`

描述要執行什麼：

```text
task_id
problem_type
problem_ref
solver_id
solver_config
seed
budget
求解模組選擇（若需要，表示方式待定）
```

### `ValidatedRunResult`

表示求解正常完成，而且求解模組已驗證結果：

```text
task_id
execution_status
solution_status
objective
solution_payload
validation
statistics
artifacts
全部實際 addAct 提交紀錄
```

### `SolveFailure`

表示沒有正常產生結果：

```text
task_id
failure_kind
message
diagnostics
```

這裡還要定義四種情況：

1. 找到可行解。
2. 正常跑完，但最終解不可行；仍返回真實目標及該解，標示不可行。
3. Solver 回傳的結果沒有通過 Validator。
4. 程式執行中發生錯誤。

求解完成、Python 保存完成及主程序確認交付要分清；寫檔失敗與無完成通知不能都當成算法失敗。`SolveFailure` 等名稱只是資訊範例，不代表保存錯誤與交付未確認已決定共用同一個型別。

停止點：使用幾個實際例子檢查資料結構，包括 MKP、SCVRP、連續型問題。

## 第三階段：可選的 Python 契約原型，不碰算法

若採這個遷移手段，可先建立：

```text
Python 求解任務包裝
```

它只是把現在的流程包起來：

```text
ProblemBank.get()
→ Solver.solve()
→ Problem.validate()
→ ValidatedRunResult
```

現在這段邏輯位於 [machine/core.py](../../machine/core.py)。若採此原型，`Machine` 只呼叫求解任務，數學驗證在任務內；不因此新增獨立 backend 服務，也不表示最終永久維護兩套正式求解模組。

這時：

- CDELS 不改。
- CDELS_2 不改。
- RNG 不改。
- 設定檔不改。
- 輸出內容不改。
- 不加入 C++。
- 不搬目錄。

停止點：完整測試證明新舊 Python 流程的任務、seed、objective、solution 和輸出完全相同。

此步若採用，是驗證新的任務邊界沒有改變既有行為；是否採用，仍由具體遷移計畫決定。

## 第四階段：製作最小 C++ 原型

已有的候選控制原型及真 CDELS fresh-process oracle 對照見 [19](../analysis/system_redesign/19_architecture_candidate_experiments.md)；尚未完成正式整合或 thread-safe CDELS port。以下是後續正式原型的選題與驗收要求，不是宣稱研究原型尚未開始，也不因測過就採用。

可先選一個小型 SCVRP 題目、一個 seed、少量固定迭代；題目與原型範圍在實作前確認。

以 D35 曾選定的完整方案作比較基線，依 [14 的三個維度](../analysis/system_redesign/14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度) 說清各候選的排程責任、程序／執行緒與 binding／IPC 組合，再製作小型原型。程序是否重用、是否使用執行緒與如何跨語言呼叫要分開；同程序擴充模組不排除多執行緒。

比較：

- 輸入資料傳遞成本。
- 啟動成本。
- 記憶體占用。
- C++ crash 對 Python worker 的影響。
- 打包及部署難度。
- 是否能回傳相同的 `ValidatedRunResult`。
- 是否完整返回每次 addAct 的編碼、適應值及實際外部快照。
- 是否在求解前保留實際輸入，已知算法錯誤後仍能對應 task、保留已知資訊並觸發整場停止；未知退出不猜根因，停止收尾於架構細化後驗證。
- 保存沿用 D34 的同步 task 位置與主管摘要／路徑要求；比較輸出器語言時，須依 07 列出 D18 完整返回 Python 及所有權差異待確認，不因 A 符合舊流程就優先 A。

這不是完整移植，而是用證據比較呼叫與並行架構的組合；尚未選定新方案。

停止點：以證據收斂架構組合，再細化正式介面；原型採用 pybind11 不等於正式工具或版本已定。

## 第五階段：完成一條 C++ 垂直流程

只處理：

```text
SCVRP Problem
＋
CDELS Algorithm
＋
SCVRP Validator
＋
addAct 狀態紀錄
＋
ValidatedRunResult
```

全部在 C++ 求解模組中完成。

舊 Python 保存基線中，Python 接收完整求解結果如下；候選若改完整歷史轉入 Python 的方式或返回邊界，須先依 07 列差異待確認：

```text
RunTask
→ C++ 求解任務入口
→ 最終結果與全部紀錄，一次返回
```

驗證內容包括：

- 固定 seed。
- 固定迭代數。
- 初始種群相同。
- 每代過程相同。
- 最終解相同。
- RNG 消耗相同。
- 可行性及 objective 相同。
- 真實目標與 legacy 搜尋罰分明確分開對照。
- 開關記錄不改搜尋結果；舊快照不受緩存重用影響。
- 沒有可行解時的回傳語意正確。
- 可捕捉算法錯誤與原生致命崩潰都觸發整場停止，含其他算法正在求解的 task；不再啟動新 task，輸入與已知錯誤按要求留存，已成功保存結果不被清除，不自動重跑。
- 保存原因留存，按 D40 驗證可信才重用、不可信環境不再用；候選替換範圍／時機及同 host 連帶影響須先依 14 確認再驗收，不默選立即或排空後退休，不把普通保存錯誤一律全場停。
- 未知退出只按收到的回報與已知事實記錄，不推翻完整成功／錯誤回報，不自動核對文件或補登成功；原因判定與安全處置仍待細化。
- 保存完成但通知未達時不偽造完成狀態；正式確認方式於實作前收斂。

停止點：完整通過 C++ legacy、Python CDELS 與新 C++ 任務入口的對照。

## 第六階段：整場實驗重啟後的任務級續跑

核心路徑須先驗證同步 task 保存、算法錯誤停止整場及各類異常的紀錄；之後再進一步設計與實作：

- 整場重啟時辨識先前已成功保存的任務。
- 重啟後跳過完成任務所需的標記與核對；staging／原子提交等具體機制另議，不能把核心單次交付判定全部延後。
- 已完成任務重跑時跳過。
- 中斷中的任務重新開始。
- 不做算法內部 checkpoint。

這項整場重啟後續跑功能等核心重構驗證完成後再處理，不等於延後核心錯誤分類、紀錄與停止要求。C++ 回傳不代表 Python 已落盤，更不代表 addAct 本身能恢復中間狀態。

- 目錄重構。
- 舊程式碼淘汰。
- 連續型 C++ 問題。

## 現在明確不做的事情

為了避免範圍再次膨脹，目前先凍結：

- 算法內部 checkpoint。
- RNG 中途狀態恢復。
- 遠端服務或 RPC。
- GPU／叢集架構。
- 超出本輪 addAct 責任的通用 Observation 框架。
- ML/HPO callback。
- 大規模目錄搬移。
- CDELS 演算法優化。
- 強迫所有 problem 使用同一種 solution 陣列。
- 歷史分批交付、算法／addAct 自行寫檔、背景 writer、Redis；C++ 獨立輸出元件仍是待比較候選，非已採用方案。
- 磁碟滿／磁碟故障等硬體／資源層專用處理，及為此新增的獨立錯誤保存媒介或服務。

本版接受單任務完整歷史可能耗盡 RAM 的風險，沒有暗中採樣或覆蓋舊紀錄的替代方案。

## 目前下一步

本次 [19](../analysis/system_redesign/19_architecture_candidate_experiments.md) 封存與只讀核對後停止，再依 [14 的比較維度](../analysis/system_redesign/14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度) 確認候選差異與方案，不直接移植。此次未編譯、求解、故障注入、重跑原 audit 或重驗未封存的大份完整輸出；原研究數字保留當時範圍。

依序收斂：

1. 先分開比較排程責任、執行拓撲與呼叫邊界，再核對輸出器語言、D18 返回／所有權及錯誤映射差異；D34 同步 task 保存位置不重開，算法錯誤停止與保存錯誤分開處理。
2. 問題固定數值的正式交接與共享實作；不變需求已定，候選若偏離 D74–D77 原交接機制須列差異待確認。
3. 設定讀取責任與最終位置。
4. 多問題任務、支援清單及統計。
5. 形成逐步修改計畫，明確批准後才改程式。

這樣每一步都能回退，既有系統也會持續可執行，不會發生改到一半整套系統不能使用的情況。
