你現在先不要動程式碼，也不用一次把最終架構想完。這不是「整套重寫」，比較像先建立新接頭，再逐一把舊流程接過去。

目前最重要的是把工作切成有停損點的階段；每一階段驗證通過才進下一階段。

## 整體路線

```text
釐清責任
  ↓
定義資料契約
  ↓
先用現有 Python 流程接上新契約
  ↓
確認系統行為完全沒變
  ↓
製作最小 C++ 求解原型
  ↓
決定 Python 如何呼叫 C++
  ↓
完成一條 C++ 垂直流程
  ↓
加入單任務保存／中斷續跑
  ↓
最後才整理 Trace、目錄及 ML/HPO
```

## 第一階段：只確定責任，不改程式

先定案以下原則：

- 實驗系統負責：
  - 展開任務
  - 分派任務
  - 接收結果
  - 保存結果
  - 統計分析
- 求解模組負責：
  - 載入問題
  - 執行算法
  - 驗證 objective、constraints 和 solution
  - 回傳已驗證結果
- 實驗系統只檢查通訊契約，不重算數學結果。
- 中斷時只從未完成任務重新執行，不恢復算法中間狀態。

這階段的產物只是一份有效需求文件，並同步移除現有文件中衝突的 checkpoint 設計。

停止點：你確認這個責任分層後才繼續。

## 第二階段：定義三個資料契約

只討論資料，不修改算法：

### `RunTask`

描述要執行什麼：

```text
task_id
problem_type
problem_ref
solver_id
solver_config
seed
budget
backend
```

### `ValidatedRunResult`

表示求解正常完成，而且求解模組已驗證結果：

```text
task_id
execution_status
solution_status
objective
solution_payload
validation
statistics
artifacts
```

### `SolveFailure`

表示沒有正常產生結果：

```text
task_id
failure_kind
message
diagnostics
```

這裡還要定義四種情況：

1. 找到可行解。
2. 正常跑完，但沒有可行解。
3. Solver 回傳的結果沒有通過 Validator。
4. 程式執行中發生錯誤。

停止點：使用幾個實際例子檢查資料結構，包括 MKP、SCVRP、連續型問題。

## 第三階段：先接回現有 Python，不碰算法

建立：

```text
PythonExecutionBackend
```

它只是把現在的流程包起來：

```text
ProblemBank.get()
→ Solver.solve()
→ Problem.validate()
→ ValidatedRunResult
```

現在這段邏輯位於 [machine/core.py](/home/sean/optiforge-optimization-solver/machine/core.py:171)。調整後，`Machine` 不再知道 Problem 怎麼驗證，只呼叫 backend。

這時：

- CDELS 不改。
- CDELS_2 不改。
- RNG 不改。
- 設定檔不改。
- 輸出內容不改。
- 不加入 C++。
- 不搬目錄。

停止點：完整測試證明新舊 Python 流程的任務、seed、objective、solution 和輸出完全相同。

這一步非常重要，因為它證明新的 backend 邊界沒有改變既有行為。

## 第四階段：製作最小 C++ 原型

先只選一個小型 SCVRP 題目、一個 seed、很少的迭代數。

分別評估：

- pybind11
- C++ executable/subprocess
- 必要時才考慮長駐 worker

比較：

- 輸入資料傳遞成本。
- 啟動成本。
- 記憶體占用。
- C++ crash 對 Python worker 的影響。
- 打包及部署難度。
- 是否能回傳相同的 `ValidatedRunResult`。

這不是完整移植，只是用證據決定呼叫方法。

停止點：選定 C++ invocation 方式。沒有證據前不先認定 pybind11。

## 第五階段：完成一條 C++ 垂直流程

只處理：

```text
SCVRP Problem
＋
CDELS Algorithm
＋
SCVRP Validator
＋
ValidatedRunResult
```

全部在 C++ 求解模組中完成。

Python 只會看到：

```text
RunTask
→ NativeExecutionBackend
→ ValidatedRunResult
```

驗證內容包括：

- 固定 seed。
- 固定迭代數。
- 初始種群相同。
- 每代過程相同。
- 最終解相同。
- RNG 消耗相同。
- 可行性及 objective 相同。
- 沒有可行解時的回傳語意正確。

停止點：完整通過 C++ legacy、Python CDELS 與新 native backend 的對照。

## 第六階段：單任務保存與中斷恢復

到這時才處理：

- 每個完成任務立即保存。
- 寫入 staging。
- 結果完整後原子提交。
- 已完成任務重跑時跳過。
- 中斷中的任務重新開始。
- 不做算法內部 checkpoint。

所以你的判斷是對的：這項功能可以等 backend 重構驗證完成後再實作；但 `task_id` 和完成狀態要先存在於資料契約中。

## 第七階段以後

前面都穩定後才處理：

- CDELS Trace／Observation 整理。
- 目錄重構。
- 舊程式碼淘汰。
- 連續型 C++ 問題。
- ML/HPO 的 ask/tell 或 callback。
- 第三方框架 adapter。
- 效能與共享記憶體優化。

## 現在明確不做的事情

為了避免範圍再次膨脹，目前先凍結：

- 算法內部 checkpoint。
- RNG 中途狀態恢復。
- 遠端服務或 RPC。
- GPU／叢集架構。
- 通用 Observation 系統。
- ML/HPO callback。
- 大規模目錄搬移。
- CDELS 演算法優化。
- 強迫所有 problem 使用同一種 solution 陣列。

## 你現在只需要做的決定

目前還不需要決定 C++ 怎麼呼叫，也不需要決定最終目錄。

下一步只做第一、二階段：

1. 整理有效需求，消除文件矛盾。
2. 定義 `RunTask`、`ValidatedRunResult`、`SolveFailure`。
3. 用 SCVRP、MKP、連續型問題各舉一個實際資料範例。
4. 停下來給你審核。
5. 你確認後才開始改 Python 系統。

這樣每一步都能回退，既有系統也會持續可執行，不會發生改到一半整套系統不能使用的情況。
