# 系統重構：討論進度與遷移路線

目前先不動程式碼，也不用一次把最終架構想完。不是「整套重寫」，而是確認邊界後逐一遷移。

目前最重要的是把工作切成有停損點的階段；每一階段驗證通過才進下一階段。

## 討論大綱與目前進度

1. 單次任務輸入輸出：責任與必要資訊已確認，正式型別仍待細化。
2. C++ 求解模組內部組裝：責任已確認。
3. 呼叫、資料交接及設定位置：部分待議；全量歷史一次回傳及軟體 task 異常後繼續已確認，worker／主程序保存仍是候選。
4. 多問題任務展開、算法支援與統計：需求已提出，細節未定。
5. 遷移順序與驗證：小步驗證原則已確認，具體執行方案尚待批准。

先用傳統與 AI 情境檢查共同邊界，再集中細化傳統問題。以下是實作路線草案，不和上述五項討論議題編號混用。

## 實作路線草案

```text
釐清責任
  ↓
定義資料契約
  ↓
收斂呼叫、資料與實驗安排；必要時用現有 Python 作契約原型
  ↓
製作最小 C++ 求解原型
  ↓
決定 Python 如何呼叫 C++，以及 Python 的結果保存路徑
  ↓
完成含 addAct、最終驗證、完整歷史一次回傳及軟體異常後繼續的垂直流程
  ↓
加入整場實驗重啟後辨識／跳過已完成任務的續跑能力
  ↓
最後才做記憶體改善、目錄整理與 ML/HPO 正式整合
```

## 第一階段：只確定責任，不改程式

以下責任已確認：

- 實驗系統負責：
  - 展開任務
  - 分派任務
  - 接收結果
  - 保存結果
  - 統計分析
- 求解模組負責：
  - 依傳入數值準備問題（誰讀哪些原始檔及 SHM 方式仍待議）
  - 執行算法
  - 驗證 objective、constraints 和 solution
  - 保存每次實際 addAct 快照，完成後一次回傳已驗證結果與全部紀錄
- 實驗系統只檢查通訊契約，不重算數學結果。
- 中斷時只從未完成任務重新執行，不恢復算法中間狀態。
- 單一 task 軟體異常須記錄，必要時恢復／替換 worker，再跑下一個新 task，不中斷整場，也不默認重試原 task。
- 求解異常保留實際輸入，不要求 Python 診斷 C++ 根因；Python 寫檔異常須保留原因。
- 不處理磁碟滿／磁碟故障等硬體／資源層非預期行為，不為錯誤紀錄增加獨立儲存媒介。

這階段的產物只是一份有效需求文件，並同步移除現有文件中衝突的 checkpoint 設計。

此責任分層已獲確認，不再要求重複確認；實作仍待後續議題收斂。

## 第二階段：定義三個資料契約

只討論資料，不修改算法。以下名稱與欄位是資訊範例，不是已固定的 schema；詳見 [任務與結果契約](../analysis/system_redesign/03_task_and_result_contract.md)。

### `RunTask`

描述要執行什麼：

```text
task_id
problem_type
problem_ref
solver_id
solver_config
seed
budget
求解模組選擇（若需要，表示方式待定）
```

### `ValidatedRunResult`

表示求解正常完成，而且求解模組已驗證結果：

```text
task_id
execution_status
solution_status
objective
solution_payload
validation
statistics
artifacts
全部實際 addAct 提交紀錄
```

### `SolveFailure`

表示沒有正常產生結果：

```text
task_id
failure_kind
message
diagnostics
```

這裡還要定義四種情況：

1. 找到可行解。
2. 正常跑完，但最終解不可行；仍返回真實目標及該解，標示不可行。
3. Solver 回傳的結果沒有通過 Validator。
4. 程式執行中發生錯誤。

求解完成、Python 保存完成及主程序確認交付要分清；寫檔失敗與無完成通知不能都當成算法失敗。`SolveFailure` 等名稱只是資訊範例，不代表保存錯誤與交付未確認已決定共用同一個型別。

停止點：使用幾個實際例子檢查資料結構，包括 MKP、SCVRP、連續型問題。

## 第三階段：可選的 Python 契約原型，不碰算法

若採這個遷移手段，可先建立：

```text
Python 求解任務包裝
```

它只是把現在的流程包起來：

```text
ProblemBank.get()
→ Solver.solve()
→ Problem.validate()
→ ValidatedRunResult
```

現在這段邏輯位於 [machine/core.py](../../machine/core.py)。若採此原型，`Machine` 只呼叫求解任務，數學驗證在任務內；不因此新增獨立 backend 服務，也不表示最終永久維護兩套正式求解模組。

這時：

- CDELS 不改。
- CDELS_2 不改。
- RNG 不改。
- 設定檔不改。
- 輸出內容不改。
- 不加入 C++。
- 不搬目錄。

停止點：完整測試證明新舊 Python 流程的任務、seed、objective、solution 和輸出完全相同。

此步若採用，是驗證新的任務邊界沒有改變既有行為；是否採用，仍由具體遷移計畫決定。

## 第四階段：製作最小 C++ 原型

可先選一個小型 SCVRP 題目、一個 seed、少量固定迭代；題目與原型範圍在實作前確認。

分別評估：

- pybind11
- C++ executable/subprocess
- 必要時才考慮長駐 worker

比較：

- 輸入資料傳遞成本。
- 啟動成本。
- 記憶體占用。
- C++ crash 對 Python worker 的影響。
- 打包及部署難度。
- 是否能回傳相同的 `ValidatedRunResult`。
- 是否完整返回每次 addAct 的編碼、適應值及實際外部快照。
- 是否在求解前保留實際輸入，程序異常後仍能對應 task，必要時恢復執行能力並執行下一個新 task。
- 同條件比較 worker 或主程序保存；不預設 B 必須多一層 Python worker，也不因 A 符合舊流程就優先 A。

這不是完整移植，只是用證據決定呼叫方法。

停止點：選定 C++ invocation 方式。沒有證據前不先認定 pybind11。

## 第五階段：完成一條 C++ 垂直流程

只處理：

```text
SCVRP Problem
＋
CDELS Algorithm
＋
SCVRP Validator
＋
addAct 狀態紀錄
＋
ValidatedRunResult
```

全部在 C++ 求解模組中完成。

Python 只會看到：

```text
RunTask
→ C++ 求解任務入口
→ 最終結果與全部紀錄，一次返回
```

驗證內容包括：

- 固定 seed。
- 固定迭代數。
- 初始種群相同。
- 每代過程相同。
- 最終解相同。
- RNG 消耗相同。
- 可行性及 objective 相同。
- 真實目標與 legacy 搜尋罰分明確分開對照。
- 開關記錄不改搜尋結果；舊快照不受緩存重用影響。
- 沒有可行解時的回傳語意正確。
- 單一 task 軟體異常後不終止整場；輸入與寫檔原因按要求留存，其他已保存結果不被清除。
- 保存完成但通知未達時不偽造完成狀態；正式確認方式於實作前收斂。

停止點：完整通過 C++ legacy、Python CDELS 與新 C++ 任務入口的對照。

## 第六階段：整場實驗重啟後的任務級續跑

核心路徑須先驗證 Python 保存及單 task 軟體異常後繼續；之後再進一步設計與實作：

- 整場重啟時辨識先前已成功保存的任務。
- 重啟後跳過完成任務所需的標記與核對；staging／原子提交等具體機制另議，不能把核心單次交付判定全部延後。
- 已完成任務重跑時跳過。
- 中斷中的任務重新開始。
- 不做算法內部 checkpoint。

這項整場重啟後續跑功能等核心重構驗證完成後再處理，不等於延後單 task 故障恢復。C++ 回傳不代表 Python 已落盤，更不代表 addAct 本身能恢復中間狀態。

## 第七階段以後

前面都穩定後才處理：

- 舊 CDELS 專用 trace 的額外整理；本輪 addAct 與完整歷史回傳已屬核心流程，不延至這裡。
- 目錄重構。
- 舊程式碼淘汰。
- 連續型 C++ 問題。
- ML/HPO 的 ask/tell 或 callback。
- 第三方框架 adapter。
- 額外效能與歷史記憶體優化；基本資料交接方式須在核心原型前決定。

## 現在明確不做的事情

為了避免範圍再次膨脹，目前先凍結：

- 算法內部 checkpoint。
- RNG 中途狀態恢復。
- 遠端服務或 RPC。
- GPU／叢集架構。
- 超出本輪 addAct 責任的通用 Observation 框架。
- ML/HPO callback。
- 大規模目錄搬移。
- CDELS 演算法優化。
- 強迫所有 problem 使用同一種 solution 陣列。
- 歷史分批交付、C++ 直接寫檔、背景 writer、Redis。
- 磁碟滿／磁碟故障等硬體／資源層專用處理，及為此新增的獨立錯誤保存媒介或服務。

本版接受單任務完整歷史可能耗盡 RAM 的風險，沒有暗中採樣或覆蓋舊紀錄的替代方案。

## 目前下一步

先審閱本次整理的設計文件，再接續第三項中「Python 如何呼叫 C++」的討論；不是直接開始移植。

依序收斂：

1. C++ 呼叫、worker／主程序保存與軟體 task 異常後繼續的候選機制及原型驗收範圍。
2. 問題固定數值的交接、共享與生命週期。
3. 設定讀取責任與最終位置。
4. 多問題任務、支援清單及統計。
5. 形成逐步修改計畫，明確批准後才改程式。

這樣每一步都能回退，既有系統也會持續可執行，不會發生改到一半整套系統不能使用的情況。
