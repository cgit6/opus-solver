### 不要重新詢問的既定前提

- 首版包含 MKP 的 BSMA／BSCA／HSMSCA 與 45 組參數、SCVRP、單目標連續問題、固定欄位混合編碼、多目標及混合編碼多目標的組合、小型特徵篩選。
- 算法 YAML 在 C++ 模組內，每算法一份，同存能力／參數規則及各組專用實際值；Python 指定來源及原組號，不開檔解析。
- 種群大小屬算法參數，各組可不同；單一解算法不強加種群參數。整次求解停止設定仍屬實驗 YAML，run／exp 各自整場統一、逐 task 套用。
- 一個 task 是「一個問題實例、一個算法、一組參數、一個 seed」的一次完整求解。一般 run 明列 seeds，組內全配對、組間不交叉；C++ 展開及判重，不擴大選取範圍。
- Python 只提供傳統題庫來源及選題；C++ 直接讀取、檢查與準備。同題相同固定資料場內準備一次；全部選中題目及必要預檢通過才搜尋，不先跑合法子集。
- 本場題庫留至整場結束且全部引用釋放；task 的 RNG、編碼、分數、算法緩存、最佳結果獨立。算法不得改共用題目。
- 問題判定、算法搜尋、求解任務最終驗證；不可行、正常無候選解及執行錯誤分開。搜尋罰分不能冒充真實目標值。
- 正確增量更新允許；每完成一個候選解評分計一次，完整一次再三次完成的移除更新共四次。最終驗證另計，提交／複製分數不計。
- 多目標返回算法自身維護的最終解集合；首版只支援迭代／時間上限，不支援的提早停止整場預檢拒絕；同一檢查點所有已啟用且成立的停止原因都要保留。
- `addAct` 不評估、不修復、不消耗 RNG；快照不受後續更新覆寫。固定輸入、seed、迭代及對齊條件下，紀錄開關不能改變搜尋。時間停止不承諾同迭代數。
- Python 不再逐 task 登記、ACK 或接收開始／完成通知；準備完成也是 C++ 內部階段。管理端只接整場終結摘要、位置及可取得錯誤，不取得完整歷史，也不保證即時 task 清單。
- 完成交付前確認管理／通訊中斷，停止整個 C++ 程序，不等在途算完；沉默不等於斷線，不新增無訊息超時。缺完整終結回報，不掃檔或靠退出碼補登成功、不自動重跑。
- 每場新識別加入檔名；同名同設定不覆蓋前場，撞名不得覆寫，命名不消耗算法 RNG。
- 硬體／資源故障及額外儲存備援不納入保障；路徑、權限、序列化等軟體保存錯誤仍須處理。Linux／WSL 首版範圍不變。

使用者選擇：

> 留下可取得的錯誤紀錄後，終止整個 C++ 程序；接受其他在途解與尚在記憶體的歷史遺失。

不再安排新 task、不等待其他 task 到下一個合作停止點或照原額度算完。已存好資料保留，不自動重跑。原生致命崩潰本來就未必有機會留因；不能將此選擇寫成「所有致命退出都保證完整保存／清理」。正式終止與已知錯誤交付機制歸單元 10，事件處置仍須完成單元 7 核對。

### H7-02｜開始前實際輸入／task 關聯保存失敗：停止整場

使用者選擇：

> 停止整場，因為這次實驗已有工作無法留下必要的追查資料。

不是跳過該 task、繼續其他題目。沒有完成必要事前留存的 task 不能開始算法。**exp 是否仍要求正常逐 task 留存這類資料尚待第五節回答**；不能用 H7-02 偷偷替該題選答案，也不能取消 run 的既定事前留存責任。

### H7-03｜原先 exp「task 詳細輸出失敗後繼續下一 seed」的回答

使用者原先選擇：

> 繼續試下一個 seed；新 seed 若已開始求解，仍占本題 repeat 一次，失敗輪次不補跑。

當時假設 exp 仍為每個 task 保存結果及歷史：有一份必要輸出失敗，該 seed 不能收錄；同輪其他正常 task 仍完成並保存，再依政策安排下一 seed。

**這個具體分支因第四節的新輸出分工而不再適用 exp。** 新設計沒有 exp 的 task 詳細結果／歷史檔，不能繼續列出此種 exp 寫檔失敗，也不能把這個回答不加說明轉成 run 的新決議。保留原答覆及背景，是為避免新環境重問或誤套。

既有 `repeat` 只計真正嘗試的新 seed、舊 seed 不占額度、碰撞跳過不計次等規則不變；異常中斷時無法確認的計數不得推造。

### H7-04｜C++ 連錯誤原因也存失敗：終結失敗回報交給 Python

在 Python 仍可聯絡的前提下，使用者選擇：

> 以整場失敗回報把已知原因交給 Python 留存，停止本場；不新增逐 task 通知。

不能只放在 C++ 記憶體等整批正常結束。這是整場失敗交付，不恢復逐 task 進度通知。錯誤紀錄須保存實際原因，不只寫「失敗」；若通訊也失效，只能記錄實際可取得的事實，不能捏造原因或已交付成功。Python 二次保存／回報失敗等細節仍須在單元 7／10 明確化，不聲稱已有正式 fallback 實作。

### H7-05｜中斷前已存好的部分 seed 名單可人工再使用

最初使用者表示看不懂，經白話例子確認：某題要收集 100 個，已正式收錄並存好 20 個後整場中斷；下一場可以手動以 `replay` 指向完整可讀的這份名單，先重新測試該 20 個。

使用者最後選擇：**允許使用**。

- 只使用已成功保存、完整可讀且可對應題目的清單，不從損壞或半寫入內容猜 seed。
- 下次仍按本次題目、算法、參數、停止及收集條件重新求解、篩選；不能直接沿用歷史分數或合格判定。
- 來源實驗未正常完成應明示；部分清單不代表原實驗成功。
- 不自動掃檔、接續算法、中途恢復或只補失敗工作；完整設定與既有來源預檢仍要通過。
- 「下一場要補足 80 個合格 seed」不等於最多只需再嘗試 80 次。

### H7-06｜seed 名單本身保存失敗：停止整場並留因

使用者後來以第四節原話明確回答：

> 如果寫 seed 名單寫檔失敗，那停止整場，留下錯誤原因。

不採「停止更新名單但繼續整場求解」的選項。先前成功保存的名單與其他已存資料保留；失敗更新不能宣稱已保存、收滿或整場完成。與 H7-04 核對錯誤原因保存及終結回報，不新增硬體備援保障。

### 尚不能冒充使用者決議的工程建議

助理曾提出：最終驗證發現分數不符／編碼損壞應視為執行錯誤；清理失敗導致共用狀態不可信應停止整場。這些是待完整事件核對的工程建議，**不是問答工具中另獲使用者選定的新條文**。應與既定正確性、錯誤分類及整場停止政策一起收斂，不將正常不可行或無候選解改成錯誤。

## 四 最新且已確認的輸出分工：取代原先 exp 全量落檔

使用者原話：

> 喔我調整一下輸出內容那 exp 模組不輸出 "每個 task 的詳細紀錄" 只輸出 "收集到的 seed 名單" 但是 run 模組只輸出 每個 task 的詳細紀錄 不輸出 seed 名單，然後回答你的問題如果寫 seed 名單寫檔失敗，那停止整場，留下錯誤原因。

| 入口 | 已確認的研究輸出 | 不再要求的研究輸出 |
| --- | --- | --- |
| `run` | 各 task 的詳細結果與完整提交歷史，沿用結果 JSON／歷史 JSONL 的設計。 | 收集到的 seed 名單。一般 run 本來就不負責篩選合格 seed。 |
| `exp` | 按題目及既定順序正式收錄的 seed 名單，供下次優先試用。 | 每個 task 的詳細結果 JSON 與完整歷史 JSONL，不論該 seed 收錄與否。 |

因此：

- 原單元 6「收錄與未收錄的 exp task 都保存全部結果及歷史」已被明確取代，不能只把未收錄者刪掉、仍替收錄者存詳細檔。
- exp 仍需真的求解、評估、最終驗證，將結果交給 C++ 收集功能比較；不輸出 task 詳細檔不等於不產生計算結果，或只信任歷史合格標記。
- 收集可能使用已收錄輪次的統計／比較資料；在相關判斷仍引用時不能提前釋放。該類資料與 `addAct` 完整快照不是同一件事。
- 本輪沒有將寫檔移回 Python，也沒有改變 C++ 收集責任、原組號、seed 順序、額度或同題逐輪規則。
- run 的外部資料開關仍只控制外部快照，不省略基本歷史；不能藉它悄悄實作 exp 的整份歷史關閉。exp 是否關閉整個歷史累積仍未答。
- seed 名單是研究檔案；C++ 向 Python 的整場終結摘要／位置／錯誤是管理交付，不能因兩者都叫「摘要」就一併取消。
- 是否另外產生統計報告、exp 能向 Python 提供哪些必要彙總，仍由單元 9 依新輸出範圍確認，不能自行加回 exp 的詳細紀錄檔。
- exp 正常時還要不要保存逐 task 實際輸入與關聯，是第五節的獨立未答問題；保留錯誤原因的明確要求不因此取消。

新流程的企劃骨架：

```text
共用：Python 交付安排 → C++ 預檢／題目準備 → C++ 安排與求解／驗證

run：每 task → C++ 同步保存結果 JSON／歷史 JSONL
            → 完成相關使用及清理 → 下一 task
     不輸出收集 seed 名單

exp：同題同 seed 全部所選算法／參數組結果齊備
     → C++ 按本次條件判斷 → 成功更新正式收錄 seed 名單
     → 依收滿／repeat 等規則決定下一輪
     不輸出 task 詳細結果／歷史
     事前追查及記憶體歷史策略：待回答

整場：Python 接收終結交付；缺少回報不掃檔補登成功
```

### P7-A｜exp 是否仍保存正常逐 task 的追查輸入

原問題：

> exp 不輸出編碼、分數及歷史檔後，是否仍保留「開始前的實際輸入、task 關聯及錯誤原因」，讓出錯時能追查？

| 選項 | 含義與影響 |
| --- | --- |
| 仍保留追查紀錄（助理建議，未選定） | 正常研究產物只有 seed 名單；另外保留必要輸入與錯誤紀錄，維持事前追查能力。這些紀錄不是候選解／分數／歷史詳細檔。 |

要確認的是責任與追查能力，不是先選輸入檔名、schema、日誌庫或儲存媒介。不要為滿足「只輸出 seed 名單」而自行把錯誤紀錄也取消。

### P7-B｜exp 是否停止在記憶體累積 addAct 歷史

原問題：
