## 一 已確認小節：共用設定與利用舊 seed 加速收集

### 本次實驗名稱與併發數

一般 `run` 與 `exp` 都在各自實驗 YAML 明寫 `worker_count`，必須是正整數；缺少就報錯，不補預設、不沿用程式寫死值。它表示最多同時求解幾個 task，不直接表示 Python 程序數，也不在此決定 C++ 執行緒與保存／清理階段的具體配置，這些歸單元 4。

實驗名稱使用本次 YAML 的 `experiment_name`。例如來源摘要屬於 `test_A`，本次 YAML 填 `test_B`，本次實驗就叫 `test_B`；原摘要名稱只作來源資訊，不覆蓋本次名稱。同名輸出的處理與保存位置歸單元 6、9，不由這個例子決定。

以下是兩個入口各自 YAML 可使用的共用欄位片段，不是完整設定，也不是目前讀取器已支援的新功能：

```yaml
experiment_name: collect_reuse_001
worker_count: 8
```

這裡的 8 是示例，不是預設值或固定的程序／執行緒數。

### 入口與模式

摘要路徑仍設在 `cli/exp/exp_cfg.yaml` 的 `replay` 欄位，不是一般 `cli/run` 設定。`replay` 的值是摘要檔案路徑，不是布林開關。其用途已釐清為加速本次 seed 收集，兩種分支都要按本次收集條件判斷：

| 設定意圖 | 應執行的流程 | 不做的事 |
| --- | --- | --- |
| 未指定摘要路徑 | 從頭收集 seed，依本次條件判定是否收錄及是否繼續安排工作。 | 不自行尋找或套用舊摘要。 |
| 指定有效摘要路徑 | 對本次選中的題目先試用摘要內對應的舊 seed，重新求解與判斷；合格數不足再補找新 seed。 | 不直接採用歷史分數、歷史合格判定或全部原任務配對；不是故障自動重試或中途續算。 |

即使本次收集條件已改變，仍先試舊 seed，再用本次條件判斷；不新增自動比對歷史條件、版本鎖定或改回舊條件的流程。沒有對應舊 seed 的已選題目從頭收集，摘要中未被本次選取的題目不執行。

一般 `cli/run` 的用途不因此改變。其一般實驗與人工指定配對仍依原有設定原則討論；不因本章而增加一條「一般入口直接讀 seed-bank」的路徑。

### replay 欄位與路徑規則

| `replay` 設定 | 應執行的流程 |
| --- | --- |
| 省略欄位或填 YAML 的 `null` | 表示未指定摘要，執行 seed 收集。 |
| 空字串 `""` 或只有空白的字串 | 同樣表示未指定摘要，執行 seed 收集，不因這種空值報錯。 |
| 非空白字串 | 原樣作為摘要路徑，取得對應題目的候選 seed 加速本次收集；不得自動去除前後空白。 |
| 其他型別，例如布林、數字、清單或物件 | 報設定錯誤，不開始收集或求解，不先轉成字串繼續。 |

指定路徑時，還須遵守以下規則：

- 只接受相對路徑，以專案根目錄為起點，不以 `cli/exp/` 或其他啟動位置作為找檔起點。
- 實際指向的摘要必須位於專案內。絕對路徑即使指向專案內也不接受；相對路徑若經 `..` 或符號連結指向專案外，同樣報錯。
- 不一律禁止路徑含 `..`；判斷的是實際目標是否仍在專案內，不能只看文字沒有以 `/` 開頭就放行。
- 非空白路徑原樣查找。例如 `" output/example/summary.json "` 不得默改成 `output/example/summary.json`；若原樣找不到檔案就報錯。只有整串空白才依上表走收集。
- 檔案不存在、無法讀取、指向的不是摘要檔案或內容不合法時，指出問題，不開始求解，也不退回全新收集。摘要須能提供或明確連到可對應題目的候選 seed，不能只憑平均值或執行次數推算；正式格式仍待議。

「有效摘要沒有某個已選題目的舊 seed」與「指定摘要本身無效」不同：前者對該題從頭收集，後者報錯，不偷偷略過來源錯誤。

這是摘要入口的路徑限制，不是對整個專案所有檔案讀取增加一套規則。摘要所連結明細的路徑規則、正式交接及可用性仍待後續單元確認，不能直接套用本節限制。

以下只示範新設計中的 `replay` 欄位，不是完整可執行的 exp 設定；現有讀取器尚不支援此欄位，本輪也不修改正式 YAML。

```yaml
# 新設計示例：執行 seed 收集；省略欄位、空字串或只有空白也相同。
replay: null
```

```yaml
# 新設計示例：從專案根目錄讀摘要，先試用對應題目的舊 seed。
replay: output/example/summary.json
```

指定有效摘要仍不代表完整實驗設定已通過：本次名稱、`worker_count`、頂層 `stop_condition` 與完整收集設定等仍須通過必要預檢；完整設定與正式介面仍待議。

### exp 統一停止條件與選填原組別

新設計由 `cli/exp/exp_cfg.yaml` 明寫一份頂層 `stop_condition`，從頭收集、試用舊 seed 及不足後補找所產生的每個 task 都使用它。每個 task 各自套用同一份停止設定，不是整場共用一個迭代或時間額度；例如設最多 5,000 輪，是每個 task 各自最多 5,000 輪，不是將 5,000 輪分給所有 task。

- 不以算法檔或歷史摘要中的停止值為來源，不提供按算法、題目或原組別覆寫，也不在本次設定缺漏時回退到這些值。
- 沿用已確認的 `stop_condition` 欄位、型別與單目標語意，見 [既有停止欄位與語意來源](../system_redesign/18_experiment_configuration_and_task_expansion.md)。本次改的是 exp 的提供位置與適用範圍，不改迭代計數、計時、零次初始化及提早停止的既定規則。
- exp 的兩種模式都必須明寫停止設定及其中必要值。缺少必要值、型別錯誤、欄位互相衝突，或任一所選算法不支援時，啟動前報錯，不補預設、不先跑合法子集。
- Python 檢查實驗安排、傳遞並記錄實際使用的設定；C++ 依既定責任檢查支援能力並執行停止判斷。多目標停止語意仍待對應單元確認，不直接套用單目標比較。
- 這份設定只管一次求解的停止，不取代 `collects` 的合格數量目標或 `repeat` 的新 seed 嘗試上限。每題試用舊 seed 不占 repeat，補找真正嘗試的新 seed 無論合格與否都計次；跳過重複值不計次。不按單一算法 task 扣額度，也不將 repeat 當成算法迭代上限。

以下是新設計的局部示例，不是現有讀取器可執行的完整設定，5,000 也不是自動補入的預設值：

```yaml
replay: null
stop_condition:
  type: max_iterations
  max_iterations: 5000
  max_seconds: null
  stop_on_best_known: false
  max_no_improvement_iterations: null
```

這個示例表示收集時每筆 task 最多更新 5,000 整輪，不啟用達標或無改善提早停止。將 `replay` 改成有效摘要路徑時，先利用舊 seed 加速收集；試用及補找產生的 task 都使用這次同一份 `stop_condition`，不恢復歷史或算法檔的停止值。新讀取器與正式執行接線尚未實作。

摘要中的原組別資料仍為選填：有則保留，沒有也不阻擋試用舊 seed、不猜測補齊。它不決定本次選題、算法或停止條件，因此不需要為此建立原組別停止對應表，或強制新增組名、編號。選填組別的正式保存表示與報告用途留單元 6、9 細化。

本節維持取代 exp 先前「各原分組分別明寫停止條件」及「原組別資訊必填」的安排；一般 `cli/run` 的分組停止設計不受影響。摘要須提供可對應題目的候選 seed，本次算法與參數組由 YAML 提供，不再以還原全部原任務配對為摘要入口的用途。

### 完整收集設定、預檢與實際篩選

有無摘要都必須完整提供 `collects`、`repeat`、`solvers`、`dataset_settings` 及其必要子設定，不能全部省略或只提供部分。這些欄位不只是保留來檢查，而是本次收集真正使用的設定。

這套設定須通過完整啟動前檢查，包括必要欄位、型別、合法值、引用資源及支援配對。例如本次 YAML 指定的算法、參數組、題目或比較條件已不存在，即使摘要沒有列到它，也要指出並拒絕啟動。問題及算法的專用規則仍由對應模組提供，不在 Python 另外維護一份。

檢查與執行的界線如下：

- 預檢先確認比較條件存在且設定合法，不在預檢中執行算法或拿舊結果決定收錄。正式求解後，必須實際呼叫本次收集判斷；舊 seed 的新結果也不例外。
- 本次 YAML 決定題目、算法、參數組、收集條件及收集數量。摘要提供候選 seed，不覆寫這些選取；合格數不足時要補找，不保證嘗試一次就能收錄一個。
- 摘要與本次選取可以不同。對應題目的舊 seed 配合本次算法／參數組求解；本次新增的題目從頭收集，摘要多出的未選題目不執行。不能把不同題目的 seeds 任意互相套用。
- 摘要來源及本次共用 `stop_condition` 仍須通過必要預檢。收集設定合法不能掩蓋來源內容或停止設定錯誤，也不以歷史值修補本次缺少的設定。
- 本次 `dataset_settings` 中的組別欄位按收集規則檢查，例如必要的 `experiment-id` 不能省略；摘要原組別仍選填，缺少不能反過來以收集設定補造或要求必填。

前面的示例都是局部片段，不表示可以省略完整收集設定。順序、收滿停止追加、repeat 計數與兩種重複處理依下節已確認規則執行；具體預檢 API、通訊格式、預檢接線及資料準備方式仍待細化，不因規則已確認就視為正式介面已完成。

### 舊 seed 順序、收集上限與避重

以下為 2026-10-27 逐題確認的有效規則，適用於每題的收集流程；不是對算法內部 RNG 或候選解搜尋策略的修改。

| 項目 | 已確認規則 |
| --- | --- |
| 舊 seed 判斷順序 | 保留摘要順序，例如 `[7, 3, 9]` 就依 7、3、9 判斷；不因 seed 3 先算完而先收錄。這不要求求解必須序列執行。 |
| 收滿停止追加 | 達到本次 collects 後，不再安排後續候選，不要求試完摘要中的全部舊 seed。已派出工作的收尾另歸單元 4、7，不承諾完全沒有在途多算或立即中止。 |
| repeat 額度 | 只限制本題補找時真正嘗試的新 seed。舊 seed 不占額度，新 seed 合格或不合格都計一次；一個 seed 輪次內的多個算法／參數組 task 不各扣一次。 |
| 摘要候選重複 | 同一題的候選清單含重複 seed，啟動前報錯、不啟動，不自動去重；不同題使用相同 seed 不算重複。 |
| 補找撞重複 | 若產生的 seed 本題已試過，不重新求解、不扣 repeat，繼續產生下一個；已試的舊 seed、新 seed、合格與不合格者均在避重範圍內。 |
| 補找起點 | 沿用固定產生規則，從該題固定起點重新往後產生；不要求摘要保存或接續舊搜尋位置。生成位置會因跳過重複而前進，不等於實際新 seed 嘗試數。 |
| 額度用完仍不足 | 保留已得到的結果，明示該題實際收集數量與未收滿，繼續其他題目；不再替本題追加求解，不當成算法錯誤，也不冒充已收滿。 |

例如每題 `repeat: 100`，已試用 20 個舊 seed 但尚未收滿，仍可再真正嘗試最多 100 個新 seed。這是最多 120 個不同 seed 的求解輪次，不是最多 100 個，也不是 120 個單一算法 task；若先收滿就提早停止追加。從頭收集、沒有舊 seed 的題目，全部真正嘗試的 seed 都屬新 seed，受 repeat 限制。

必須分開三件事：摘要候選資料重複是輸入錯誤；補找產生碰撞是跳過與計數問題；一般 task 判重仍遵守既有規則。同一輪中各算法都使用 seed 7，不代表候選清單列了多次 7，不應誤報候選重複；正式來源格式與 task 表示仍由後續介面設計處理。

「未收滿」是預期的收集結束，不是非預期算法錯誤。原有算法錯誤停止整場、正常不可行照實回報、保存與交付錯誤分別處理的政策不變；普通收集不足不能擴大成忽略這些錯誤。

本節不另選正式 seed 產生器、合法值域或空間耗盡政策，不新增設定欄位或通訊格式。並行在途工作的計數與收尾、報告欄位及保存表示仍留單元 4、6、7、9 細化；規則模型不代替這些機制的驗證。

目前收集的一輪，是同一題、同一個 seed，讓所選算法／參數組各求解一次，再將這一輪結果交給收集判斷；它可能參考已收集結果，而不是每個 task 各自算一個收錄 seed。原始碼依據見第三節。一個 seed 若對應 45 組算法參數，就可能需要 45 個 task；收集數量不等於 task 數量。新架構的正式判斷接線及規則表示仍待對應單元細化，不能由本輪另加一套比較公式。

例如摘要提供下列題目與候選 seed；舊算法與原組別只是來源資訊，不控制本次選取：

| 原組別（選填） | 題目 | 算法／參數組 | 起始 seed |
| --- | --- | --- | --- |
| 原組 A | MKP／SENT／sent02 | BSCA／0 | 3 |
| 原組 B | MKP／WEING／weing5 | HSMSCA／2 | 7 |

若本次 YAML 仍選這兩題，改選 BSCA／0 與 HSMSCA／2 兩組參數，就分別用 sent02 的 seed 3、weing5 的 seed 7 跑本次兩組，每個 seed 的新結果交給本次條件判斷；不是只執行來源中的兩筆原 task，也不把 seed 7 自動套給 sent02。若本次只選 sent02，再新增另一題 P，則 weing5 不執行，P 從頭收集；精確題目對應與來源明細格式仍待正式資料契約收斂。

若本次選的 BSCA 參數組 0 種群大小原本為 20，目前檔案改成 40，就讀取並記錄 40，不因摘要保留過 20 而改回。當前選取的參數組不存在、停止設定缺少或算法不支援本次題目時，先報錯，不開始求解、不用歷史值補齊；也不把沿用舊 seed 誤認為結果必須與歷史相同。

## 二 責任流程與預檢邊界

利用舊 seed 加速收集的責任流程如下，不預先決定具體 API、通訊、檢查先後或並行派工：

1. Python 讀取本次 exp YAML 的名稱、併發數、選題、算法／參數組、收集條件、數量與停止設定，按 `replay` 規則決定是否使用摘要。沒有摘要就從頭收集；指定來源無效則報錯，不偷偷退回。
2. 有摘要時，取得可對應題目的有序候選 seed 與可用來源資訊，同題候選重複列為啟動前輸入錯誤，不自動去重。只對本次選中題目試用舊 seed；沒有舊 seed 的已選題目從頭收集，不執行摘要多出的未選題目，也不推算來源未記錄的 seed。
3. Python 協調完整預檢；C++ 問題模組與算法提供專用輸入、參數及支援檢查。來源、本次完整設定與配對都須合法，全部本次選中題目準備成功後才開始任何 task，不先跑合法子集。題目與算法數值讀目前指定檔案，保留實際輸入及執行關聯。
4. 對有候選 seed 的已選題目先試用舊 seed，以本次 YAML 的算法及參數組建立 task；每筆都使用本次 exp 共用停止設定。C++ 完整求解、最終驗證，依既有責任保存結果與全部實際提交。
5. Python 依摘要順序執行舊 seed 的收集判斷，不因結果完成先後改變收錄順序；合格才計入數量，收滿就不再追加。條件已變仍重新判斷，不拿歷史合格標記直接接受，也不自動比對歷史條件。
6. 舊 seed 試用後仍不足，從固定起點補找，跳過本題已試 seed，不扣 repeat；真正嘗試的新 seed 合格與否都計次。收滿停止追加；新 seed 額度用完仍不足則保留結果、記錄數量並繼續其他題目，不是算法錯誤。在途收尾與正式報告接線仍待對應單元。
7. Python 依實際取得的結果、來源與收集事實彙整報告；保存、交付、清理及異常處置不因使用舊 seed 而省略，正式報告與摘要格式歸單元 6、7、9。

一般 task 判重不取消，但不與候選清單檢查混用：摘要同題候選重複拒絕啟動，補找撞到已試 seed 則跳過、不重新求解、不計新 seed 嘗試。正式預檢 API、錯誤格式及資料交接仍待議。

這是本次實驗主動試用舊 seed，不是故障自動重試、只補失敗 task、自動跳過成功或中途續算。歷史合格標記不能代替本次判斷；正常不可行仍按原則回報，不冒充算法錯誤。摘要在中斷後是否可用、哪些來源內容可供試用仍須於單元 6、7、9 收斂，不宣稱現有恢復機制已驗收。

## 三 摘要的必要能力與目前實作

### 必要能力

作為本次候選 seed 來源，摘要必須提供或明確連到可對應題目的 seed 資訊，不能只保存統計平均值或次數。必要能力是「能知道這些 seed 對應哪個題目」，不是要求沿原算法／參數組重建全部歷史 task；算法與參數組來自本次 YAML。題目對應方式、來源正式必要欄位及明細格式留單元 2、6、9 細化。

若來源無法確定候選 seed 或其題目對應，不能只因檔名是 `summary.json` 就視為可用，也不能從平均值、次數或檔名猜測補齊。這與來源有效但不含本次新增題目的 seed 不同：後者可對新增題目從頭收集，不是摘要解析失敗後的偷偷退回。

摘要原組別仍選填、有則保留，歷史算法、分數及合格標記不控制本次選取或接受。來源內嵌或連結明細、保存時點及中斷可用性仍待議；本次實際 task 的完整輸入與結果仍須記錄，候選 seed 來源不能代替完整求解紀錄。來源檢查不等於讓 Python 重算目標函數或驗證解的數學正確性。

| R05 舊 10 個全通過 | 本次目標 100 個合格 seed，舊 10 個重新求解後都通過本次判斷。 | 尚需補收集 90 個合格 seed，不代表只需再嘗試 90 次。 |
| R06 參數已變 | 同一算法及參數組，歷史種群大小 20，目前檔案為 40。 | 讀取並記錄目前的 40，不改回 20，也不因此宣稱原結果可重現。 |
| R07 題目數值已變 | 題目識別相同，目前合法數值不同於歷史。 | 讀取並記錄目前值；仍做必要預檢與最終驗證，不因歷史差異自動阻擋、比對或修正。 |
| R08 歷史停止不同 | 原組 A、B 歷史上限不同，本次 exp 明寫最多 5,000 輪。 | 本次試用及補找的各 task 都使用本次 5,000 輪設定，不用原組別上限，也不按算法或組別覆寫；不代表正式停止接線已驗收。 |
| R09 摘要資訊不足 | 來源只有平均值／次數，無法得知可用 seed 或對應題目。 | 報來源內容錯誤，不推算、不開始求解，也不偷偷退回從頭收集；原組別缺少不屬此錯誤。 |
| R10 本次設定缺少 | 本次 YAML 選取的參數組不存在，或本次頂層停止設定缺必要值。 | 預檢報錯，不以歷史值或預設補上，不先跑其餘合法任務；不是要求本次沿用歷史參數組。 |
| R11 算法不支援 | 當前選取的算法不支援本次題目的編碼、目標數量、組合或停止設定。 | 指出不支援，整場不啟動，不自行換算法或轉型；正式查詢介面仍待議。 |
| R12 兩種重複分開 | 摘要同題候選 seed 重複，或補找時產生本題已試 seed。 | 前者啟動前報錯、不自動去重；後者跳過、不求解、不扣 repeat。一般 task 判重不取消，不把各算法使用同一 seed 誤報成重複候選。 |
| R13 舊 10 個僅 8 個通過 | 本次目標 100 個合格 seed，舊 10 個中僅 8 個重新通過。 | 尚需補收集 92 個合格 seed；歷史曾收錄的另 2 個不能直接計入，不保證補找只需 92 次。 |
| R14 收集條件改變 | 舊 seed 在原條件下合格，但本次條件不同。 | 仍先試舊 seed，重新求解並按本次條件判斷；不直接沿用標記，不自動比對、阻擋或改回歷史條件。 |
| R15 選題不同 | 有效摘要有 P／Q，本次 YAML 選 P／R。 | P 先試用對應舊 seed，R 從頭收集，Q 不執行；不能把「R 缺舊 seed」當成整份摘要無效。 |
| R16 不可行結果 | 本次求解得到正常不可行結果，或歷史結果曾不可行。 | 不冒充算法執行錯誤，也不以歷史狀態代替本次判斷；收錄與否依本次收集條件。 |

### 舊 seed 順序與額度：12 項獨立規則模型

2026-10-27 的問答後，已用對話工具內的獨立 JavaScript 同步規則模型核對以下 12 項，結果全部通過。模型輸入為舊 seed 有序清單、人工給定的新候選序列、目標收錄數、repeat，以及人工指定的通過判斷；保存受試順序、舊／新嘗試清單、收錄清單、重複跳過數與是否不足。這些數字是檢查條件，不是新增的系統預設值。

| 模型案例 | 輸入／條件 | 核對結果 |
| --- | --- | --- |
| B01 摘要順序 | 舊 seed 為 `[7, 3, 9]`，目標 3，repeat 為 10，全部合格。 | 通過；判斷順序為 7、3、9，沒有改按數值排序。 |
| B02 舊 seed 超額 | 舊 seed 為 1 至 100，目標 10，repeat 為 100，全部合格。 | 通過；只試用前 10 個，不再追加其他舊 seed 或新 seed。 |
| B03 舊／新額度分開 | 舊 seed 為 1 至 20，新候選為 1000 至 1099，目標 1、repeat 為 100，全部不合格。 | 通過；舊 20 次加上新 100 次，共 120 個 seed 輪次，仍未收滿；不是 120 個算法 task。 |
| B04 摘要重複先報錯 | 舊候選 `[7, 3, 7, 9]`，目標 1、repeat 為 1，原本每個 seed 都可通過判斷。 | 通過；在任何判斷／求解替身執行前報來源重複，不以達標或自動去重繞過。 |
| B05 補找重複不計次 | 舊 seed 7 已試且不合格，新候選 `[7, 12, 12, 13]`，目標 1、repeat 為 2，全部不合格。 | 通過；跳過舊 7 與重複新 12，真正嘗試新 12、13，兩次跳過不占額度。 |
| B06 固定起點 | 舊 7 不合格，新候選從 `[7, 12, 13]` 開頭開始，目標 1、repeat 為 2，只有 12 合格。 | 通過；從頭遇 7 就跳過，再試 12 達標，不使用歷史搜尋位置。 |
| B07 舊 10 個全通過 | 舊 seed 為 1 至 10，新候選為 1000 至 1099，目標 100、repeat 為 100，全部合格。 | 通過；再嘗試並收錄新 90 個就達標，沒有用完新 100 次。 |
| B08 舊 10 個僅 8 個通過 | 舊 seed 為 1 至 10，僅 1 至 8 合格；新候選為 1000 至 1099、全部合格，目標 100、repeat 為 100。 | 通過；再嘗試並收錄新 92 個，最終共 100 個合格；舊試用仍為 10 次。 |
| B09 新 seed 不合格也計次 | 無舊 seed，目標 2，repeat 為 3，新候選 `[20, 21, 22, 23]` 中只有 21 合格。 | 通過；真正嘗試前 3 個新 seed，僅收錄 1 個，不再追加第 4 個。 |
| B10 不足後繼續其他題 | 第一題舊 1 至 8 合格、新 `[20, 21]` 不合格，目標 10、repeat 為 2；第二題舊 `[7, 3]` 皆合格，目標 2、repeat 為 2。 | 通過；第一題記為 8／10 不足，第二題仍執行並收滿；不模擬算法錯誤。 |
| B11 跨題相同 seed | 兩題各自候選清單皆為 `[7]`，各需 1 個、repeat 為 1 且合格。 | 通過；兩題都可試用 seed 7，不以跨題共用集合誤報候選重複。 |
| B12 固定輸入重複推演 | 舊候選 `[7, 3, 9]`、新候選 `[7, 12, 13, 14]`、目標 4、repeat 為 3；判斷為「seed 不等於 3，且（seed 為 7 或已收錄清單含 7）」。 | 通過；兩次完整模型輸出一致，皆收錄 `[7, 9, 12, 13]`；不宣稱正式系統可重現性已驗證。 |

模型的界線：

- 這是單一同步、有限序列的規則模型，不是正式算法、讀取器、摘要解析器、seed 產生器或真實比較條件。B01 只核對給定的判斷順序，沒有測試並行完成通知與緩衝。
- 新候選序列是人工給定，且足夠完成各案例；沒有驗證現有 seed 公式、合法值域、空間耗盡或正式產生器的終止性。序列不足時的模型保護不構成正式耗盡政策。
- 沒有執行 C++、真實求解、IPC、並行排程、檔案保存或在途工作清理；B10 只證明規則可表達「不足後繼續下一題」，不代表正式錯誤恢復或報告格式已驗收。
- B12 只比較模型的語意輸出，不承諾 AI 訓練、時間停止模式或正式跨語言計算必然重現；既有固定輸入／seed／迭代數與紀錄不得干擾搜尋的原則仍保留。
