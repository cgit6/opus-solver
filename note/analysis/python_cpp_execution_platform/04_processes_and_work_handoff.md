## 二 程序圖與責任

以下是傳統問題的邏輯程序圖，不指定通訊套件、執行緒精確數量或函式簽章。AI 執行環境歸單元 8，不能由此推定加入 AI 後整場仍只有兩個程序。

```text
Python 管理程序
  │ 啟動；一次交付本場安排；監督程序
  ▼
C++ 執行程序（每場新建）
  ├─ 算法設定、題庫讀取／預檢／準備
  ├─ 本場唯讀題庫
  ├─ 一般工作展開／獨立收集功能 → 待辦工作
  └─ 可重用的工作執行緒
       每條工作鏈：留存實際輸入與 task 關聯 → 求解與最終驗證
                   → 同步保存 → 完成相關使用與清理 → 接下一個 task
  │ 整場終結摘要、紀錄位置及可取得錯誤資訊
  ▼
同一個 Python 管理程序：記錄、監督、彙整
```

圖內的題庫、收集、輸出是責任劃分，不是另開的程序或背景寫入服務。`worker_count` 仍是最多同時求解的 task 數，不是 Python 程序數；保存／清理中的工作鏈不得提前接另一題，具體執行緒配置與資源限制接線由單元 10 核對。

Python 不讀算法 YAML、不解析傳統題目數值，不重新計算解，也不決定哪個 task 應先執行。C++ 不擴大 Python 提供的選取範圍；各 task 的 RNG、編碼、分數、最佳結果、緩存與歷史保持獨立。

## 三 正常交接順序

1. Python 讀取並檢查本場實驗安排，啟動新的 C++ 執行程序，一次交付選題／來源、算法／原組號、seeds 或收集需求、併發與整場停止額度等安排。種群大小及其他算法專用實際值由 C++ 讀算法 YAML，不放回 Python 的責任中。
2. C++ 讀取指定算法 YAML 及題庫，完成必要檢查與所有選中題目的準備。一般 run 的展開及重複工作檢查也是搜尋前預檢的一部分；不能把「預檢後安排工作」解讀成先求解、後發現重複。任一必要檢查或準備失敗，不先跑合法子集。
3. C++ 內部確認準備完成，表示本場開始搜尋的準備條件已滿足，不表示任何 task 已開始或已有結果；不要求向 Python 發準備完成通知。
4. C++ 依安排選取工作，在算法開始前將實際題目／算法輸入與 task 關聯寫入本場可追查的保存紀錄，不能只留在 C++ 程序記憶體中。關聯須足以識別本場實際工作及連到已保存內容，不只是一個 PID、來源路徑或組號；不得事後重讀可能改變的來源代替。這一步由 C++ 自行完成，不向 Python 逐 task 登記或等待確認；正式格式歸單元 10、保存失敗歸單元 7，不新增硬體保存保證。
5. C++ 開始該 task 並執行算法，addAct 只在 C++ 記錄狀態；不要求向 Python 回報每個 task 的開始事實。取消通知不取消內部追查紀錄，也不使 Python 能憑已交安排推定即時在途清單。
6. 求解任務完成搜尋及最終驗證；正常不可行或正常無候選仍可完成並如實標示，不編造編碼或分數，不以空結果掩蓋算法例外。這是內部求解階段完成，不等於結果已保存，也不逐 task 通知 Python。
7. run 由 C++ 同步保存結果 JSON／完整歷史 JSONL，兩者完整才算該 task 保存成功。exp 不輸出 task 詳細檔，保留相關結果供收集判斷並更新 seed 名單；名單寫檔失敗停整場並留因。管理端不接全量資料重寫，也不要求逐 task 保存回報。exp 事前追查與 RAM 歷史仍待回答。
8. 同一工作鏈完成本機保存、相關資料使用與 task 私有資料清理後，才能接下一個 task；不等待 Python 確認，其他工作鏈不必一起等待。仍被輸出、收集判斷或其他使用者引用的資料不得提前釋放，本場題庫不逐題回收。
9. 全部工作及所需保存、清理完成，且所有題庫使用者已釋放引用後，C++ 統一釋放本場題庫，向 Python 交付整場終結摘要、紀錄位置及可取得錯誤資訊，正常關閉本場程序。Python 記錄實際收到的整場交付並彙整；關閉交錯與正式訊息由單元 7、10 落實，不能只見正常退出碼就推定缺少的交付已完成。

「一次交付本場安排」不是要求 exp 預先列出所有未來候選 task。C++ 收集功能仍可依本次結果追加工作，每一個新增 task 同樣必須先留存實際輸入與關聯，再開始算法。每場新識別與跨檔關聯、完整保存及候選摘要更新要求見單元 6，不在此另選檔名或序列化細節。

## 四 內部階段與對外交付

| 階段／資料 | 處理與交付責任 | 不可據此推定什麼 |
| --- | --- | --- |
| 準備完成 | C++ 內部確認必要預檢及題目準備通過，不要求對外通知。 | task 已開始、已有分數或輸出。 |
| 開始前實際輸入與 task 關聯 | C++ 在算法前留存，供結果對應及人工追查；不逐 task 登記、不等待 Python ACK。 | Python 已即時取得任務清單，或留存本身代表算法已開始。 |
| task 開始、搜尋及最終驗證完成 | C++ 內部區分實際進度，保存可行／不可行或正常無候選等已知結果；不要求逐 task 通知。 | 求解完成就是寫檔成功，或 Python 已知道當下在跑哪些 task。 |
| 本機保存結果 | C++ 留存所需輸出及保存事實；完整結果和歷史皆保存才算完整，失敗原因依可取得資訊留下。 | 本機已保存等於 Python 已收到整場交付，或缺回報就一定未寫檔。 |
| 整場終結摘要、位置與可取得錯誤 | Python 記錄收到的本場狀態、摘要與位置，並據此彙整；不接收完整歷史。 | 退出碼、路徑存在或通道關閉可以代替缺少的完整回報。 |

以上區分內部事實與對外交付，不要求每個表格階段成為訊息，也不新增正式事件名稱或 schema。C++ 仍須保留足以追查的工作及實際輸入關聯；Python 不因不讀完整歷史而重新計算數學結果。正式整場訊息、收訖與程序退出交錯須由單元 7、10 在實作前落實及驗證。

## 五 收集的逐輪與並行邊界

一輪是「同一題、同一個 seed、全部所選算法與參數組」的工作及收集判斷，不是算法內的一代更新。對題目 P，seed 1 這輪的結果尚未完成判斷時，不安排 P 的 seed 2；但 P 的本輪多個 task，以及題目 Q 的輪次，可以在併發上限內並行。

- 同題前一輪判斷完，仍未收滿且還有可嘗試候選，才可安排下一輪；判斷完不代表無條件追加。
- 收滿就不再安排後續 seed，不要求試完全部舊 seed；此方案不預先派出同題後續輪次，因此不再把「收滿時如何處理已提前派出的後續 seed」列為未決選項。其他題目的工作仍可在途；異常時如何停止與清理歸單元 7。
- 舊 seed 依摘要順序；repeat 只計新 seed 嘗試，不按輪內 task 數扣額度；碰撞跳過與摘要重複拒絕的規則不變。未收滿但新額度用完仍正常保留結果並繼續其他題目。
- 不按算法完成先後改變候選 seed 收錄順序；輪內出錯時不能拿部分結果假裝完成本輪判斷，依既有錯誤政策及單元 7 的處置辦理。
- 每輪結果齊備並完成判斷後，C++ 更新正式收錄 seed 名單，不等 Python；exp 不輸出收錄／未收錄 task 詳細檔。名單保存失敗已定停整場並留因，跨題更新不丟清單，詳見單元 6 及移機交接。

這是選定的派工界線，不保證執行緒永遠滿載，也不以同步規則模型宣稱吞吐量或公平性已驗證。

## 六 管理中斷、退出與未確認交付

在本場完成交付之前，確認 Python 管理程序退出或通訊已中斷時，C++ 執行環境必須停止開始新 task，並停止整個求解程序，不等在途 task 自然求解完成。不能假設已退出的 Python 還能發出停止命令；如何偵測中斷並確實結束程序，是單元 7、10 必須落實及驗證的工作。

這項規則接受未保存的結果及歷史可能遺失，不承諾致命退出或強制終止時每個清理函式都會執行、每個錯誤原因都能送達，或程序能立即安全停止。正常流程的保存與釋放順序不能反過來要求斷線後等在途 task 算完。

- 長時間沒有訊息不等於通訊中斷；本版不因此增加無訊息超時或單 task 強制超時。
- 管理／通訊中斷與算法錯誤分開記錄，不能把被連帶中止的 task 說成算法失敗或成功。
- 已完成正常整場交付後的通道關閉不是異常；C++ 已成功保存的結果不因程序後來退出而撤銷。本機保存完成與 Python 已收到整場交付是不同事實。
- 沒有完整整場回報時，保留本場安排、C++ 已留存輸入／已有文件及最後已知事實，交付保持未確認；不掃檔或依退出碼補登成功、不自動重跑。Python 本身已退出時，也不能承諾它仍能補寫最後一筆紀錄。
- 多 task 共用 C++ 程序，原生崩潰未必能定位肇因 task。取消逐 task 通知後，Python 不保證掌握當下的在途或未完成清單；已有 C++ 工作關聯可供追查，但不能據此猜測誰造成崩潰或補登未收到的完成事實。

## 七 歷史模型與現行文件核對

### 歷史證據：原單元 4 的 9 項同步規則模型

以下保留原單元 4 規劃問答中通過的 9 項檢查及限制，均為記憶體內同步狀態模型。**本區塊使用修訂前的 task 登記、確認及階段通知政策，僅供追溯，不是目前有效交接規則，也不代表單元 6 新方案已驗收。** 模型按給定事件序列更新登記、確認、開始、求解、保存與退出等布林事實，並檢查同題未判斷輪次及管理中斷的預期狀態；本次沒有重跑模型、算法、IPC 或大型測試。

| 編號 | 條件 | 已通過的規則判斷 |
| --- | --- | --- |
| M04-01 | 已登記、已收到登記確認，但沒有開始事件。 | 仍不是已開始。 |
| M04-02 | 已登記但沒有確認，嘗試開始。 | 不得進入已開始狀態。 |
| M04-03 | 登記、確認、開始後，求解完成，沒有保存回報。 | 不得標成已保存。 |
| M04-04 | 已收到保存成功事實，之後收到退出。 | 已確認保存不撤銷。 |
| M04-05 | 求解完成，但沒有完整保存回報便退出。 | 交付保持未確認，不補登成功。 |
| M04-06 | P 題有尚未判斷的 seed 輪次。 | 不得追加 P 的下一輪。 |
| M04-07 | P 題仍有尚未判斷的輪次，Q 沒有。 | 不因 P 等待而禁止 Q 的輪次並行。 |
| M04-08 | P 的前輪已完成判斷。 | 解除前輪未判斷造成的阻擋；仍須遵守收集數量與額度等條件。 |
| M04-09 | 管理中斷時，一題已保存、一題在途、一題待開始。 | 要求停止整個程序、不再開始新工作、不等在途自然完成；保留已保存者，其餘未完成，不改稱算法錯誤。 |

限制：模型沒有驗證真實程序間訊息、並行競態、登記持久保存、檔案保存、Python 退出偵測或程序終止。M04-04 的輸入明確是保存事件在退出前，不代表所有通知／退出交錯均已處理；M04-09 只核對要求的停止狀態，不證明 C++ 已能偵測或執行停止。既有研究原始數據不改寫，也不拿舊隔離政策的實驗當本方案驗收。
