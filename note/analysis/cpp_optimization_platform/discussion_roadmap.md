# C++ 平台的待議事項與討論順序

整理日期：2026-10-25。接續入口見 [設計索引](README.md)。

已收斂的主方向是 C++ 平台加 Python AI 問題模組；接下來討論如何落實，不再以「Python 一定負責派工與保存」作為起點。功能需求見 [需求基線](requirements_baseline.md)，目前候選見 [架構方向](architecture_direction.md)。

## 討論原則

- 先從需求推導程序、資料與責任，不直接將現有 Python 類別逐一翻成 C++。
- 保留已確認的研究與正確性要求；需要改變既有功能或風險取捨時，明確說明並由使用者確認。
- 每次只收斂一個單元，確認後更新文件。需要原型時，以小型、可對照的實驗驗證具體疑問，不把合成測試當完整平台驗收。
- 分清楚「方向已確認」「具體機制待定」與「正式實作已驗證」，不因選定 C++ 就宣稱效能、可重現性或故障記錄已成立。

## 新方案的討論順序

本表是新平台的討論安排，不延續舊方案的單元編號或待議編號。

| 單元 | 要確認的內容 | 收斂條件 |
| --- | --- | --- |
| 1 執行程序與故障範圍 | C++ 管理與求解是否分程序；task 如何並行；算法錯誤、未知退出與不可信環境如何處置。 | 能畫出程序圖，說清楚崩潰後誰還活著、掌握哪些 task 輸入與事實、何時停止或可繼續派工。 |
| 2 題目準備與有型別題庫 | 各題型如何解析、預處理、唯讀共用與回收；算法如何引用；求解程序結束後的資料生命週期。 | 以 MKP 與路線題走完準備、同題多 seed 共用、使用期間有效、誤寫保護及程序退出的案例。 |
| 3 設定與任務支援 | C++ 啟動、實驗設定位置與完整內容、題庫與參數選取、支援查詢、預檢及精確配對重跑。 | 用一般批次、精確配對、未知欄位、重複與不支援設定，驗證展開範圍與拒絕原因符合既有規則。 |
| 4 算法結構與狀態紀錄 | 主／內／外結構、解狀態與完整編碼、evaluate、增量更新、RNG、工作空間、addAct 及外部狀態控制。 | 以單一解與種群算法確認狀態持有；測小操作同步、紀錄不改變 RNG、舊快照不被覆寫。 |
| 5 結果交付與保存 | 完整結果與歷史如何交給 C++ 輸出責任、所有權、同步保存、錯誤原因留存與交付確認。 | 核對正常／不可行、保存失敗、清理失敗、通知未達與退出交錯，保留實際輸入及已保存結果，不誤判成功。 |
| 6 統計與報告 | 可行率、執行錯誤、連帶停止、保存失敗與交付未確認如何分列；目標值樣本、排名與跨題彙整。 | 用人工小樣本確認分母、排除規則及全不可行情境，避免不同問題單位直接混算。 |
| 7 建置與分步遷移 | C++ 標準、依賴、建置與測試入口、既有算法與題庫的遷移範圍、對照驗證及正式入口切換。 | 形成每步可驗收、有停止點的修改計畫；先完成代表性垂直流程，再逐批擴大，不一次重寫所有算法。 |

## AI 情境隨相關單元一起檢查

AI 不是等傳統平台全部實作完才檢查的附加功能，也不是現在就要做完整訓練平台。先以特徵篩選作代表，確認共同設計不把 Python 評估能力排除：

- 單元 1 確認 AI 評估在同程序還是獨立程序，多個 task 的並行與錯誤如何納入整場政策。
- 單元 2 確認 C++ 持有什麼問題資料，Python 持有什麼資料、切分與可變模型狀態，不把模型訓練狀態誤當唯讀題庫。
- 單元 3 至 4 確認設定、編碼規則、評估呼叫、回傳值與隨機上下文。不能因新增 AI 就偷偷派生搜尋 seed，或讓 addAct 額外訓練一次。
- 單元 5 至 6 確認模型產物、訓練錯誤、最終驗證與評分統計；搜尋用評分資料與最終測試資料的使用規則須明確。
- 單元 7 確認 Python 環境與部署方式，以及傳統執行是否需要安裝 Python；模型／框架選型不在本輪自動定案。

第一個 AI 交接例子須說清楚「設定提供什麼 → Python 準備什麼 → C++ 收到什麼 → 每次評估傳回什麼」，不另建一套外層實驗管理。

## 下一個單元的具體問題

目前停在單元 1 開始之前，需要依序確認：

1. C++ 實驗管理與載入算法的求解工作，是否在不同程序？若求解程序崩潰，誰能保留實際輸入、已知階段與受影響 task？
2. 題庫與多個 task 是否放在同一求解程序並以執行緒共用？若採多程序，資料如何共用或重新準備，成本及故障範圍是什麼？
3. 非預期算法錯誤如何停止整場，不讓尚未完成的 task 冒充成功，也不提前釋放仍在使用的資料？未知退出不能直接猜測為算法根因。
4. 保存錯誤後若清理成功且環境可信，如何繼續新 task？若必須關閉整個求解程序，何時關閉、如何記錄連帶中止，以及是否重建題庫接續未開始工作？已接受可能連帶中止，不表示已定恢復機制。
5. 從特徵篩選情境確認 Python 評估可以接入上述邊界；不先定 pybind11、每個 task 啟動腳本、subinterpreter 或服務化。

本單元的產物應是可解釋故障與資料持有關係的程序圖及事件案例，而不是先寫正式排程器。

## 本輪不執行的工作

不改動正式程式、算法、註冊、設定或建置環境；不刪除 Python／Numba 對照版本；不搬移舊方案與研究原始證據。不新增自動歷史恢復、checkpoint、背景輸出、Redis 或硬體備援。

後續若採用舊原型，須先檢查它和新平台的管理語言、程序安排、計時、所有權與錯誤政策是否相同；相似名稱或舊測試通過，不代表新組合已通過。
