# C++ 平台與 Python AI 問題模組的架構方向

整理日期：2026-10-25。狀態：以 C++ 建立平台的主方向已確認；程序邊界、執行緒安排、AI 呼叫及正式資料結構仍待討論。

## 以 C++ 建立完整平台

C++ 負責實驗管理、設定讀取與檢查、題目準備與持有、任務調度、算法執行、驗證、狀態紀錄、結果保存及統計。Python 不再是實驗管理主體，保留為 AI 問題的資料準備、訓練與評分環境。

這不是替現有 Python worker 加上 C++ 函數，也不是把所有 Python 檔案逐一翻譯。先依 [需求基線](requirements_baseline.md)設計責任與資料生命週期，再決定新程式的模組與遷移範圍。

## 傳統與 AI 實驗共用外層管理

```text
C++ 實驗管理讀設定並展開 task
  → 檢查配對、輸入與執行設定
  → 準備本次選中的問題
  → 全部準備成功後，安排 task 求解
      → C++ 算法產生候選解
          → 傳統問題：C++ 問題模組評估
          → AI 問題：Python AI 問題模組評估
      → C++ 算法根據評估結果繼續搜尋
      → 達停止條件，求解任務依問題規則最終驗證
  → 每個 task 完整交付結果與歷史，由輸出責任同步保存
  → 整理任務狀態、統計與報告
```

這是責任流程，不是程序圖。AI 模組內的一次訓練不另開另一場外層實驗；問題特有的資料準備與最終模型要求仍由對應問題模組決定。

## 有型別題庫與算法私有狀態

目前優先細化的候選，是 C++ 將解析及預處理完成的題目，保存在有明確型別的題目物件中。同一求解程序內的多個 task，直接引用同一份唯讀題目，不在每個 task 啟動時重新解碼共享記憶體。

例如，兩個 task 使用同一題 MKP：

```text
C++ 題庫中的題目 P
  價值、重量、容量及共用衍生資料
       ↑ 唯讀引用             ↑ 唯讀引用
  task A 的算法內部結構   task B 的算法內部結構
  私有 RNG、編碼、分數     私有 RNG、編碼、分數
  工作緩存、最佳解、歷史   工作緩存、最佳解、歷史
```

「把題目存進算法內部結構」在此指保存有效的唯讀引用，不是每題 task 深度複製整個題目。MKP、路線問題與連續問題可以有各自的題目型別，不要求建立一個包含所有題型欄位的巨大 struct。

題目解析時仍須檢查數值型別、必要欄位與尺寸。有型別介面減少讀取端解讀格式的分歧，不代表編譯器能自動證明題庫數值或數學模型正確。唯讀存取仍須有保護與驗證，不能僅以 `const` 宣稱已防止所有誤寫。

這個候選以同程序共用為前提；若最後選擇多個求解程序，一般 C++ 物件不會自動跨程序共用，必須重新評估資料持有方式。此處尚未選定多執行緒或多程序。

## 題庫與任務的生命週期

- task 結束不等於求解程序結束。健康程序可保留題庫供後續 task 使用，但前題的可變搜尋狀態不得混入下一題。
- 一般程序私有記憶體隨程序結束由作業系統回收；原生崩潰時不保證執行解構函數，但不代表程序私有 RAM 永久殘留。
- 具名共享記憶體、檔案與其他外部資源有不同生命週期；上項不宣稱它們都會隨程序自動刪除。
- 若題庫只由求解程序持有，程序退出後題庫也消失。之後建立新求解程序，需要重新準備題庫；是否建立、由誰準備及如何繼續未開始 task，仍須確認。這不等於自動重跑失敗或連帶中止的 task。
- 結果或輸出器仍引用題目及歷史時，持有者不得提前釋放或覆寫它們。

「保留題目資料直到使用者結束」的生命週期要求保留；「一定由 Python 主程序持有共享記憶體」不再是新方向的前提。

## Python AI 問題模組的範圍

以特徵篩選為例，Python AI 問題模組依設定載入資料、確定特徵順序與資料切分、準備模型建立方式，再提供候選解的評估能力。C++ 算法提出特徵選取編碼，AI 模組訓練並評分，將目標值與可行性交回算法。

整場選題、算法、seed、停止與任務紀錄由 C++ 平台管理；Python AI 模組不再另外管理一份相同的 task 清單。模型訓練本身的步驟、資料處理與評分規則，仍是 AI 問題責任。

AI 接線尚需確認：

- 同程序嵌入 Python，或使用獨立 Python 評估程序；不預設每個候選解啟動一次腳本。
- 編碼規則、評估輸入、回傳結果、例外與模型產物的正式交接方式。
- 多 task 的模型、評估 RNG 與可變訓練狀態如何隔離；唯讀資料能否共用須依實作驗證。
- Python 執行限制、訓練內部並行、CPU／GPU 資源及資料切分對可重現性的影響。
- 傳統實驗是否能在未安裝 Python 的環境獨立執行；不能把「不呼叫 AI」直接等同「編譯及執行時完全不依賴 Python」。

[原特徵篩選逐欄交接](../system_redesign/10_ai_feature_selection_boundary.md)可作需求例子，但其中 Python 實驗主程序的流程不再沿用。

## 已改變的舊架構前提

| 舊方案前提 | 新方案方向 |
| --- | --- |
| Python 是實驗系統主體，C++ 是被呼叫的求解模組。 | C++ 建立完整模擬平台，Python 作為 AI 問題模組。 |
| 以 Python worker 與 C++ 的 binding 或 IPC 為呼叫主軸。 | 先決定 C++ 管理與求解的程序邊界；跨語言接線聚焦 AI 評估。 |
| 衍生資料先回 Python，再搬到 Python 管理的共享記憶體。 | 優先細化 C++ 準備並持有有型別題庫；不強制繞回 Python 或沿用 SHM 搬運。 |
| 每題完整結果及歷史必須交回 Python 輸出器。 | 求解與輸出仍分工，但都在 C++ 平台責任內設計，不要求完整歷史先轉成 Python 物件。 |
| 固定沿用 Python 啟動與單 task 重跑命令。 | 保留 YAML、指定配對重跑與輸入留存能力，另定 C++ 啟動與建置入口。 |

這些是新的設計起點，不代表正式 API、程序配置、輸出格式或建置工具已決定。尚未決定的細節不回頭以舊 Python 方案自動補齊。

## 舊實驗能支持的範圍

[既有候選實驗](../system_redesign/19_architecture_candidate_experiments.md)及其原始證據保留作參考。當時 threads 案是 Python 執行緒池呼叫釋放 GIL 的 C++ 核心，不是新 C++ 平台的調度器；不能據此宣稱完整 C++ 管理、真實算法並行或 AI 接線已通過驗收。

統一使用 C++ 的理由是資料、執行與維護方向的選擇，不是已量測出整個平台必然比 Python 管理方案快。
