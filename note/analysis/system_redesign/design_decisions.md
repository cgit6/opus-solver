| D27 | 一個 task 出錯，不取消、不重跑其他正常 task。 | 其他任務的 RNG 與可變狀態須隔離；固定 seed、固定迭代下仍須核對其過程與結果。現有程序池尚不符合這項要求。 | [14](14_python_cpp_invocation_and_failure_replay.md)、[16](16_process_lifecycle_experiment.md) |
| D28 | 本版不加入卡住後自動超時中止。 | 沒有明確錯誤或程序終止、但一直未完成的工作，暫由研究者人工處理；不等於更動算法本身的正常停止條件。 | [14](14_python_cpp_invocation_and_failure_replay.md) |

| D30 | 首版支援 Linux／WSL。 | 不以原生 Windows 作本版驗收平台；C++ 核心仍避免不必要的平台耦合。 | [14](14_python_cpp_invocation_and_failure_replay.md)、[17](17_invocation_comparison_experiment.md) |
| D31 | 本版不內建單一 task 的停止命令，由研究者透過外部工具人工處理。 | 系統依觀察到的程序終止等事實記錄與恢復；不因此加入自動超時，亦不承諾辨識所有卡住情況。 | [14](14_python_cpp_invocation_and_failure_replay.md) |

| D33 | 失敗 task 能透過 Python 命令單獨從頭重跑即可。 | 不要求 Python-free 的獨立原生重跑入口，不恢復算法中間狀態；正式命令及保存格式尚未實作。 | [14](14_python_cpp_invocation_and_failure_replay.md) |

| D40 | Python 保存錯誤須記實際原因與 task 對應；本題資源清理成功後重用 worker，清理失敗或狀態不可信才替換。 | task 仍是保存失敗，不因 worker 可重用而變成功；保留可取得的清理錯誤，不自動重求解或重試保存。 | [15](15_task_failures_and_result_storage.md) |

確認依據主要為使用者明確接受責任分工、接受前兩項議題，以及本輪「全部保留」「C++ 全部求解完一次返回」「確定」。D08–D16 亦包含先前對主／內／外結構、增量扣分、addAct 與固定迭代重現性的明確要求。

D23 依據使用者進一步明確說明：希望異常時記下 task 任務內容，日後重現這個 task 找問題；並要求將這項重要需求及呼叫討論獨立成文。

D24–D26 依據後續明確確認：軟體 task 異常不終止整場、必要時替換 worker、寫檔原因須留存，且不處理磁碟滿／磁碟故障等資源層情境。這取代較早的 fail-fast 要求，不表示恢復能力已實作。

D27–D29 依據本單元逐題確認：其他正常 task 照常執行、不做卡住後自動超時中止，並在乾淨控制實驗後選擇「重用健康的求解程序」。舊核心的記憶體增長不作選型證據；控制實驗及限制見 [16](16_process_lifecycle_experiment.md)，不是正式求解模組已完成的證明。

D30–D35 依據後續逐題確認及使用者接受的本單元整理計畫：先定 Linux／WSL、人工停止與完整呼叫／Python 重跑範圍，再選 worker 同步保存；看過兩案三種配置的控制實驗後，確認同程序擴充模組。數據、來源與限制見 [17](17_invocation_comparison_experiment.md)。原型使用 pybind11 3.1.0，不代表正式依賴版本或公開 API 已定案；這次文件整理沒有重跑實驗。

D36–D40 依據使用者後續確認及本單元實作計畫：主程序指定並追蹤工作、接收兩種階段通知，對缺少最終回報採保留現況、不自動核對；分開處理非預期 C++ 錯誤與 Python 保存錯誤。已用 [15 的十個事件案例](15_task_failures_and_result_storage.md#十個事件案例) 核對規則一致性，沒有完成正式 IPC、退出訊息處理或故障恢復驗收。

## 三、延後處理

- 大型完整歷史的記憶體上限、分批交付、背景寫入、Redis：先遵守 D17–D20，不並行實作替代路線。
- 算法內部 checkpoint、RNG 中途恢復：不以 addAct 取代；任務級重跑與算法中途續算是不同功能。
- 整場實驗重啟後辨識／跳過已完成 task：待核心重構通過驗證後設計與實作，不宣稱現有一般入口已具備。D23–D25 的異常輸入、寫檔原因及不中斷派工須納入核心驗收，必要的單次交付判定不能一併延後。
- AI 的正式模型訓練整合、GPU／遠端執行、訓練失敗與快取策略：先保留交接情境，不擴充第一版。
- Legacy bug 修正、算法流程變更與新效能優化：不和系統重構混成同一批修改。
- 舊設定遷移、大規模目錄搬移與舊算法淘汰：另設遷移關卡。

| 曾討論方案 | 本次有效決定 |
| --- | --- |
| 主系統重新跑 problem.validate，確保每份回傳的數學正確性。 | 最終數學驗證是求解任務責任；實驗側不重算。 |
| 為避免責任不清，先強制加入 problem／solver／validator 版本和 digest。 | 先定責任，不把這些欄位當成必要解法或人為正確性的保證。 |
| addAct 為避免快取不同步，先重新 evaluate。 | 記錄不評估；完整小操作自己同步編碼與分數。 |
| 提交時自動標記「未評估」，或只准固定幾個時點提交。 | 不採此限制；由算法作者選擇完整操作後的提交點。 |
| 普通大量實驗只保留摘要，少數 seed 才保留全部歷史。 | 所有任務每次提交全量保留。 |
| C++ 直接寫檔、同步分批交 Python、背景寫入或 Redis。 | 目前先全部保留於單任務記憶體，完成後一次交 Python。 |
| 第一階段完全忽略 AI，設計做完再想是否相容。 | AI 用來檢查共同邊界，但傳統問題先細化實作。 |
| 用保存所有 addAct 紀錄，宣稱可恢復算法中間狀態。 | 不成立；觀測歷史不保證含有完整隱藏工作狀態與 RNG。 |
| 推薦 pybind11，就視為已選定 A 且出錯只影響單 task。 | D35 的最終選擇依保存路徑、對照測試與使用者確認，不是工具名稱本身提供故障隔離；正式監督仍須避免整池失效並保留實際輸入。 |
| 因 A 符合現有 worker 流程，就優先 A；或 B 有編解碼就全算額外成本。 | 優先理由已撤回；A 的語言交接不等於程序交接已完成，兩者需按相同條件拆分工作。 |
| 單一 task 執行失敗就停止整場實驗。 | D24 取代此策略：記錄異常，必要時恢復執行能力，繼續下一個新 task。 |
| 為確保故障原因留存，引入另一顆磁碟、另一台機器或獨立錯誤保存服務。 | D26 排除硬體／資源層故障專用處理，不增加這些機制。 |
| 用未按新生命週期整理的舊 C++ 核心記憶體增長，判定程序重用本身不適合。 | 此理由已撤回；乾淨控制實驗只提供有限證據，使用者據此選擇 D29，不宣稱正式算法已驗證。 |
| 其他工作可以因某個 task 出錯而一起取消、從頭重跑。 | D27 要求其他正常 task 照常執行；不能以沿用現有 broken pool 處理方式為由放寬。 |
| worker 沒有最終回報時，主程序自動掃檔或讀完成記錄，替它補登成功。 | D38 不採此功能；保留現有文件與已知事實，記交付未確認，不自動核對或重跑。 |
