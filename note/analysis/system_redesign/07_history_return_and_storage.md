# 07｜完整歷史、一次回傳與保存責任

狀態：完整歷史一次交付、健康程序重用、同程序 C++ 擴充模組與 Python worker 同步保存已確認；主程序只收摘要與檔案位置。D36–D40 已確認派工、通知與異常處置；正式表示、通訊／監督及所有權待議，大型記憶體風險延後解決。對應 D17–D20、D24–D29、D34–D40、P07、P10。

## 最後定案

每個求解任務由 C++ 完整執行與最終驗證後，一次返回：

1. 該任務的最終結果。
2. 該任務全部實際 addAct 提交紀錄。

Python 實驗模組接收並負責文件保存、統計及報告。C++ 不直接寫紀錄文件，不連 Redis，不啟動背景寫入，也不採同步分批交付。

D34 已選 worker 在 C++ 返回後呼叫共用 Python 輸出器，同步保存完本題再接下一題；主程序只收摘要與檔案位置，不接收整場完整歷史。這仍屬實驗側保存，不等於 C++ 算法寫文件。D35 已選 worker 內同程序擴充模組，詳見 [14](14_python_cpp_invocation_and_failure_replay.md)、[15](15_task_failures_and_result_storage.md)。

## 全部保留的範圍

使用者明確選擇：例如 100 題、每題 10 個 seed，這 1,000 次求解都保留每次實際提交的編碼、對應真實適應值與外部快照。

- 不只保存某些 seed。
- 不改成隔若干代抽樣。
- 不只保留最佳解或統計摘要。
- 不以環形緩存覆蓋舊紀錄。
- 若某次外部參數原本就是 nil，保留這個事實，不要求補造外部資料。

全量保留是「每次實際呼叫 addAct 的內容均保留」，不代表系統自動在每條語句後插入提交。提交頻率與文字標籤仍由算法作者定義。

## 任務生命週期

```text
Python 分派一個任務
  → C++ 初始化題目、算法、工作空間與紀錄容器
  → 算法搜尋，addAct 將快照累積於本任務記憶體
  → 到達停止條件，求解任務完成最終驗證
  → 一次交回最終結果及全部提交紀錄
  → 該 Python worker 同步保存本題
  → 主程序只接收摘要與檔案位置，後續彙整分析
```

每個任務完成時各自回傳，不是整場 1,000 個任務都算完才第一次交付。D37–D38 已確認階段及最終回報的判定政策；正式保存格式與通訊實作仍須細化，不預設新增完成標記或自動文件核對。不能宣稱目前一般 CLI 已做到任務級即時保存。

已選的 Python worker 在保存、交接與本題狀態清理後，繼續接下一個新 task；不是讓整場歷史永久堆在該程序內。但「一次返回」不等於立刻釋放所有 C++ 結果記憶體：Python 輸出器仍使用的資料，必須有有效持有者，不能提前釋放或被下一題覆寫。具體移交／持有方式與是否複製仍待 [08](08_cpp_invocation_and_shared_memory.md) 決定；上述路徑不等於正式回收及通知協議。

清理不能刪掉尚未交付的歷史，也不能把完整歷史改成逐代寫檔。程序重用的控制實驗見 [16](16_process_lifecycle_experiment.md)，不代表正式保存流程的記憶體風險已解決。

## 已選 worker 保存，主程序保存為未採用的比較

| 路徑 | C++ 返回之後的 Python 工作 | 主程序接收的內容 |
| --- | --- | --- |
| 主程序保存（本版不採用） | worker 將完整結果與歷史交給主程序，由主程序呼叫輸出器。 | 完整結果與歷史。 |
| worker 保存（D34） | worker 同步呼叫同一套 Python 輸出器，完成該 task 的文件後回報。 | 統計所需摘要及檔案位置，不必再傳完整歷史。 |

這是同機器、輸出位置可見的比較；已選隔離 Python worker 同步保存，共用的是輸出程式，不是讓所有 worker 同時修改同一個檔案。獨立 task 檔案、摘要與完成確認的具體格式仍待定。

worker 保存避免把完整歷史再交給主程序；使用者接受該 worker 保存時暫不接新題，以免前題未存又產生下一份大結果。其他 worker 可繼續工作，但多 worker 也可能競爭磁碟。主程序保存也能透過限制待存結果數來控制積壓，不能宣稱它必定 OOM。D34 不解決單任務全歷史 RAM，亦不保證零複製或整體更快；後續 D35 的呼叫選型與控制證據見 [17](17_invocation_comparison_experiment.md)。

## 軟體異常時的保存責任

求解完成、Python 保存成功及主程序確認交付，是不同事實。Python 寫檔失敗須保留原因及 task 對應；沒收到完成通知時不能反推求解失敗，也不能只因看到檔名就宣稱完整交付。

單一 task 的軟體異常不終止整場：留下必要紀錄，必要時恢復／替換 worker，再處理下一個新 task。原生求解異常只要求保留實際輸入，不要求 Python 診斷 C++ 根因；正常不可行結果不是此處的執行錯誤。

其他正常 task 不因這次異常被取消或重跑；本版不加自動超時或內建單 task 停止。D36–D40 已確認主程序先保留輸入及 worker／task 對應再指派，等待訊息與退出事件，接收已接收任務及 C++ 正常返回兩種通知。退出時先處理已交付通知；仍缺少完整最終回報才記交付未確認，保留現有文件，不自動核對、補登或重跑。完整成功／錯誤回報不因 worker 後續退出被改寫；task 結果與 worker 健康分開。非預期 C++ 錯誤替換該 worker，Python 保存錯誤清理成功且狀態可信才重用，否則替換。正式通訊／監督與狀態保存格式仍待細化。

磁碟滿、磁碟故障等硬體／資源層異常已明確排除，不為此增加獨立磁碟、另一台機器或錯誤保存服務。此範圍不變更完整歷史的既有 RAM 風險；完整規則見 [15](15_task_failures_and_result_storage.md)。

## 此版明確接受的限制

單個任務的全部歷史至少必須在求解期間保留於記憶體。基本估算為：

```text
歷史大小 ≈ 提交次數 × 每次保存的編碼、適應值、外部狀態大小
```

種群越大、編碼越長、提交越頻繁，成長越快。緩存重用能減少重新配置工作記憶體，但不能讓已保留的所有不同歷史免費存在。

多 worker 同時求解、C++ 轉 Python 與保存前暫存仍可能增加尖峰。D34 不再讓完整歷史預設從 worker 傳給主程序，但這不保證 bounded memory、零複製或超大題不會 OOM。

這是使用者選擇延後處理的已知風險，不可暗中改成截斷、抽樣、只記錄摘要或增加背景服務。

若任務在回傳前崩潰，記憶體內尚未交付的歷史可能一起失去。此版也不承諾每次 addAct 都已落盤或斷電不丟；完整求解歷史的中途 durable 保存不在目前設計內。

但失敗 task 的實際起始輸入必須能保留，讓研究者事後從頭單獨重跑。這是實驗側任務邊界的輸入保存與異常追蹤，不是 addAct 分批輸出，也不依賴崩潰程序正常返回。需求與未定機制見 [14](14_python_cpp_invocation_and_failure_replay.md)。

## 討論過但本版不採用的方案

| 方案 | 原本想解決什麼 | 本次不採用的原因／狀態 |
| --- | --- | --- |
| C++ 自行分批寫檔 | 限制歷史累積。 | 增加求解側文件責任與 I/O，未獲接受。 |
| C++ 同步分批交 Python | 保持保存責任在實驗側。 | 會暫停求解等待保存；本輪改選全部完成一次交付。 |
| 背景 writer | 嘗試讓 I/O 與搜尋重疊。 | 使用者認為增加複雜度，先擱置。 |
| Redis | 嘗試減少寫入等待。 | 未實測；不能當成解決完整歷史 RAM 問題的保證。 |
| 大量實驗只留摘要 | 降低紀錄量。 | 與使用者全部任務完整保留的決定不符。 |

以上不是另一組待實作選項，除非使用者重新開啟此議題。

## Problab 提供的參考及限制

Problab 大量模擬每局更新統計，下一局重用工作緩存；詳細開發入口則累積有限局數，算完一次返回。它支持「計算與輸出分開」的責任概念。

它也將內部結果轉為對外 DTO，再由 HTTP 入口輸出 JSON。DTO 是交付資料，不是 Web 專用；本系統可借用此分層，外層改成文本輸出，但不代表已決定 DTO 型別或保存位置。

但它不是替數千次大型求解保留全部歷史而仍固定記憶體的證據，也不能把一次優化迭代當一局清空舊 addAct 來假裝滿足本需求。來源見 [12](12_prior_work_and_references.md)。

## 後續實作必須驗證

- 每筆紀錄順序與內容完整，nil 不被誤轉成其他狀態。
- 返回後資料仍有效，不因釋放 C++ 工作空間而懸空。
- 健康程序接下一題後，前題已交付但仍被使用的歷史不會被清理或覆寫；不讓不應保留的本題資料跨任務累積。
- Python 保存失敗要清楚回報，不能把回傳成功當成磁碟保存成功。
- 軟體保存異常的原因及 task 關聯可查，依清理成功／失敗決定重用或替換，後續新 task 可執行；通知與退出交錯按 [十個事件案例](15_task_failures_and_result_storage.md#十個事件案例) 驗證，不把已交付結果改成失敗。
- 每個任務各自回傳，不隱含要求整場批次一起留在 C++。
- 保存格式及壓縮策略尚未決定；不要把「一次回傳」誤解成只能建一個巨大 JSON 字串。
