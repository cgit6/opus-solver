# 09｜實驗安排、算法支援與統計

狀態：第四項展開與統計尚未整體定案；單 task 異常後繼續、健康程序重用、同程序呼叫與 worker 同步保存已確認，D36–D40 補足派工、通知及異常政策，正式恢復機制與統計仍待設計。對應 D24–D40、P04–P05、P08、P10。

## 使用者的實驗需求

- 題目可從命令列或實驗設定指定。
- 實驗模組根據選題、算法、參數組與重複次數展開任務。
- 希望同一次實驗能跑不同問題類型下的多題／題庫，前提是算法支援。
- 原始結果保留，以便不同研究報告採不同統計方式。
- 高併發與問題資料共享要一起考慮，而不是只增加 worker。

多問題需求不表示任意算法都能解任意問題，也不表示不同目標值可直接混成一個平均。

## 一般入口和 seed 收集入口不能混淆

現況：

- [cli/run/main.py](../../../cli/run/main.py) 是一般模擬入口。
- `cli/exp` 用於根據特定條件收集 seed，會使用共同的下層模擬能力。
- `cli/exp/exp_cfg.yaml` 不是一般實驗安排的通用設定範本。

重構應沿著共同執行流程整理責任，但保留兩種入口不同的使用意圖。不要只因名稱叫 exp，就拿它定義所有未來實驗格式。

## 目前支援檢查怎麼做

[cli/run/support.py](../../../cli/run/support.py) 的 `validate_execute_args()` 讀取題目 metadata，檢查 solver YAML 的：

- problem_types。
- encodings。
- directions。

例如 [cdels.yaml](../../../configs/solvers/cdels.yaml) 宣告 SCVRP、route／transfer 編碼與最小化。拿它跑 MKP，這條一般 CLI 路徑會在預檢拒絕。算法 adapter 本身也有型別限制。

目前一般入口還要求一個 solver，且不能混用 problem_type／encoding／direction；不能把未來跨問題實驗需求寫成現在已支援。

## 未來支援清單要解決的問題

| 問題 | 需要明確化的責任 |
| --- | --- |
| 算法支援哪些題型／編碼／方向？ | 宣告應由算法實作及其維護者負責，不能僅靠研究者手填任意配對。 |
| Python 如何知道 C++ 有哪些算法？ | 由呼叫契約暴露或取得支援資訊；具體查詢方式待定。 |
| YAML 和 C++ 宣告不一致怎麼辦？ | 不能各自維護互相矛盾的有效清單；權威及同步方式待定。 |
| 某些組合不支援？ | 應在求解前明確回報；整場拒絕或只建立合法組合，待確認。 |

這裡的相容性預檢是任務安排責任，不是實驗側重算 objective 或驗證最終解。

## 多問題任務展開的例子

一場研究包含 MKP 題與 SCVRP 題，選用的算法只支援 SCVRP，就不能直接對全部題目做笛卡兒積，然後把 MKP 失敗當正常樣本。

若某個算法支援兩種問題，也需要為每個 task 保留具體問題類型、題庫、題目、參數組與 seed。如何在一份實驗設定描述這些分組尚未定案。

不同參數組應使用可對照的題目及重複設定；seed assignment 要明確保存。為了 legacy 重現，可以把所需 seed 當作本次實驗的明確設定值傳入，不必修改算法內流程。

## 不可行解的統計：問題已記錄，規則未定

求解結果不可行仍正常完成，原始解、真實目標值與 feasible=false 必須保留。

但不能默默把不可行目標值和可行解放在一起比較「誰更好」。待討論項目包括：

- 可行率／成功率的定義與分母。
- objective 平均值是否只計可行結果，是否另列全樣本描述。
- 全部 seed 都不可行時，報表怎麼表示，不偽造零分。
- 求解失敗、保存失敗、交付未確認及正常不可行結果如何分列與設定分母；不能偽造零分或默默隱去異常 task。
- 跨題目、不同單位／方向如何分組，是否需要正規化或排名。

以上是待設計項，不是已選定某種統計公式。

## 保存與中斷

完整回傳是單任務粒度；D34 已選 worker 在求解完成後同步保存，主程序只收摘要與檔案位置。派工與通知判定按 D36–D40，正式檔案格式、通訊／監督機制及整場續跑仍待設計。

異常 task 的實際輸入保存與事後單獨重跑則已確認為需求，不能等正常結果返回才處理，也不和整場自動續跑一起延後；呼叫方式與故障邊界見 [14](14_python_cpp_invocation_and_failure_replay.md)。

目前 [cli/run/support.py](../../../cli/run/support.py) 通常等整批 Simulator 結束才呼叫 writer；[tools/show.py](../../../tools/show.py) 還會重設 variant 輸出目錄。未來若改任務級保存，必須一起核對，避免完成後又刪掉先前紀錄。

SCVRP 專用資料驗證命令已有自己的 plan／逐任務保存機制，不代表一般實驗入口已支援相同續跑。這兩條能力不可混稱。

最新要求是單一 task 的系統軟體流程異常須記錄，必要時替換 worker，再處理下一個新 task，不因此停止整場，也不默認重試原 task。這取代較早的 fail-fast 要求。正常不可行解仍正常保存，不觸發 worker 故障恢復。

D36–D40 補足記錄政策：只記管理端實際收到的事實；worker 退出時先處理已交付通知，缺少完整最終回報才記交付未確認，不自動核對文件、補登或重跑。task 結果與 worker 健康分開，完整成功／錯誤回報不因後續退出被改寫；替換 worker 也不增加一次 task 重跑。這些語意已定，報表欄位、分組與分母仍待本章收斂。

其他正常 task 不取消、不重跑；健康求解程序繼續接新工作，每題狀態獨立，本版不加入卡住後自動超時中止。若實際出現連帶中斷，須如實記錄隔離不符合需求，不能把整池取消後重派當成已接受策略；本章也不據此先決定統計分母。

求解異常須保留實際輸入，不要求 Python 查出 C++ 根因；寫檔異常須保留原因。磁碟滿／磁碟故障等硬體／資源層情境不納入此版專用處理。如何恢復派工、處理在途與未確認 task，詳見 [15](15_task_failures_and_result_storage.md)。

D34 的 worker 同步保存與 D35 的同程序 C++ 擴充模組是已確認目標，不是既有一般入口已改好。正式報表需確認摘要足以彙整，詳查可按需讀取已存文件，不因此在主程序保留整場完整歷史。整場中斷後跳過完成 task 仍是後續功能。

## 本章驗收方向

多問題任務展開應先只測小型組合：合法配對、非法配對、同名但不同題庫、明確 seed、參數組、不可行及執行失敗。先驗證任務清單與分組，再談大量執行效能。
