# 求解架構比較：可進入決策討論的實驗結論

日期：2026-10-24。這是暫存研究證據，不是正式架構決策或系統驗收。

## 先看結論

1. **沒有證據顯示必須把整個實驗系統改寫成 C++。**Python 可以繼續安排實驗；有型別的題目資料、計算及高量輸出，可以放在獨立求解程序內的 C++ 元件。元件的責任與實作語言是兩回事。
2. **同一個求解程序內，多個執行緒共用 C++ 題目物件，原型已能保持每題狀態獨立。**但現有 CDELS C++ 原碼不能原封不動丟進去：RNG、NP、世代編號等共用狀態必須先整理為每題獨有，再做真實算法驗證。
3. **完整歷史轉成 Python 物件再格式化，確實可能成為瓶頸。**將相同 JSON 的轉換與保存交給獨立 C++ 輸出器，在歷史量大的合成測試中有改善。這不需要讓算法本身負責寫檔，也不等於 C++ 在所有情境都比較快。
4. **共用題目資料能省掉題庫副本，但不能解決每題自己的種群與完整歷史記憶體。**後兩者仍會隨題目、提交量和同時執行題數成長，這次沒有把它宣稱為已解決。
5. **真正尚需決策的是故障處置邊界。**同程序內若某題寫檔後清理失敗，立刻關閉整個求解程序會連帶失去其他尚未交付的題；等其他題跑完再關閉則沒有等待時間上限。這不是效能測試能替你決定的取捨。

以上是根據本次原型提出的設計推論，沒有修改正式決議、求解器或派工程式。

## 效能數字代表什麼

這裡是**合成工作負載，不是真實 CDELS**。兩案使用相同 C++ 計算核心；多執行緒案由 Python thread pool 呼叫會釋放 GIL 的原生計算，**尚未實作正式 C++ 排程器**。因此不能據此宣稱 C++ 派工比 Python 派工快或慢。

以下是 2,000 點、4 個執行單元、每批 8 個 task、每組 5 次的中位數，括號為最小至最大值。計時涵蓋派工、計算、轉換、同步寫檔及小型回報；**不含啟動、題目預處理、編譯及事後內容核對**。

| 形式／輸出器 | 計算較多的測試，毫秒／批 | 歷史較多的測試，毫秒／批 |
| --- | ---: | ---: |
| 多程序／Python | 64.94（59.26–87.54） | 54.23（41.82–124.96） |
| 多程序／C++ | 65.34（60.99–90.41） | 48.00（35.41–68.93） |
| 多執行緒／Python | 58.54（49.80–140.80） | 106.59（82.21–147.64） |
| 多執行緒／C++ | 68.50（52.67–73.82） | 41.61（31.75–88.21） |

**解讀：**計算較多時沒有穩定、全面的贏家；寫檔波動也很大。歷史較多時，多執行緒搭配 Python 物件轉換／JSON 格式化的成本值得避免，C++ 輸出器是可用方向。不能把單一比值推廣成正式系統的固定加速倍數。

### 記憶體另做測量，不混入上述計時

2,000 × 2,000 的 uint64 題目表本身為 32,000,000 bytes。4 個執行緒共用一份；本次一般多程序對照各持有一份，總共四份，**沒有使用共享記憶體**。

以下是另一輪各 4 個 task 的測量，包含管理程序及其求解程序的 PSS 加總：

| 形式／輸出器 | 題目備妥後 MiB | 抽樣最高 MiB |
| --- | ---: | ---: |
| 多程序／Python | 183.79 | 202.66 |
| 多程序／C++ | 183.81 | 190.91 |
| 多執行緒／Python | 64.49 | 81.47 |
| 多執行緒／C++ | 61.08 | 68.23 |

**限制：**每配置只量一輪、約 10–16 次抽樣；這是抽樣最高值，不是真正峰值。測量時有刻意同時保留 4 題的原生結果，再開始保存；原型也沒載入完整專案或模擬 CDELS 種群。不能據此估算正式大型題目的記憶體上限。

## 實際找到的問題與可用處理方式

### 1. 只為每題重新設 seed，不代表 RNG 已獨立

原 C++ `compat_rng.cpp` 使用程序共用的 state。單獨執行時，seed 1 前兩次應為 `41、18467`；交錯 seed 2 的初始化與一次抽取後，seed 1 下一次變成 `29216`。

這是**錯誤地共用原碼時的反例，不是目前獨立程序 oracle 的 bug**。結論是多執行緒整合前必須把 RNG 及其他可變狀態放進每題自己的物件，不能只補一個 `srand(seed)`。

### 2. 「worker 清理失敗就換掉」在不同架構下，影響範圍不同

清理失敗原型確實讓原生結果仍被持有，並拒絕再派工給不可信的執行單元。不是只設一個假的失敗旗標；但也沒有模擬任意原生堆積損壞。

| 測試策略 | 多程序案 | 同程序多執行緒案 |
| --- | --- | --- |
| 立即替換該物理程序 | 其他程序的題目可完成 | 2／4 單元時，另有 1／3 題尚未交付結果會失去 |
| 不再派新題，等其他正常題完成才關閉 | 本次其他題皆完成 | 本次其他題皆完成，但可能等很久 |

第二種只在**能界定為清理／輸出端問題、其餘狀態已知健康**的情況下有討論價值；不能推論未知 C++ 記憶體損壞也能安全繼續。未替正式政策做選擇。

### 3. 只靠通知傳回寫檔錯誤原因，仍可能遺失原因

原型實際產生 JSON 序列化 TypeError，接著讓錯誤通知只傳一半就退出。若錯誤只存在通知中，管理程序只能知道「C++ 已返回、最終交付未確認」，拿不到 TypeError 的原因。

另一個受測提案是：**worker 先用獨立錯誤輸出格式保存原因，再發送通知**。同樣斷掉通知時，人工仍可在預先知道的位置取得錯誤原因與 traceback。這不是另買硬碟、Redis 或背景寫入；也沒有讓主程序自動掃描文件、補登成功或重跑。

這個提案需要你接受才成為正式政策；它不承諾硬體故障、任意時點突然被殺或錯誤紀錄本身寫入失敗也一定留存。

### 4. 多程序並非一定要重建四份有型別題目物件

另外的 Linux 可行性測試，先在乾淨單執行緒程序準備題目，再 fork 4 個子程序。題目表對應記憶體的 PSS 加總為 31,250 KiB，約等於一份表；更換一個正常退役程序後，也不必重算題目。

**這是另一條可能路線，不是直接切換現有系統的建議。**它尚未解決正式管理隔離、第三方函式庫與 AI 執行環境的 fork 安全；現有已載入 NumPy／ML 的 Python 程序不應直接照搬。

## 現在適合討論的決策

1. 是否以「Python 管實驗；獨立求解程序內共用 C++ 題庫與計算；獨立輸出器可由 C++ 實作」作為優先細化候選，而不是立即選定正式架構？
2. 如何區分可隔離的輸出／清理失敗與不可信原生狀態，以及各自的程序退役規則？
3. 是否接受 worker 先保存寫檔錯誤原因、再通知管理程序的提案？

沒有足夠證據直接定案：正式 CDELS 多執行緒安全、C++ 排程器收益、AI 共用此架構、真實大型題目的記憶體上限，以及所有 IPC 異常情況。
