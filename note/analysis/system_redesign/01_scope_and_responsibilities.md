# 01｜範圍與責任

狀態：責任分工與 D34 的 worker 同步保存已確認；D35 曾選定的完整拓撲現在作重新評估基線，狀態及比較維度見 [14](14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度)。D79–D80 將算法錯誤改為停止整場，正式實作與遷移尚未開始。本章對應 D01–D05、D21–D40、D79–D80。

## 要解決什麼

目前多數實驗流程與問題定義使用 Python。目標是保留 Python 管理實驗，讓傳統優化問題的搜尋與數學計算在 C++ 內完成，避免每次廉價、高頻評估都跨語言。

這不是要新增一個獨立「後端服務」。以下是業務責任，不要求做成四個服務或四個可部署系統。

## 已確認的責任分工

| 責任 | 處理的事 | 不處理的事 |
| --- | --- | --- |
| 實驗管理 | 選題與算法、展開任務、分派、接收、保存、統計、異常紀錄及依錯誤種類停止／恢復。 | 不定義 objective／constraints，不重新驗證解的數學正確性，不要求診斷 C++ 根因。 |
| 問題 | 解的意義、目標函數、限制式、可行性與問題相關的驗證規則。 | 不替算法選 mutation、修復順序、接受機率或搜尋罰分。 |
| 算法 | 初始化候選解、搜尋策略、運算子、增量更新、最佳解保存、停止迴圈與提交時點。 | 不任意改問題規則，不把搜尋罰分混成真實目標，不做文件 I/O。 |
| 求解任務 | 組裝該題與算法、初始化執行環境、執行一次完整搜尋、最終驗證、回傳結果與歷史。 | 不安排整場實驗，不承擔實驗／輸出側的文件責任。 |
| 狀態紀錄子模組 | 接收 addAct，保存當時的不可變快照，於任務完成交付歷史。 | 不重新評估、不修復編碼、不改 RNG／算法狀態。 |

問題、算法、任務入口及狀態紀錄屬於求解側的內部責任，保存由實驗／輸出側負責。D18–D19、D34 當時已選完整返回 Python 再由 Python 輸出器保存，仍是有效舊基線；候選若改 C++ 獨立輸出或完整返回邊界，須依 [07](07_history_return_and_storage.md#已確認交付需求與保存基線) 列差異待確認，不能由語言反推算法承擔文件責任。

非預期算法錯誤（可捕捉錯誤或原生致命崩潰）依 D79–D80 停止整場，包含其他算法正在求解的 task；不再啟動新 task，保留已保存結果，不自動重跑。正常不可行不算算法錯誤；Python 保存錯誤仍依 D40。求解異常保留實際輸入；Python 寫檔異常保留原因。D34 的同步 task 保存、保存完才接下一題及主管只收摘要／路徑保留；輸出器已有 [19 的候選對照](19_architecture_candidate_experiments.md)，尚未選新方案，不把文件責任移入算法。C++ 輸出器候選出錯也須按業務階段分類，D25／D40 映射差異依 07 待確認，不僅憑語言觸發算法錯誤停止。

正常運行重用健康程序，每 task 的 RNG／可變狀態與歷史獨立；同一邏輯工作鏈同步保存、交接及清理後，環境可信且整場未停止才接下一題，不要求同 host 其他鏈一起等保存。task、工作鏈、host 與 thread 依 [14 名詞表](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍) 分清，結果仍被使用時不得清理。D35 是比較基線；首版 Linux／WSL、不做自動超時或內建單 task 人工停止，新架構／安全收尾／未知退出仍待定。

D36–D40 要求管理端先保留輸入與 task 的實際執行關聯再指派、等待事件。實體 host 退出先按各題已交付通知／完整回報判定，已交付不撤銷，缺回報者記未確認、不自動核對／補登／重跑。算法錯誤依 D79–D80 停整場；D40 保存原因，清理成功且可信才重用，否則不再使用不可信環境。舊基線可替換程序，新拓撲的實體範圍與時機依 [14](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍) 待確認，不默選退休策略、不因普通保存錯誤一律全場停；未知退出不猜根因。正式通訊／監督與格式仍待定，案例見 [15](15_task_failures_and_result_storage.md)。

本版不處理磁碟滿、磁碟故障等硬體／資源層異常，也不增加獨立錯誤保存媒介。範圍與未定機制見 [15](15_task_failures_and_result_storage.md)。

D25 的保存原因要求不是最佳努力：範圍內 Python 軟體保存失敗，原因與 task 必須事後可查；產生／通知／持久保存分開，不能只靠通知宣稱完成。正式留存時序與二次軟體失敗／退出的保障依 [15](15_task_failures_and_result_storage.md#保存錯誤原因的留存界線) 待確認，不默選 artifact、不宣稱全軟體情境已保證，也不把軟體問題擴列為 D26 排除。

## 人與程式各負責什麼

- **實驗人員**維護題庫數值、選題、參數組合與研究設定，確認它們符合研究意圖。這些角色可以是同一個人，不要求額外組織分工。
- **問題開發者**維護目標函數、限制式、解碼及問題測試。
- **算法開發者**維護搜尋邏輯、狀態同步、正確的增量計算及提交時點。
- **系統開發者**維護任務安排、資料交接、保存與報告，不替研究者判斷研究設定的科學合理性。

例如，研究者把 MKP 容量填成錯誤的 100，而實際想研究的是 80。程式可以檢查容量是否為合法數值，但無法只靠一個版本號或 digest 知道人原本想填 80。輸入檢查和人為設定正確性不能混為一談。

## 傳統問題的任務流程

以下沿用 D35 比較基線及舊 Python 保存基線描述既定責任；架構依 [14](14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度) 重新評估，輸出器語言、D18 返回與所有權差異依 [07](07_history_return_and_storage.md#已確認交付需求與保存基線) 核對待確認。

```text
Python 安排任務、準備輸入
  → C++ 任務入口準備問題與算法
  → 算法搜尋，使用 C++ 問題計算／增量規則
  → 求解任務依問題規則最終驗證
  → 回傳最終結果及全部已提交歷史
  → 該 Python worker 同步保存本題
  → 主程序接收摘要與檔案位置，彙整分析
```

「Python 準備輸入」不代表 Python 必須建立一套新的數學 evaluator。讀取 YAML、載入數值與執行限制式判定是不同工作；細節見 [02](02_problem_data_and_configuration.md)。

## 為什麼仍需要最終驗證

算法可能用容量緩存與增量差值加速搜尋。任務結束時依問題規則核對最終編碼、分數與可行性，能發現緩存或增量更新錯誤。

這項驗證在求解任務內完成。開發階段也可以用舊 Python 或獨立 oracle 比對 C++；但那是研發測試，不是要求每次正式實驗都跨回 Python 重算。

對隨機／AI 評估，最終驗證不能任意重新抽樣一次，再把分數不同當成錯誤；其驗證上下文見 [05](05_evaluation_and_incremental_updates.md)。

## 現況與目標的差異

目前 [machine/core.py](../../../machine/core.py) 的 `run_task()` 仍依序執行：

```text
problem_bank.get → solver.solve → problem.validate → SimulatorRunRow
```

目標不是刪除驗證，而是把最後的數學驗證移入求解任務責任。此處尚未修改。
