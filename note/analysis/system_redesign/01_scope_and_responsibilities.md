# 01｜範圍與責任

狀態：責任分工、同程序 C++ 擴充模組與 Python worker 同步保存已確認；正式實作與遷移尚未開始。本章對應 D01–D05、D21–D40。

## 要解決什麼

目前多數實驗流程與問題定義使用 Python。目標是保留 Python 管理實驗，讓傳統優化問題的搜尋與數學計算在 C++ 內完成，避免每次廉價、高頻評估都跨語言。

這不是要新增一個獨立「後端服務」。以下是業務責任，不要求做成四個服務或四個可部署系統。

## 已確認的責任分工

| 責任 | 處理的事 | 不處理的事 |
| --- | --- | --- |
| 實驗管理 | 選題與算法、展開任務、分派、接收、保存、統計、異常紀錄與恢復派工。 | 不定義 objective／constraints，不重新驗證解的數學正確性，不要求診斷 C++ 根因。 |
| 問題 | 解的意義、目標函數、限制式、可行性與問題相關的驗證規則。 | 不替算法選 mutation、修復順序、接受機率或搜尋罰分。 |
| 算法 | 初始化候選解、搜尋策略、運算子、增量更新、最佳解保存、停止迴圈與提交時點。 | 不任意改問題規則，不把搜尋罰分混成真實目標。 |
| 求解任務 | 組裝該題與算法、初始化執行環境、執行一次完整搜尋、最終驗證、回傳結果與歷史。 | 不安排整場實驗，不直接寫結果文件。 |
| 狀態紀錄子模組 | 接收 addAct，保存當時的不可變快照，於任務完成交付歷史。 | 不重新評估、不修復編碼、不改 RNG／算法狀態。 |

問題、算法、任務入口及狀態紀錄屬於求解側的內部責任。最終資料返回 Python 後才由實驗側保存。

單一 task 軟體異常後，實驗側留下所需紀錄，必要時恢復／替換 worker，再處理下一個新 task，不停止整場。求解異常保留實際輸入；Python 寫檔異常保留原因。D34 已選 worker 同步呼叫 Python 輸出器，保存完才接下一題，主程序只收摘要與位置；這仍屬實驗側保存，不把文件責任移入 C++ 算法。

健康求解程序可繼續接新 task，但每題 RNG、算法狀態與歷史獨立；結果仍被使用時不得提前清理。D35 已選主程序外的 Python worker 載入同程序 C++ 擴充模組；原生崩潰只替換該 worker，其他正常 task 不取消、不重跑。本版不做自動超時或內建單 task 停止，首版 Linux／WSL；這些決議不改責任分工，正式追蹤與恢復機制仍待細化，見 [14](14_python_cpp_invocation_and_failure_replay.md)、[17](17_invocation_comparison_experiment.md)。

D36–D40 補足管理端政策：主程序先保留輸入及 worker／task 對應再指派，等待訊息與退出事件；worker 通知已接收及 C++ 正常返回。退出又缺少完整最終回報時，保留現況、記交付未確認，不自動核對文件、補登或重跑；完整回報不因後續退出被改寫。非預期 C++ 錯誤替換該 worker，Python 保存錯誤則依清理結果決定重用或替換。詳見 [15](15_task_failures_and_result_storage.md)，正式通訊／監督與資料格式尚未定案。

本版不處理磁碟滿、磁碟故障等硬體／資源層異常，也不增加獨立錯誤保存媒介。範圍與未定機制見 [15](15_task_failures_and_result_storage.md)。

## 人與程式各負責什麼

- **實驗人員**維護題庫數值、選題、參數組合與研究設定，確認它們符合研究意圖。這些角色可以是同一個人，不要求額外組織分工。
- **問題開發者**維護目標函數、限制式、解碼及問題測試。
- **算法開發者**維護搜尋邏輯、狀態同步、正確的增量計算及提交時點。
- **系統開發者**維護任務安排、資料交接、保存與報告，不替研究者判斷研究設定的科學合理性。

例如，研究者把 MKP 容量填成錯誤的 100，而實際想研究的是 80。程式可以檢查容量是否為合法數值，但無法只靠一個版本號或 digest 知道人原本想填 80。輸入檢查和人為設定正確性不能混為一談。

## 傳統問題的任務流程

```text
Python 安排任務、準備輸入
  → C++ 任務入口準備問題與算法
  → 算法搜尋，使用 C++ 問題計算／增量規則
  → 求解任務依問題規則最終驗證
  → 回傳最終結果及全部已提交歷史
  → 該 Python worker 同步保存本題
  → 主程序接收摘要與檔案位置，彙整分析
```

「Python 準備輸入」不代表 Python 必須建立一套新的數學 evaluator。讀取 YAML、載入數值與執行限制式判定是不同工作；細節見 [02](02_problem_data_and_configuration.md)。

## 為什麼仍需要最終驗證

算法可能用容量緩存與增量差值加速搜尋。任務結束時依問題規則核對最終編碼、分數與可行性，能發現緩存或增量更新錯誤。

這項驗證在求解任務內完成。開發階段也可以用舊 Python 或獨立 oracle 比對 C++；但那是研發測試，不是要求每次正式實驗都跨回 Python 重算。

對隨機／AI 評估，最終驗證不能任意重新抽樣一次，再把分數不同當成錯誤；其驗證上下文見 [05](05_evaluation_and_incremental_updates.md)。

## 現況與目標的差異

目前 [machine/core.py](../../../machine/core.py) 的 `run_task()` 仍依序執行：

```text
problem_bank.get → solver.solve → problem.validate → SimulatorRunRow
```

目標不是刪除驗證，而是把最後的數學驗證移入求解任務責任。此處尚未修改。

## 尚未定案與不在此章決定的事

- 已選同程序擴充模組的正式函式、binding／建置方式與 worker 監督機制。
- 問題數據用一般陣列、共享記憶體或其他表示。
- 欄位型別、檔案位置、C++ 的模板／介面設計。
- 是否需要遠端服務、第三方 scheduler 或框架 adapter。

先確定責任，不用技術元件名稱反推責任。
