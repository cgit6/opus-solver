## 已有的邊界

- Python 安排一個完整求解任務。
- 傳統問題的搜尋、objective、constraints 與最終驗證在 C++ 內完成。
- 每 task 完整計算與驗證後一次交付結果及全部紀錄；D18 返回 Python 與 Python 輸出器仍是有效舊保存基線，候選語言與交付邊界差異依 [07](07_history_return_and_storage.md#已確認交付需求與保存基線) 列出待確認。
- 不在傳統問題每次 objective 呼叫時返回 Python。

以上是正式求解的責任與頻率。D74–D77 另確認求解前的題目準備及共享原則，不能把題目預處理與單 task 求解混成同一階段；正式 binding、資料描述與所有權實作仍須細化。

## 呼叫與資料交接的關係

D35 當時選定的完整拓撲現在是重新評估基線；D29 的健康程序重用、每題狀態獨立及 D34 保存路徑保留。D79–D80 改算法錯誤停止整場、保留已保存結果且不自動重跑。其後已有 [19 的候選證據](19_architecture_candidate_experiments.md)，仍依 [14 的比較維度](14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度) 確認組合與差異，不自動改架構或 D74–D77 機制；Bank、prefork、唯讀頁面探針不等於正式交接驗收。

D32 已確認 Python 正式 API 只需一個完整求解能力，不要求逐步算法介面；函數名稱、參數及結果 schema 尚未定。呼叫決策見 [14](14_python_cpp_invocation_and_failure_replay.md)，控制對照見 [17](17_invocation_comparison_experiment.md)。

這不排除 D74 的獨立題目預處理階段。預處理先準備本次要共用的固定資料；之後每個正式 task 仍完整求解、最終驗證並一次返回結果及全部歷史，不把「一次返回」誤解成整場只准呼叫一次 C++，也不要求公開逐步算法物件。

不能把語言交接與程序交接混為一談。D35 比較基線中的擴充模組在 Python worker 內返回，再由該 worker 同步保存；D34 的主程序只收摘要與位置要求保留，不因呼叫拓撲重新評估就把整份歷史交主程序。這沒有取消跨 worker 共用唯讀題目數值的需求，也不能因 SHM／buffer 名稱就推定全程無複製。輸出器語言及 D18 返回／所有權差異見 [07](07_history_return_and_storage.md#已確認交付需求與保存基線)，通知政策及待細化機制見 [15](15_task_failures_and_result_storage.md)。

D36–D40 的派工與異常政策不等於完整所有權實作：主程序派工前保留實際輸入，不等於每題複製整份數據。D77 曾定主程序持有及 task 解除連接的安排，現為原交接基線；新候選的差異依 [上表](#不變需求與原交接基線) 核對，不把「仍在使用就不可回收」重新列為未定。固定數值的正式表示、實際配置／映射／回收及轉換成本仍屬第 2 單元（原 Q3.2）的交接細化。D48–D49 已在 [18](18_experiment_configuration_and_task_expansion.md) 確認重跑讀指定參數與題庫檔案，由人維護一致，不自動引用歷史副本；實際輸入紀錄仍須保留內容供追查／人工重建，不能只留可變來源路徑或暫時 SHM 名稱。紀錄表示與交接契約仍待細化，不把記錄與自動恢復混為一談；接續議題統一見 [13](13_open_questions.md)。

## 已確認的題目準備與求解流程

這是 D74–D77 原交接基線的流程，不是所有新拓撲必須照搬的程序／映射圖；候選偏離其機制時須先列差異待確認，不自動取消既有安排。

```text
Python 實驗側讀取設定，確定本次選中的題目
  → 一個隔離 worker 逐題呼叫 C++ 問題預處理
  → 衍生資料先算好，再搬入共享記憶體一次
  → 全部題目準備成功後，才分派正式求解 task
  → 各求解 worker 按 task 連接共享唯讀資料，執行 C++ 完整求解
  → Python worker 保存結果後，結束本 task 的資料存取
  → 整場工作結束且所有使用者釋放後，由主程序清理共享資料
```

D74 的「全部題目」是本次選中的不同題目，不是整個專案的全題庫。同一題搭配多個 seed、算法或參數組，不因此各自重新準備相同固定資料；預處理 worker 也不限定之後由誰求解該題。任一題準備失敗，記錄原因，不先啟動已備妥題目的正式求解。這是求解前啟動關卡，與正式求解後依 D79–D80 處理算法錯誤停止分開；不把預處理失敗、不可行解或 Python 保存錯誤混為算法執行錯誤。

原交接基線依 D75 統一採「C++ 先算好，再搬一次」，當時沒有採已知大小就直接填共享區的另一條路徑；搬完才釋放不再需要的暫存。沿用此基線時仍須如實保留暫存與共享區可能同時存在的記憶體成本；新候選若改準備或搬移機制，依上表列差異待確認。不能因此宣稱零複製、記憶體無尖峰或正式求解可以再按 task 重算固定資料。

以上不指定函式名稱、資料描述格式、由哪段 Python 程式實際配置共享區，或每個小量純量都必須放共享記憶體。交付內容與正式接口仍須細化。

## 決策來源與本次恢復範圍

D74–D77 來自 2026-10-22 的原始逐項問答，2026-10-23 已查閱原始記錄並恢復至文件。當時選項與確認順序如下：

1. 「一個 worker 逐題準備」：一個隔離 worker 準備本次題目，全部成功才開始並行求解；任一題失敗就不進入正式求解。
2. 「全部先算好再搬一次」：衍生資料由 C++ 先準備，再搬入共享區，隨後釋放不再需要的暫存。
3. 「採用唯讀存取保護」：求解端採唯讀映射方向，搭配 C++ 唯讀介面，不只靠程式約定。
4. 「每個 task 連接後釋放」：使用及保存結果完畢後解除本 task 的連接，主程序仍保留原資料到整場結束。

當時已確認共享資料由實驗側持有、不依附準備它的 worker。這四項是補回漏記決議，不是本輪重新選型或新做的性能／故障實驗。正式機制仍待驗證；本次不重匯出整份對話，也不把更早的 [對話逐字稿](../../codex_conversation_transcript_2026-10-14.md) 當成已包含這些 10 月 22 日問答。

## 資料區分：已定原則與待定表示

| 資料 | 已定原則／待定表示 | 原因 |
| --- | --- | --- |
| 同題重複任務的 values／weights／座標／距離等固定大陣列 | 共用唯讀題目資料；原交接基線依 D75 先算後搬，新候選偏離時列差異待確認。具體原始數值封裝與布局仍待定。 | 避免各 task 重複準備同份大數據；不把每一項純量都強制放共享區。 |
| seed、少量算法參數、迭代上限 | 屬本 task 輸入；直接傳值等正式交付表示仍待細化。 | 小資料不一定值得額外管理 SHM，也不由 C++ 重選整場實驗安排。 |
| population、trial、容量工作緩存、RNG | 每個任務自己持有。 | 不同 seed／算法執行狀態不能互相覆寫。 |
| addAct 歷史 | 本任務獨立保存，完成後返回。 | 不把題庫共享記憶體誤當成全量歷史儲存。 |

SHM 只共享明確放入的資料，不會自動共享其他 Python／算法內容。舊多程序基線各 worker 有自己的 Python 執行環境；候選同 host 多 threads 則共用程序位址空間，不能宣稱 Python 環境仍按 worker 隔離。無論拓撲，各 task 的算法可變狀態、工作空間及 RNG 仍須私有，具體映射待確認。

健康程序可跨 task 存在，但本題的 RNG、population、工作狀態與歷史仍須獨立初始化及正確交接／清理。原交接基線中 D77 的每 task 解除共享資料存取不取消程序重用；新候選也不因此獲准跨 task 保留可變算法狀態，或在其他使用者仍需共用數值時移除它。

## 原始數值與衍生數值的責任

- Python 可以載入原始數值，但不因此取得問題數學定義的責任。
- 距離捨入、限制式衍生表、可行性相關轉換，必須遵循問題規則。
- 同一題的固定衍生資料由 C++ 問題模組依數學規則準備，正式求解共用。D74 的隔離 worker 與 D75 的搬入共享區是原交接基線；候選偏離時依上表列差異待確認，型別、布局與正式交接表示仍待細化。
- 不允許 Python 和 C++ 各用不同距離規則，又把同名矩陣視為同一道題。

若問題需要算法專用 lookup table，應區分是共通問題資料，還是算法內部緩存；不一律搬到實驗管理。

「是否另保存當時已計算的衍生數值供追查」仍未決定。共享記憶體是本次執行期間的資料，不等於磁碟保存或完整環境封存。D23／D45 要求的實際輸入紀錄不取消，D48–D49 的重跑仍讀指定設定；本次不自行增加歷史自動採用、比對或恢復機制。

## 已確認的數值型別與轉換邊界

- D72：題目／算法參數的整數欄位必須提供整數；20.0、20.7、字串及布林值都不能先轉成整數後接受。
- D73：浮點欄位可接受浮點輸入，以及可精確表示於目標型別且符合欄位範圍的整數；失真或超出範圍報錯，不接受字串或布林值。不能一律拒絕大整數，也不能一律先轉成浮點數。
- 專用檢查依 D69–D70 由對應 C++ 模組執行；Python 讀取／包裝資料時不能先改掉原輸入，讓原本不合法的型別或數值消失。正式檢查與轉換的交接步驟仍待細化。
- 此處不選全系統浮點精度、整數位寬、陣列布局、binding 或 SHM 表示，也不改算法內部取整、問題明定的衍生計算與 D61 停止規則。

D78 另要求保留足以判斷未知題目欄位的內容，不能先刪掉不認識的欄位，再聲稱問題模組已檢查通過。它和 D72–D73 的原型別／數值保留共同約束交接，但不在本輪指定共同 schema 或序列化格式。

現有 MKP loader 的整數轉型、連續題的 float64 整理都是現況，不等於新規則已實作；本次不改程式。具體例子、原始碼位置及限制見 [02](02_problem_data_and_configuration.md#第-3-單元子題數值型別與轉換規則已確認)、[18 的 N01–N10](18_experiment_configuration_and_task_expansion.md#數值轉換規則核對)。僅有這兩項規則，不能宣稱資料已能無損、無複製交給 C++。

## 已確認的共享資料生命週期

以下分清原交接基線的持有／連接機制與不變的保護／有效性要求；新候選如何落實及是否偏離基線，依 [對照表](#不變需求與原交接基線) 核對。

- **原交接基線由主程序持有共用資料**：資料不依附預處理 worker 或某個求解 worker；本次工作尚未結束、仍有使用者時不提早移除。
- **求解端唯讀**：D76 要求唯讀存取保護及 C++ 唯讀介面，不只是約定不要寫。正式映射方式、誤寫效果與故障隔離須另測，不能把 const 或 NumPy 唯讀標記當成底層保護已完成。
- **原交接基線每個 task 按需連接並解除**：只連接本 task 需要的資料；使用與同步保存結果完畢後解除自己的存取，當時未採啟動時連上全部題目或跨 task 長期保留連接。新候選若改持有或映射方式，須明列差異待確認。
- **結果使用期間保持有效**：若返回結果或歷史仍引用題目數據，必須等相關消費者用完再解除；保存完成之前不能為接下一題而提前回收。
- **所有使用者釋放後才清理共用資料**：停止要求不等於所有 task 已安全結束；原交接基線由主程序在整場收尾清理。候選須說清持有者／回收時序；一個 task、邏輯單元或 host 結束，都不能代替確認其他使用者已釋放。D40 替換與同 host 連帶影響依 [14](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍) 待確認，不提前回收其他 task 仍使用的資料。

以上保留 D76–D77 的不變要求與原交接基線，不是已完成的 C++ 持有者、映射、引用或回收實作，也未批准另一套機制。

| H02 尚未全部備妥 | A 已準備完成，B／C 仍在逐題準備。 | 不先分派 A 的正式求解；全部選中題目成功後才開始並行求解。 |

| H04 準備者不再存活 | 固定資料已成功交付實驗側後，預處理 worker 結束。 | 資料不得因準備者退出而失效，後續求解不綁準備者；這是目標要求，不宣稱退出／回收實作已通過。 |
| H05 意外寫入 | 某求解 worker 嘗試修改共用距離表。 | 需要唯讀保護阻擋一般誤寫；若造成該 worker 出錯，仍須避免污染其他 task。正式故障效果另驗證。 |
| H06 單 task 解除連接 | A 題某 task 使用及保存完畢，其他 task 仍在讀相同資料。 | 只解除已結束 task 的存取；主程序保留原資料，其他使用者不受影響。 |
| H07 結果仍有引用 | C++ 已返回，但 Python 輸出器尚在使用引用題目資料的結果。 | 不得因 C++ 返回就提前解除或覆寫；等使用及保存完成後再回收本 task 存取。 |
| H08 整場收尾 | 整場工作已結束，但仍有使用者未釋放；或所有使用者均已釋放。 | 前者不得清理共用資料；後者才由主程序清理。正式引用追蹤與異常清理仍待實作。 |

這些只核對規則一致性，不驗證 RNG、數值相等、實際複製次數、RAM 尖峰、原生誤寫或通知／退出交錯；不屬正式共享機制驗收。

## 仍待細化的交接實作

D74–D77 不是從未決定：沿用原交接基線時，繼續細化下列實作；新候選若改變具體機制，須先按 [對照表](#不變需求與原交接基線) 列差異待使用者確認。不變的準備關卡、共用唯讀、task 狀態私有及使用期間有效性不得因換拓撲而省略。

1. 預處理 worker 與正式求解 worker 各自接收哪些題目資料、算法參數及執行設定？正式檢查結果如何交回 Python？
2. 沿用基線時，主程序持有的共享區如何配置、描述、傳遞及附接，D75 搬一次的成本與暫存尖峰如何核對？新候選的實際持有者與搬移安排相對基線有哪些差異？

4. C++ 視圖、Python 物件與共享區如何維持持有關係？結果／歷史輸出完畢後，如何正確回收，是否另有完整副本？不預設再向主程序交完整歷史。
5. D72–D73 的數值兼容規則已定；具體位寬／浮點精度、其他跨精度轉換、形狀與排列，以及正式轉換 API 仍待決定，不能先改值來繞過已定檢查。
6. task 異常後如何保存／取得實際輸入？不能只留下已釋放的 SHM 名稱或可變來源路徑。「是否另保存衍生資料供追查」仍未決定，不自動採用歷史值。

memoryview 或 buffer 介面名稱本身不等於保證零複製。需要實際型別／布局／持有者符合要求，並檢查傳輸全程。
