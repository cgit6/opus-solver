# 03｜單次任務與結果契約

狀態：任務粒度、必要資訊、不可行語意、異常留存、程序重用，以及 D30–D40 的呼叫／保存／通知政策已確認；正式欄位、型別、通訊／監督實作、所有權與序列化待定。對應 D04–D07、D18、D23–D40、P07–P10。

## 一個 task 是什麼

```text
一個問題實例 × 一個算法 × 一組算法參數 × 一個 seed × 一次完整求解
```

例如一題跑 10 個 seed，是 10 個任務。每個任務內可以有數千次迭代、數萬次評估和許多 addAct，不能把其中每次評估都當成一個完整外層任務。

一個健康求解程序可以依序執行多個這樣的完整 task；程序不是 task 的唯一身分。每題仍按自己的輸入與 seed 初始化，交付後正確清理，不能延續上一題的 RNG、世代計數或歷史。結果仍被使用時不得提前釋放；正式介面與所有權細節待定。

## 任務輸入必須能表達什麼

| 資訊 | 用途 | 邊界 |
| --- | --- | --- |
| 任務識別與實驗關聯 | 知道結果屬於哪題、哪組參數、哪次重複。 | 不是強制採某種 UUID／digest 格式。 |
| 問題類型、題目與實際數值 | 建立指定問題。 | 傳值或共享記憶體引用尚待定。 |
| 算法 ID 與本次有效參數 | 建立算法與初始化狀態。 | 不能只傳未解析索引而無法知道實際使用什麼。 |
| seed 與停止條件 | 決定隨機起點與本次預算。 | 逐流程重現使用固定迭代；不以執行秒數承諾重現。 |
| 紀錄相關設定 | 決定已允許的外部狀態提交行為等。 | 不違反本輪所有任務的全部實際提交均保留。 |

既有 `RunTask` 類別不必原樣搬成 C++ struct；這裡先確認資訊與責任。

## 非預期結束時也要能重建這份工作

實驗模組須保留 task 實際收到的問題數值、完整有效算法參數、seed、停止條件、紀錄設定及其他初始化輸入，讓研究者事後只重跑該 task。

不能依賴 C++ 正常回傳，才第一次留下重跑所需輸入。D36 要求主程序先保留實際輸入及 worker／task 對應，再逐題指派；異常時補上已知事實。具體保存格式、通訊與監督實作仍待定。

大份固定數據可保存一次後引用，但可變檔案路徑或暫時 SHM 名稱不足以保證日後重建。此需求不等於自動續跑整場實驗，也不等於每次必定再次崩潰。詳見 [14](14_python_cpp_invocation_and_failure_replay.md)。

單一 task 軟體異常後須記錄並繼續下一個新 task，必要時替換 worker；不是自動重試本 task。Python 寫檔異常另外要求保存原因與 task 對應，不能只用求解失敗的輸入紀錄代替。保障範圍與已確認的記錄語意見 [15](15_task_failures_and_result_storage.md)。

其他正常 task 不取消、不重跑；本版不加入卡住後自動超時中止，也不把長時間未返回本身當成已知求解錯誤。固定迭代的重現性及程序重用證據範圍見 [14](14_python_cpp_invocation_and_failure_replay.md)、[16](16_process_lifecycle_experiment.md)。

## 正常結果必須能表達什麼

- 對應的任務識別。
- 正常完成、最終解是否可行。
- 可完整重建的最終解，不只一個分數。
- 真實目標值；若算法另有 penalty／search score，獨立保存。
- 迭代數、評估數、停止原因及時間紀錄。
- 求解任務已完成最終驗證的結果／必要說明。
- 全部實際 addAct 紀錄，隨本次任務一次交付。

這些是語意需求，不代表已同意新增一整套大型驗證證明或多版本欄位。

## 不可行，不等於沒有正常算完

| 情境 | 任務意義 | 回傳方向 |
| --- | --- | --- |
| 到達停止條件，最終候選解可行 | 正常完成。 | 真實目標、完整解、feasible=true、歷史。 |
| 到達停止條件，最終候選解不可行 | 正常完成，但沒交付可行解。 | 仍保存該解與真實目標，feasible=false，不以錯誤阻擋。 |
| 輸入缺失、算法不支援、執行例外 | 沒有正常完成指定求解。 | 明確錯誤，不偽造零分／空解為成功。 |
| 最終解與聲稱的確定性分數／可行性不一致 | 求解／驗證失敗。 | 回報失敗，不以「不可行」掩蓋狀態錯誤。 |

若根本無法產生任何可返回候選解，其結果型別仍需細化；不能把「有解但不可行」與「沒有解物件」混成同一件事。

## SCVRP 為什麼不能只有一條平面陣列

SCVRP 結果除了走訪順序，還可能需要路線分隔、空路線、轉移狀態、轉移車輛與容量資訊，才能完整重建與驗證。

既有 [engine/models.py](../../../engine/models.py) 的 `SolveResult.best_solution` 強制是一維 NumPy array；目前專用算法可能使用編碼陣列配合 metadata。這是現況，不是新系統必須永久沿用的表示限制。

新契約要求完整資訊，但本輪不指定所有問題只能用同一個任意 object，也不指定所有解必須二維矩陣。

## 接收結果與數學驗證的界線

Python 必須能辨識「收到哪個任務的結果、成功還是錯誤、能否保存」，這是接收契約，不是重新算目標函數。

最終數學核對由求解任務依問題規則完成；實驗側不再建立第二個正式 evaluator。開發測試仍可以用 Python oracle，比對後不必在每次實驗重跑它。

## 完成、返回、保存是三個不同時點

```text
C++ 計算／驗證完成 → Python 收到完整回傳 → Python 保存成功
```

這次已決定前兩者一次交付；「何時把任務標成可在重啟後跳過」屬於後續持久化設計。不能因 C++ 回傳，就宣稱磁碟已保存成功。

已選由 Python worker 同步保存，再把摘要／檔案位置交給主程序，不交付整份歷史給主程序。D37 的「已接收任務」「C++ 已正常返回」只記收到的階段事實，不代替完整最終回報。D38 要求退出時先處理已交付通知，仍缺少完整最終回報才記交付未確認；保留輸入與現有文件，不自動核對文件、補登或重跑。

task 結果與 worker 健康分開：已收到的完整成功／錯誤回報，不因 worker 後續退出被改寫。D39 的非預期 C++ 錯誤須替換該 worker；D40 的 Python 保存錯誤須保留實際原因，清理成功且狀態可信才重用，否則替換。正式欄位、通訊／監督與回收方式仍待定，不新增實驗側數學重驗；十案例見 [15](15_task_failures_and_result_storage.md#十個事件案例)。

完整歷史不是 checkpoint。中斷時重跑未完成任務，不代表能拿 addAct 的最後一筆直接接著算。

## 驗證案例

開發時至少使用 MKP、SCVRP、連續題各一個代表，分別驗證可行、不可行、輸入錯誤及核對失敗的結果語意；完整紀錄還須測外部結構為 nil。這是未來驗收清單，本次沒有執行。
