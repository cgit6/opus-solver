# 03｜單次任務與結果契約

狀態：任務粒度、必要資訊、不可行語意、異常留存及程序重用已確認；D30–D40 曾收斂呼叫／保存／通知政策，其中 D35 現作重新評估基線，架構狀態與比較維度見 [14](14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度)。D50–D64 補足參數明寫、迭代計數及停止子設定，D74–D78 補足題目準備、共享生命週期與未知欄位政策。完整任務／結果欄位、型別、通訊／監督、所有權實作與序列化仍待定；D79–D80 更新算法錯誤的整場停止範圍。對應 D04–D07、D18、D23–D40、D50–D64、D74–D80、P07–P10。

## 一個 task 是什麼

```text
一個問題實例 × 一個算法 × 一組算法參數 × 一個 seed × 一次完整求解
```

例如一題跑 10 個 seed，是 10 個任務。每個任務內可以有數千次迭代、數萬次評估和許多 addAct，不能把其中每次評估都當成一個完整外層任務。

task 不是程序或 thread：健康程序可重用，候選也可能在同 host 承載多條工作鏈。每條鏈同時負責一題，完成同步保存／交接及清理、環境可信且整場未停止後才接新題，不預設永久綁某個 thread／程序；定義見 [14 名詞表](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍)。各 task 的 RNG、世代計數與歷史獨立，仍被使用的結果不可提前釋放；正式映射與所有權待定。

### 正式 task 開始前先準備題目

D74–D75 的原交接基線已選一個隔離 worker 逐題預處理、C++ 先算好衍生資料再搬入 SHM 一次。新候選若改隔離準備或搬移機制，依 [08 的分層對照](08_cpp_invocation_and_shared_memory.md#不變需求與原交接基線) 列差異待確認；同題固定資料避免重複準備、全部選中題目成功後才正式求解、準備失敗不進入求解仍是不變要求。預處理不算一輪算法更新，也不計入 D54 的求解時間。

D76–D77 保留求解端唯讀保護、資料不依附準備者，以及結果／歷史仍引用數據時不可提前回收的要求。原交接基線已選每 task 按需連接及使用／保存後解除、主程序持有至整場結束且所有使用者釋放後清理；新候選若改持有、映射與解除，須列差異待確認，正式實作仍待驗證。原流程、來源及 H01–H08 見 [08](08_cpp_invocation_and_shared_memory.md#不變需求與原交接基線)，不當成新拓撲驗收。

## 任務輸入必須能表達什麼

| 資訊 | 用途 | 邊界 |
| --- | --- | --- |
| 任務識別與實驗關聯 | 知道結果屬於哪題、哪組參數、哪次重複。 | 不是強制採某種 UUID／digest 格式。 |
| 問題類型、題目與實際數值 | 使用指定問題的準備資料。 | 固定資料共用、唯讀且使用期間有效；D74–D77 的原交接機制與候選差異依 [08](08_cpp_invocation_and_shared_memory.md#不變需求與原交接基線) 核對，正式資料描述及小量數值表示仍待定。 |
| 算法 ID 與本次有效參數 | 建立算法與初始化狀態。 | 可設定參數須明寫，不自動補值；不能只傳未解析索引而無法知道實際使用什麼。 |
| seed 與群組停止設定 | 決定隨機起點、主要方式／數值、達標開關及連續無改善輪數或 null。 | 由群組唯一提供，停止欄位依 D61；逐流程重現使用固定迭代，不以執行秒數承諾重現。 |
| 紀錄相關設定 | 決定已允許的外部狀態提交行為等。 | 不違反本輪所有任務的全部實際提交均保留。 |

既有 `RunTask` 類別不必原樣搬成 C++ struct；這裡先確認資訊與責任。

D78 要求選中題目的未知欄位在啟動前指出並拒絕整場，不能先移除欄位再聲稱已檢查。預處理與正式求解各自收到的完整欄位、函式及交付仍待定；[19 的候選研究](19_architecture_candidate_experiments.md) 不等於正式契約已完成，架構組合仍依 [14 的比較維度](14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度) 確認。

群組停止設定是 task 實際輸入，但不因此成為 D47 的判重鍵。相同問題類型、題庫、題名、算法、參數組及 seed，即使停止設定不同也拒絕本次實驗啟動。已確認的迭代計數、零次初始化及檢查點見 [02](02_problem_data_and_configuration.md)、[18](18_experiment_configuration_and_task_expansion.md)。

指定 0 次仍是一個完整 task：做原本初始化、最終驗證並返回初始結果與實際歷史，只是不做更新。若初始解達標而提早返回，或時間在初始化結束時已耗盡，完成迭代也可以是 0；不能用設定上限假裝已完成的輪數。

## 非預期結束時也要能重建這份工作

實驗模組須保留 task 實際收到的問題數值、完整有效算法參數、seed、停止條件、紀錄設定及其他初始化輸入，讓研究者事後只重跑該 task。

不能依賴 C++ 正常回傳才第一次留下重跑輸入。D36 要求管理端先保留實際輸入與 task 的執行關聯，再逐題指派；同 host 多題仍須辨識各題，不只記程序。具體識別／映射、保存格式、通訊及監督仍待定，不新增正式欄位決策。

大份固定數據可保存一次後引用，但可變檔案路徑或暫時 SHM 名稱不足以保證日後重建。此需求不等於自動續跑整場實驗，也不等於每次必定再次崩潰。詳見 [14](14_python_cpp_invocation_and_failure_replay.md)。

是否另外保存已算好的衍生數值供追查仍未決定；D74–D77 只定本次執行期間的準備、共用及清理，不等於磁碟保存策略。D23／D45 的紀錄責任不取消，D48–D49 的重跑仍讀指定設定，不自動採用歷史副本。

算法非預期錯誤依 D79–D80 停整場，涵蓋其他算法／在途 task；不再派工，保留已保存結果，不自動重跑。D25 另要求範圍內 Python 軟體保存失敗的原因與 task 事後可查，不能只用求解輸入或失敗標記代替。通知不等於持久留存；正式誰／何時／何處保存、完成判定及二次失敗／退出界線依 [15](15_task_failures_and_result_storage.md#保存錯誤原因的留存界線) 待確認，強需求不降級，也不因此宣稱任意情境已保證。

正常不可行解不觸發算法錯誤停止；Python 保存錯誤仍依 D40，不一律擴大為算法錯誤。停止時點、安全收尾及未知原因退出判定待細化，連帶停止不能冒充成功或算法自身錯誤。本版不加入卡住超時，也不把等待很久當已知求解錯誤。固定迭代的重現性及程序重用證據範圍見 [14](14_python_cpp_invocation_and_failure_replay.md)、[16](16_process_lifecycle_experiment.md)。

## 正常結果必須能表達什麼

- 對應的任務識別。
- 正常完成、最終解是否可行。
- 可完整重建的最終解，不只一個分數。
- 真實目標值；若算法另有 penalty／search score，獨立保存。
- 實際完成迭代數、評估數、停止原因及時間紀錄；初始化不算一次迭代。
- 求解任務已完成最終驗證的結果／必要說明。
- 全部實際 addAct 紀錄，隨本次任務一次交付。

這些是語意需求，不代表已同意新增一整套大型驗證證明或多版本欄位。

達標、無改善與主要上限可能同時成立；結果如何表示多條件、是否需要單一原因及其順序仍留第 4 單元，不由本輪先補定。無改善判斷依算法歷史最佳解規則，不能將它記成 D57 的題庫目標達標。

## 不可行，不等於沒有正常算完

| 情境 | 任務意義 | 回傳方向 |
| --- | --- | --- |
| 到達停止條件，最終候選解可行 | 正常完成。 | 真實目標、完整解、feasible=true、歷史。 |
| 到達停止條件，最終候選解不可行 | 正常完成，但沒交付可行解。 | 仍保存該解與真實目標，feasible=false，不以錯誤阻擋。 |
| 輸入缺失、算法不支援、執行例外 | 沒有正常完成指定求解。 | 明確錯誤，不偽造零分／空解為成功。 |
| 最終解與聲稱的確定性分數／可行性不一致 | 求解／驗證失敗。 | 回報失敗，不以「不可行」掩蓋狀態錯誤。 |

若根本無法產生任何可返回候選解，其結果型別仍需細化；不能把「有解但不可行」與「沒有解物件」混成同一件事。

## SCVRP 為什麼不能只有一條平面陣列

SCVRP 結果除了走訪順序，還可能需要路線分隔、空路線、轉移狀態、轉移車輛與容量資訊，才能完整重建與驗證。

既有 [engine/models.py](../../../engine/models.py) 的 `SolveResult.best_solution` 強制是一維 NumPy array；目前專用算法可能使用編碼陣列配合 metadata。這是現況，不是新系統必須永久沿用的表示限制。

新契約要求完整資訊，但本輪不指定所有問題只能用同一個任意 object，也不指定所有解必須二維矩陣。

## 接收結果與數學驗證的界線

Python 必須能辨識「收到哪個任務的結果、成功還是錯誤、能否保存」，這是接收契約，不是重新算目標函數。

最終數學核對由求解任務依問題規則完成；實驗側不再建立第二個正式 evaluator。開發測試仍可以用 Python oracle，比對後不必在每次實驗重跑它。

## 完成、返回、保存是三個不同時點

以下沿用 D18–D19、D34 舊 Python 保存基線。候選若改 C++ 獨立輸出、完整歷史轉成 Python 物件的方式或完整返回邊界，須依 [07](07_history_return_and_storage.md#已確認交付需求與保存基線) 列內容與所有權差異待確認，不能直接略過 D18。

```text
C++ 計算／驗證完成 → Python 收到完整回傳 → Python 保存成功
```

這次已決定前兩者一次交付；「何時把任務標成可在重啟後跳過」屬於後續持久化設計。不能因 C++ 回傳，就宣稱磁碟已保存成功。

D34 的同一邏輯工作鏈同步保存及主管只收摘要／路徑已定；Python 是舊保存基線，候選比較不重開主程序收全量保存。D37 兩種通知只記階段事實，不代替完整最終回報。D38 對實體 host 退出先處理各 task 已交付通知，再逐題判定；缺完整回報者記未確認，保留輸入／文件，不自動核對、補登或重跑。

task 結果與環境健康分開：完整成功／錯誤回報不因 host 退出改寫，同 host 其他題另判。算法錯誤依 D79–D80 停整場；D40 保存原因，清理成功且環境可信才重用，否則不再使用不可信環境。舊基線可替換程序，新拓撲的範圍／時機按 [14](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍) 待確認，不默選退休策略或把保存錯誤全場停。正式欄位／通訊／回收未定，不增數學重驗；案例見 [15](15_task_failures_and_result_storage.md#十個事件案例)。

完整歷史不是 checkpoint。中斷時重跑未完成任務，不代表能拿 addAct 的最後一筆直接接著算。

## 驗證案例

開發時至少使用 MKP、SCVRP、連續題各一個代表，分別驗證可行、不可行、輸入錯誤及核對失敗的結果語意；完整紀錄還須測外部結構為 nil。這是未來驗收清單，本次沒有執行。
