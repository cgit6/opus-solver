# 14｜Python 如何呼叫 C++ 求解模組，以及失敗 task 的單獨重跑

整理日期：2026-10-22。

狀態：已選 Python worker 內同程序 C++ 擴充模組，以及 worker 同步保存、主程序只收摘要與檔案位置（D34–D35）。異常輸入保存、重跑、原因留存、健康程序重用及其他工作不中斷不變；首版 Linux／WSL，不做自動超時或內建單 task 停止。D36–D40 已確認主程序派工、階段通知、交付未確認及兩類錯誤的處置政策；正式函式、通訊／監督實作、狀態保存格式及資料所有權仍待細化，尚未修改正式程式。

本文件獨立記錄呼叫、故障邊界、開發測試及失敗任務重跑。問題數值與共享記憶體的交接另見 [08](08_cpp_invocation_and_shared_memory.md)，不把兩個議題混成一個選型。

worker 同步保存、DTO 分層及軟體異常後繼續的完整規則見 [15 task 異常與結果保存](15_task_failures_and_result_storage.md)，本輪選型證據見 [17](17_invocation_comparison_experiment.md)。本版不新增磁碟滿、磁碟故障等硬體／資源層故障的專用處理。

## 一、這次新增的核心需求

使用者明確要求：

> task 發生非預期情況時，實驗模組要記下它收到的工作與實際輸入，讓研究者之後能單獨重跑這個 task，找出問題。

重點是「知道哪份工作未正常完成，並能重建同一份工作」，不是要求 Python 找出 C++ 哪一行出錯。

這屬於實驗管理的任務追蹤與保存責任，不是實驗側重新計算 objective／constraints；也不是要求從算法中間狀態繼續執行。

後續使用者進一步確認：求解異常只需讓 Python 知道工作未正常完成並保留實際輸入；Python 寫檔異常則須保留失敗原因。單一 task 的軟體異常不終止整場，必要時替換 worker，再處理下一個新 task，不默認自動重試原 task。

## 二、不變的既有決定

- 一個 task 仍是一題、一算法、一組參數、一個 seed 的完整求解。
- 傳統問題的搜尋、objective、constraints、最終數學驗證留在 C++。
- 全部實際 addAct 紀錄在求解任務內保存，完成後與最終結果一次返回 Python。
- Python 負責文件保存；不加入紀錄分批交付、背景 writer 或 Redis。
- 任務正常完成但最終解不可行，不算這裡的執行異常。

保存失敗任務輸入，不會更動以上邊界。

### 已確認的程序生命週期（D27–D29）

- 一個 task 出錯，不取消、不重跑其他正常 task；例如 8 個同時執行的工作壞了 1 個，其餘 7 個照常執行。
- 健康的求解程序完成一題、正確交接與清理後，繼續接下一個新 task，不每題重新啟動整個執行環境。
- 每題依自己的有效輸入及 seed 初始化 RNG、算法狀態、工作空間與歷史，不能延續上一題的搜尋進度、世代計數或亂數序列。
- 崩潰或狀態不可信時，只替換出問題的執行單元，再接下一個新 task；不默認自動重試失敗 task。非預期 C++ 錯誤即使已捕捉也替換該 worker（D39）；Python 保存錯誤則清理成功後可重用，失敗或不可信才替換（D40）。
- 結果及歷史若仍被接收／保存方使用，不得提前釋放或覆寫。正式採複製、移交所有權或保留有效持有者，仍待資料交接議題決定。
- 本版不加入卡住後自動超時中止；一直未完成、但沒有明確錯誤或程序終止的工作，暫由研究者人工處理。不能只因等很久就自動標成求解失敗；這也不更動算法自己的正常停止條件。

這些 D27–D29 決定生命週期，沒有批准跨任務共用一份可變算法緩存。程序重用證據見 [16](16_process_lifecycle_experiment.md)；後續 D35 的呼叫選型另見下一節及 [17](17_invocation_comparison_experiment.md)。

## 三、呼叫方式已選定：A｜同程序 C++ 擴充模組

### 正式方向與保障範圍（D30–D35）

```text
Python 實驗主程序
  → 隔離的 Python worker
      → 同一程序內的 C++ 完整求解入口
      → C++ 完成求解與最終驗證，一次交回完整結果及全部歷史
      → Python worker 呼叫共用輸出器，同步保存該題
      → 主程序只接收摘要與檔案位置
      → 本題資料按生命週期清理後，健康 worker 接下一題
```

即使只同時跑一題，也保留主程序與求解 worker 的程序隔離，不把可能原生崩潰的呼叫直接放進主程序。結果仍被保存方使用時，不得提前釋放或覆寫；上述流程不是正式完成通知／回收協議。

- **平台（D30）**：首版 Linux／WSL，不以原生 Windows 作本版驗收；C++ 核心避免不必要的平台耦合。
- **人工停止（D31）**：不內建單 task 停止命令；研究者使用外部工具處理，系統依已觀察到的程序終止記錄與恢復，不新增自動超時。
- **呼叫粒度（D32）**：Python 正式 API 只需完整求解及結果，不要求公開 C++ 算法物件或逐步操作函數。逐模組測試仍須做，可在原生測試或 oracle 完成。
- **重跑（D33）**：Python 命令能載入保存輸入並單獨從頭重跑即可，不要求 Python-free 的原生入口；正式命令名稱、參數與保存格式另議。
- **保存（D34）**：worker 同步保存完本題才接下一題，主程序只收統計所需摘要與位置。文件 I/O 屬 Python 實驗／輸出模組，不屬 C++ 求解核心。
- **隔離（D35）**：C++ 原生崩潰可連帶終止該 Python worker；主程序記錄並只替換該 worker，其他正常工作不中斷、不重跑。

控制原型透過 pybind11 執行；C++ 仍是編譯後的原生運算，不是轉成 Python 迴圈。正式入口名稱、binding／建置細節、資料型別與所有權仍待定；採擴充模組不等於自動零複製。C++ 核心與 Python 接線應分開，算法內部不依賴 Python 型別。

正常時重用載有 C++ 的健康 Python worker，但每題狀態獨立。D36–D40 已決定派工與異常處置政策（第七節）；正式監督／通訊協議尚未實作，不能沿用目前程序池的整池關閉策略，也不能只替換已死亡程序而繼續使用發生非預期 C++ 錯誤的 worker。

### 比較過但首版不採用：B｜獨立 C++ 求解程序

B 可由 Python 呼叫者啟動可重用的 C++ 子程序。C++ 崩潰時，Python 呼叫者通常仍存活；但需要程序間輸入／輸出與結果生命週期協議，並非只有寫 JSON 文件一種做法。

本輪配合 worker 保存路徑，另比較了「Python worker＋獨立 C++」的管線複製與共享記憶體配置。共享記憶體配置可避免兩邊各持有完整結果，不能把複製版本的成本當成獨立程序的必然成本；也不能用這個特定拓撲概括所有 B 設計。B 與 A 都依同樣要求重用健康程序、保留輸入及隔離故障。

B 的額外隔離是讓該 Python worker 在 C++ 終止後仍存活。目前需求允許替換該 worker，不要求增加這項保障；重跑也不要求脫離 Python。因此使用者看過對照後選 A，而不是宣布 B 不可行或在所有負載必定較慢。

### 決策沿革與證據

先前以「符合現有 worker 流程」或「較早驗證完整契約」優先 A 的理由仍然撤回，不作這次選型依據。程序生命週期實驗使用獨立執行檔，也沒有自行選定 B；舊核心未清理好的記憶體增長不作選型理由。

後續先確認 D30–D34，再做同一 C++ 合成工作、同一 Python 保存函數的對照；完整內容、RNG、例外、寫檔錯誤及八 worker 中的單程序終止均有控制證據。使用者據此確認 D35，詳見 [17 呼叫方式對照](17_invocation_comparison_experiment.md)。這不是宣稱正式算法、任意外部結構、資料交接及整套恢復流程已驗收。

## 四、錯誤類型、故障隔離與恢復策略要分開

| 情境 | 程序可能發生什麼 | 不可混淆的地方 |
| --- | --- | --- |
| 非預期 C++ 例外可被轉換、捕捉 | worker 可能仍存活，不等於原生崩潰。 | D39 仍要求保存輸入與錯誤、替換該 worker；已知輸入錯誤及正常不可行不混入這類異常。 |
| A 中的 C++ 非法記憶體存取等原生崩潰 | 該 Python worker 可能直接終止，不能再接新工作。 | 不是只把當前函數當成失敗後，原程序照常繼續。 |
| B 中的 C++ 子程序非預期終止 | Python 呼叫者通常仍可觀察到子程序未正常結束。 | 依已確認需求記錄並繼續新 task；不是對同一個失敗 task 自動重試。 |
| Python 輸出軟體流程出錯 | 可能可捕捉例外，求解已完成但保存未完成。 | D40 保留實際原因及 task 對應；本題資源清理成功才重用，清理失敗或狀態不可信才替換。 |

磁碟滿、磁碟故障等硬體／資源層異常不納入本版專用恢復或錯誤留存保證，亦不以相同磁碟的另一個資料夾宣稱完成跨媒介備援。

已確認的原則與待設計的機制要分開：

1. **故障隔離**：D35 以主程序外的 Python worker 載入 C++；即使只同時跑一題，原生崩潰也不能帶走管理端。正式監督與通訊協議仍待定，不再重選 A／B。
2. **恢復策略**：記錄後只替換必要的執行單元、繼續新 task；健康程序重用，不取消或重跑其他正常工作。D36–D40 決定執行對應、通知及替換政策；正式機制仍待設計，不是由語言自動完成。
3. **診斷與重跑**：保存哪些輸入及已知異常資訊，供人工調查。

最新需求已取代較早的任務失敗停止整場策略，也不接受為重建整個池而取消／重跑其他正常工作。繼續派工不能默默遺漏異常紀錄；若現況觀察到程序池連帶報錯，也不能把每個報錯 task 都當成算法自身崩潰。實際執行對應與交付未確認按 D36–D38 記錄；具體保存格式與通訊機制仍待細化。

Python 算法也需要這套任務追蹤與錯誤保存。純 Python 的一般錯誤通常較容易以例外定位，但原生依賴（例如 NumPy／Numba）崩潰仍可能使 worker 死亡；不能把這項責任視為只有 C++ 才需要，也不能因觀察到 worker 消失就斷言根因。

## 五、現有專案的實際影響範圍

以下是依目前程式推導「若接入原生 C++」的影響，不表示正式 C++ 模組已存在或目前派工流程已通過原生崩潰測試；另做的臨時對照見 [16](16_process_lifecycle_experiment.md) 與 [17](17_invocation_comparison_experiment.md)。

- [machine/core.py](../../../machine/core.py) 的單 worker 路徑直接執行 `machine.run()`，沒有獨立求解 worker；若在此程序直接載入 C++，原生崩潰可能使實驗主程序一起終止。
- 多 worker 使用 `ProcessPoolExecutor`；收到任務例外後，現有程式會取消能取消的未完成工作、關閉程序池並向外拋錯，不會自動補 worker 繼續整場實驗。
- worker 突然死亡可使程序池成為 `BrokenProcessPool`，原程序池不能繼續接新工作。重建程序池是建立新的執行環境，不是把死亡程序復活。
- 目前有 `future → task` 對應及 `_add_task_context_note()`，但程序池整體失效時，多個 future 可能一起報錯；不能只看第一個報錯 future，就認定它是造成崩潰的 task。
- [cli/run/support.py](../../../cli/run/support.py) 通常等整批完成才寫正式結果；目前不保證已算完的任務或終端錯誤訊息已永久保存。

目標已選擇主程序與載入 C++ 的 Python worker 隔離；即使只有一個求解 worker，也不沿用主程序直接求解。實際執行追蹤、退出觀察及通知未達的政策已由 D36–D40 確認，正式機制仍待細化／驗收，不能把政策定案當成程式已實作。

RNG 隔離與程序池是否連帶中止是兩件事。目前 `Machine.expand_tasks()` 在分派前決定各 task 的 seed；`_run_task_process()` 每題建立自己的 RNG，CDELS 也依本次 seed 建立自己的 MSVC 相容 RNG。失敗工作多抽亂數，不代表其他工作會共用或接續那份亂數狀態。這不等於所有算法都已完成重現性驗證；新 C++ 任務也必須遵守每題狀態隔離，固定迭代時再核對其他工作初始化、過程與結果不變。

## 六、失敗任務至少要能重建哪些輸入

| 資訊 | 保存目的 | 限制 |
| --- | --- | --- |
| task 與實驗關聯 | 找出哪份工作未正常完成。 | 正式 ID 格式未定。 |
| 問題類型、題目與實際數值 | 重建當時求解的同一道題。 | 不能只保留之後可能改變的來源路徑。 |
| 算法選擇與完整有效參數 | 重建本次真正使用的搜尋設定。 | 包含套用後的預設值，不只保存參數組索引。 |
| seed 與相關初始化輸入 | 從相同起點重新開始。 | 若算法允許額外初始解等輸入，也必須保留。 |
| 停止條件、紀錄設定與其他 task 選項 | 避免重跑時不小心改成不同工作。 | 固定迭代與按時間停止不是相同重現保證。 |
| 執行關聯與已知異常資訊 | 知道哪個執行單元在處理它，以及如何未正常結束。 | 不強制一定能取得原生 C++ 堆疊或根因。 |

大份題目數據可保存一次，各 task 引用同一份保存內容，不要求每次複製。共享記憶體名稱、暫時指標或會消失的暫存位置，不能單獨充當日後重跑的問題數值來源。

具體檔案格式、索引、保存期限及正式回報協議尚未決定；本輪不強制加入一套版本／digest／資料庫或完整環境快照系統。

## 七、已確認的主程序派工與通知（D36–D40）

### 主程序先保留，再指定一題（D36）

主程序在派工前保留實際輸入及「這個 worker 被指派哪個 task」的對應，再向可用 worker 指派一題。同一 worker 同時只處理一題；本題完成交接與清理後，或必要的替換完成後，才接下一個新 task。worker 不自行取走主程序未登記的工作。

管理端等待 worker 訊息及程序退出事件，有事發生才處理，不用迴圈反覆掃描所有 worker。這是事件驅動方向，不在本單元指定 IPC 工具、檔案格式或監督器實作，也不新增自動超時。

### 兩種階段通知不代替最終回報（D37）

| 收到的通知 | 管理端可以記錄 | 不能推論 |
| --- | --- | --- |
| worker 已接收任務 | 該 worker 已接收被指派的 task。 | 不代表 C++ 已開始或已完成。 |
| C++ 已正常返回 | 該 task 的 C++ 呼叫已正常返回 worker。 | 不代表 Python 已保存完成、主程序已收到最終結果，亦不代替結果中的可行性。 |
| 完整成功最終回報 | worker 回報保存完成，交付該題的摘要與檔案位置。 | 不代表該 worker 之後不會退出；不要求主程序重新做數學驗證或讀檔驗收。 |
| 完整錯誤最終回報 | 回報中實際已知的錯誤、task 對應及可取得原因。 | 不將未知階段或 C++ 根因補成確定事實。 |

只記實際收到的事實。沒收到某種階段通知，不代表該階段沒發生；也不因缺少前一階段通知而推翻已收到的完整最終回報。正式訊息欄位及順序保障仍待細化，不把表格當作 wire schema。

正常路徑為：

```text
主程序保留輸入與 worker／task 對應，再指派一題
  → worker 通知「已接收任務」
  → C++ 完整求解、最終驗證，一次返回結果及全部歷史
  → worker 通知「C++ 已正常返回」
  → Python worker 同步保存本題
  → worker 交付完整最終回報，主程序只收摘要與檔案位置
  → 正確清理，健康 worker 接下一個新 task
```

這些是任務邊界上的小型控制通知，不是逐代回呼 Python，不攜帶全部歷史，不要求 addAct 寫檔或讓 C++ 分批返回。

### task 結果與 worker 健康分開（D38–D40）

- 觀察到退出事件時，須先處理該 worker 已交付的通知，再判定是否缺少完整最終回報；不能只因先看到退出，就忽略已送達的成功／錯誤回報。
- 沒有完整最終回報：記「交付未確認」，保留輸入、現有文件及最後已知事實；不自動掃檔、讀完成記錄、補登成功或重跑。
- 已收到完整成功回報：該題已確認交付；worker 後續退出只影響 worker 健康，不把該題改成失敗。
- 已收到完整錯誤回報：保留已知的錯誤與原因；worker 後續退出不把它降回只有「交付未確認」。
- 非預期 C++ 錯誤：即使已捕捉而程序仍在，也保存可取得錯誤與輸入，替換該 worker（D39）。正常不可行或已知輸入錯誤不因此一律替換；已知輸入錯誤的具體回報細節另議。
- Python 保存錯誤：保存實際原因與 task 對應；清理本題資源成功後可重用，清理失敗或狀態不可信才替換（D40）。清理不代表刪除現有結果／部分文件，也不自動重試保存。

完整 [十個事件案例](15_task_failures_and_result_storage.md#十個事件案例) 以同一政策核對；只驗證規則一致性，不代表正式通訊、退出時通知處理或恢復已通過。其他正常 task 不取消、不重跑；替換後接新 task，不默默重派原失敗工作。

本節沒有選定正式通訊格式、狀態保存格式、資料所有權或監督機制。異常輸入保存也不能與較晚處理的「整場重啟後自動跳過完成任務」混成同一個延後功能。

## 八、保存異常資訊，不等於一定知道 C++ 根因

最低目標是能記錄：

> 這份 task 收到以下輸入，執行過程未正常完成；當時能取得的錯誤資訊如下。

求解異常若能取得例外訊息、標準錯誤輸出或退出狀態，可作輔助資訊，但不把 C++ 根因／完整堆疊當必要回報。Python 的一般 traceback 不等於完整原生 C++ 堆疊；`BrokenProcessPool` 本身也未必指出真正出事的 task 或原因。

Python 寫檔異常不同：失敗原因必須留存，並對應 task、路徑及失敗動作；不能只套用「不需要 C++ 根因」而省略 Python 錯誤。worker 退出又缺少完整最終回報時，按 D38 保留輸入、現有文件及最後已知事實，不自動核對文件、讀完成記錄補登成功或重跑；也不能刪掉現有文件來假裝從未保存。範圍與案例見 [15](15_task_failures_and_result_storage.md)。

開發期可考慮帶除錯資訊的建置、faulthandler、AddressSanitizer 等，但不是已選好的正式診斷方案，也不保證所有非預期終止都能留下完整線索。

若只是因其他 worker 出事而被中斷，應和「已確認在該 worker 執行時非預期終止」區分；不能把所有受影響 task 都記成算法自身崩潰。具體狀態名稱待定。

## 九、日後如何單獨重跑

目標操作是「載入已保存的任務輸入 → 呼叫單任務求解入口 → 從頭再跑一次」，不需要重跑整個題庫或所有 seed。

D33 已確認透過 Python 命令完成即可，不要求 Python-free 的原生重跑入口。目前尚未實作正式重跑命令，不提供可直接執行的虛構 CLI。

需要盡量使用相同算法實作與執行條件；程式、依賴、硬體、執行緒或資料準備方式改變，都可能影響重現。是否記錄額外環境資訊留待細化，不以保存輸入就宣稱已封存全部環境。

**能重建同一份工作，不保證每次必定再次崩潰。**競態、未初始化記憶體、資源不足等情況可能不是每次都發生。

## 十、與 addAct、checkpoint、續跑的差別

| 功能 | 本輪定位 |
| --- | --- |
| 保存失敗 task 輸入 | 本輪必要需求；支持人工定位與單獨從頭重跑。 |
| 全部 addAct 歷史 | 正常完成後一次回傳；回傳前程序崩潰，尚在記憶體的歷史可能失去。 |
| 事後單 task 重跑 | 從保存的起始輸入重新執行，不恢復崩潰前進度。 |
| 單一 task 軟體異常後繼續新工作 | 已確認必要需求；記錄後必要時恢復／替換執行單元，不終止整場，不默認重試原 task。 |
| 整場實驗重啟後跳過完成 task | 後續持久化與續跑設計，不因本需求自動完成。 |
| 算法內 checkpoint | 仍不納入本版；addAct 不保證包含完整工作緩存與 RNG 狀態。 |

保存輸入與少量異常資訊，不等於改採逐代寫入完整求解歷史。C++ 不直接負責實驗結果文件保存的責任也不變。

## 十一、修改 C++ 後如何開發測試

已選 A 的開發流程需要編譯；B 只作比較說明：

- A：修改 C++ → 重建擴充模組 → 在新測試程序載入並測試。
- B（本版不採用）：修改 C++ → 重建執行檔 → 啟動執行檔並測試。

兩者都可設計成一個命令完成必要的增量編譯與小型測試，不必每次重新部署整套系統；D32 不要求 Python 提供逐步算法 API，但不省略逐模組原生測試。增量建置也可能因共用標頭或依賴變更而重編多個檔案，不能承諾固定耗時。

不能因 B 要執行編譯好的程式，就認定算法開發完不能快速測試；A 也不是改完 `.cpp` 就自動讓已載入的 worker 使用新版本。如何避免測到舊產物，是原型應核對的事。

重用健康程序是同一版程式處理多個 task 的正常生命週期，不是要求修改 C++ 後仍沿用已載入舊產物的程序。開發測試須載入新建置產物，具體建置與重載命令另議。

## 十二、待決與原型驗收

尚未定案：

- A 的正式函式簽章、binding／建置與新版本載入方式；單／多 worker 都以隔離的 Python worker 呼叫 C++，不再重選 A／B。
- 實際輸入、worker／task 對應及最後已知事實的保存格式／位置，以及 Python 重跑入口；先保留再指派的時序已定。
- 階段／最終通知的正式格式、事件等待與退出時先處理已交付通知的通訊／監督機制；D36–D38 政策不再待選。
- 寫檔失敗與清理失敗原因的具體記錄格式及開發診斷工具；不加入完成記錄核對功能。
- 單執行單元的隔離／替換與後續派工實作；依 D39–D40 區分替換條件，其他正常 task 不取消、不重跑，不自動重試。
- worker 保存後的摘要／檔案表示、正式最終回報及結果回收時序；D34 保存位置已定，資料所有權仍待細化。

原型驗收應包含：

1. 正常完整回傳；一般 C++ 例外和原生程序終止分開測。
2. 單求解 worker 和多 worker 都能保留必要的管理／診斷能力。
3. 程序池整體失效，不誤把第一個報錯 future 指定為真正元兇。
4. 任務失敗前已保留實際輸入，不依賴 C++ 成功返回。
5. 原始來源檔修改或 SHM 釋放後，仍可由保存內容重建任務。
6. 能只重跑一個 task，使用相同有效參數、seed、初始輸入與紀錄設定。
7. 開發修改確實觸發必要重建，新測試不是跑舊模組／舊執行檔。
8. 分開量測編譯、啟動、輸入交接、搜尋／紀錄、完整回傳與 Python 保存成本。
9. 普通求解例外、原生終止及 Python 輸出軟體錯誤後，必要紀錄可查，下一個新 task 仍可執行，其他已保存結果不被清除。
10. 寫檔錯誤原因與 task 對應保留；通知未達依 D38 不自動核對文件或補登，已收到的完整最終回報不因 worker 後續退出而被改寫。磁碟滿／磁碟故障等排除情境不列入本版驗收。
11. 同一健康程序依序處理不同 seed／題目，再回到原題與 seed，初始化、過程、RNG 與結果不受前題污染；非預期 C++ 例外依 D39 替換，Python 保存例外依 D40 測清理成功／失敗。
12. 8 個同時執行的 task 中終止 1 個，只替換該執行單元；其他 7 個不取消、不重跑，固定 seed／迭代下仍符合基準，後續新工作能執行。
13. Python 接收／保存方仍持有的結果不被下一題清理或覆寫；不以每題重開的 OS 回收掩蓋未完成的資料生命週期。
14. 將 [15 的十個事件案例](15_task_failures_and_result_storage.md#十個事件案例) 落實為正式訊息／退出交錯測試；非預期 C++ 例外須替換，Python 保存錯誤則分清理成功／失敗，不能只測正常路徑。

正式求解／派工整合尚未完成上述驗收。[16](16_process_lifecycle_experiment.md) 是程序生命週期控制實驗；[17](17_invocation_comparison_experiment.md) 補充擴充模組、完整合成結果的 Python 保存、共享記憶體對照及故障測試。兩者都不是正式算法、任意外部結構、交付確認或目前程序池已符合新架構的證明。本版不做自動超時；本次只更新文件及十案例規則核對，研究附件維持原樣，沒有重新執行實驗或正式 IPC／故障恢復測試。
