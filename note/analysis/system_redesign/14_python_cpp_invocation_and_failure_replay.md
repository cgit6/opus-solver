## 架構狀態與比較維度

D35 於 2026-10-21 曾選定「Python 主程序派工、隔離的 Python worker 內同程序呼叫 C++ 擴充模組」；這是當時的完整方案，不是從未選過的建議。D79–D80 改變算法錯誤的停止範圍後，這套拓撲成為重新評估的比較基線，不能再把它寫成目前已定案的唯一架構。正式程式尚未依此完成遷移，也尚未選定替代組合。

| 比較維度 | 要分清的問題 | D35 當時方案 | 目前狀態 |
| --- | --- | --- | --- |
| 排程責任及所在語言 | 哪些 task 分派與並行調度工作由 Python 或 C++ 負責？ | Python 主程序指定 task 給可用 worker。 | 責任如何落實待比較；Python 管理實驗的 D01–D02 責任不因此取消。 |
| 執行拓撲 | 求解分布在哪些程序／執行緒，彼此如何並行？ | 主程序與 Python 求解 worker 隔離，C++ 在 worker 內執行。 | 程序與執行緒的組合及位置待比較，不能只用語言名稱表示拓撲。 |
| 呼叫邊界 | Python 與 C++ 在同程序以 binding 呼叫，還是跨程序以 IPC 交接？ | worker 內以擴充模組呼叫 C++。 | 邊界與正式介面待比較；原型的 pybind11 及版本不是正式依賴決定。 |

三個維度可以組合。同程序 C++ 擴充模組可以使用多執行緒；Python 負責外層派工，也可以搭配 C++ 內層調度。因此不能把「Python 派工」與「C++ 調度／多執行緒」當成互斥的兩個完整方案。每個候選都須說清三個維度的組合，再檢查每題 RNG／可變狀態獨立、資料與結果交付、故障記錄及停止收尾；本節沒有選定新架構、binding 工具或正式版本。共享資料的不變需求與 D74–D77 原交接基線見 [08](08_cpp_invocation_and_shared_memory.md#不變需求與原交接基線)，新候選偏離具體機制須列差異待確認，不由拓撲比較自動撤銷原決定。輸出器議題仍依各自章節。

## 執行名詞與替換範圍

下表只釐清責任與作用範圍，不是正式 schema／API，不增加識別欄位，也不選架構。歷史方法或原型的「4 worker」等名稱仍按當時實際配置解讀，不改測量口徑。

| 名詞 | 本目錄的意思 | 不可直接推論 |
| --- | --- | --- |
| task | 一題、一算法、一組有效參數、一個 seed 的一次完整求解，包含最終驗證及完整結果／歷史交付要求。 | task 不是 OS 程序或執行緒；保存仍屬實驗／輸出責任，不移入算法。 |
| 邏輯執行單元 | 串行負責一條工作鏈的角色：接收 task → 求解與驗證 → 完整交付及同步保存 → 清理，再接下一題。 | 不預設永久綁同一 OS thread 或程序；如何映射由候選說明，不要求新增 lane ID 等欄位。 |
| 實體求解程序（host） | 載入／執行求解工作的 OS 程序，可承載一個或多個執行緒／邏輯單元。 | 換一個邏輯單元或 Python worker 物件，不等於換掉 host 或恢復其原生狀態。 |
| 執行緒（thread） | 同一 host 內的執行路徑，共用該程序的位址空間。 | 不是原生記憶體或致命崩潰的隔離邊界；一條 thread 出事可影響整個 host。 |
| 管理程序 | 負責實驗安排、輸入／執行關聯及管理端紀錄的程序角色，與求解 host 分開說明。 | D35 基線將兩者隔離；新候選的實體安排仍待確認，不由本表定案。 |
| worker | D35 舊多程序基線中，一個 Python worker 對應一個邏輯工作鏈及一個實體求解程序。候選若仍用 worker，須說清指哪一層。 | 不能跨拓撲一律寫「worker 是程序」，也不能保證替換它只影響一個 task。 |

D34 的「同步保存完才接下一題」約束同一條邏輯工作鏈：它不能在前題未保存完就接新題；不表示同 host 其他邏輯單元／threads 都要等這題保存。在沒有整場停止或其他不可信狀態時，其他單元仍可處理自己的工作。D29 的健康程序重用、每 task 私有 RNG／可變狀態，以及仍被使用的結果／共享資料不可提前釋放，均不變。

D36 的對應資訊須能辨識實際 task 與承載它的執行關聯，不能在同 host 多 task 時只知道程序、卻不知道通知屬於哪題；具體表示、映射及 IPC 格式仍待細化。D38 所述退出是實體程序退出事件；同 host 多題須逐 task 處理已交付通知及完整最終回報。已確認交付不因 host 退出撤銷，缺少完整回報者依已知事實記交付未確認；不靠掃檔補登，也不因此替未知退出定根因或處置。

D40 對普通 Python 保存錯誤的原則仍是保留原因與 task 對應，不自動重求解／重試；清理成功且環境可信才可重用，清理失敗或狀態不可信則不得再重用該不可信執行環境。原多程序基線可替換其 worker 程序；新拓撲的實體替換範圍與時機須列明、待使用者確認，不能只重開 thread／worker 物件就宣稱原生環境已恢復，也不能把普通保存錯誤一律改成算法錯誤全場停。D79–D80 的算法錯誤仍停止整場。

| 對照例子 | 影響與待確認界線 |
| --- | --- |
| 舊基線：一個 worker 程序承載一條邏輯工作鏈 | A 保存／交接及清理完畢、環境健康且整場未停止後，該鏈才接 B；D40 必要時替換這個程序，不自動重跑 A。 |
| 候選：同 host 以 2／4 threads 承載工作鏈，A 正在同步保存 | A 的鏈不能先接下一題；其他鏈不因 A 正在保存就一律停等。這不授權它們在整場停止或環境不可信時繼續，也不固定鏈與 thread 的永久對應。 |
| 候選：清理失敗後立即退休實體 host | [19](19_architecture_candidate_experiments.md) 的控制例中，若其餘 1／3 題尚未交付，會連帶失去；已交付結果仍有效。不是只替換出錯 task，也不是只重開一條 thread 即可恢復。 |
| 另一候選：已知健康同伴先完成，再退休 host | 19 已測但未選；沒有等待上界，不可套到未知 heap corruption。與立即退休是競爭提案，兩者的時機、影響及 D40 映射都待確認。 |

本節不選新拓撲、退休策略、未知退出政策或錯誤留因時序。原型可行不等於正式隔離／清理驗收。

## 一、這次新增的核心需求

使用者明確要求：

> task 發生非預期情況時，實驗模組要記下它收到的工作與實際輸入，讓研究者之後能單獨重跑這個 task，找出問題。

重點是「知道哪份工作未正常完成，並能重建同一份工作」，不是要求 Python 找出 C++ 哪一行出錯。

這屬於實驗管理的任務追蹤與保存責任，不是實驗側重新計算 objective／constraints；也不是要求從算法中間狀態繼續執行。

後續使用者進一步確認：求解異常只需讓 Python 知道工作未正常完成並保留實際輸入；Python 寫檔異常則須保留失敗原因。2026-10-24 的 D79–D80 已將算法錯誤分支改為停止整場；不自動重跑，Python 保存錯誤依 D40，不把兩者混為同一種錯誤。

## 二、不變的既有決定

- 一個 task 仍是一題、一算法、一組參數、一個 seed 的完整求解。
- 傳統問題的搜尋、objective、constraints、最終數學驗證留在 C++。
- 全部實際 addAct 紀錄在求解任務內保存，完成與驗證後一次交付；D18 的完整返回 Python 邊界仍是有效舊保存基線。
- 文件保存屬實驗／輸出責任，Python 是舊保存基線的輸出語言；候選語言、返回及所有權差異依 [07](07_history_return_and_storage.md#已確認交付需求與保存基線) 列出待確認，不加入分批、背景 writer 或 Redis。
- 任務正常完成但最終解不可行，不算這裡的執行異常。

保存失敗任務輸入，不會更動以上邊界。

### 已確認的程序生命週期（D27–D29）

- 算法錯誤停止整場，其他正在運行算法與 task 也在停止範圍；不再啟動新 task，不自動重跑，已保存結果保留（D79–D80）。
- 正常運行時重用健康求解程序；同一邏輯工作鏈完成同步保存、交接及清理且整場未停止後，才接新 task，不每題重開環境；層級依 [名詞表](#執行名詞與替換範圍)。
- 每題依自己的有效輸入及 seed 初始化 RNG、算法狀態、工作空間與歷史，不能延續上一題的搜尋進度、世代計數或亂數序列。
- 算法錯誤即使已捕捉也觸發整場停止（D39、D79–D80）。Python 保存錯誤依 D40，清理成功且環境可信才重用，否則不再使用該不可信環境；舊基線替換程序，新拓撲的範圍／時機依 [上述對照](#執行名詞與替換範圍) 待確認。未知退出及停止收尾仍待細化。
- 結果及歷史若仍被接收／保存方使用，不得提前釋放或覆寫。正式採複製、移交所有權或保留有效持有者，仍待資料交接議題決定。
- 本版不加入卡住後自動超時中止；一直未完成、但沒有明確錯誤或程序終止的工作，暫由研究者人工處理。不能只因等很久就自動標成求解失敗；這也不更動算法自己的正常停止條件。

這些 D27–D29 決定生命週期，沒有批准跨任務共用一份可變算法緩存。程序重用證據見 [16](16_process_lifecycle_experiment.md)；後續 D35 的呼叫選型另見下一節及 [17](17_invocation_comparison_experiment.md)。

## 三、歷史比較基線：A｜同程序 C++ 擴充模組

### 既有方案與本輪調整（D30–D35、D79–D80）

以下是 D35 當時選定、現在重新評估的完整方案；後續依 [架構狀態與比較維度](#架構狀態與比較維度) 拆開比較，不因算法錯誤停止政策改變就自動搬移排程或採用多執行緒。

```text
Python 實驗主程序
  → 隔離的 Python worker
      → 同一程序內的 C++ 完整求解入口
      → C++ 完成求解與最終驗證，一次交回完整結果及全部歷史
      → Python worker 呼叫共用輸出器，同步保存該題
      → 主程序只接收摘要與檔案位置
      → 本題資料按生命週期清理後，整場未停止時健康 worker 接下一題
```

既有方案即使只同時跑一題，也將載入 C++ 的求解 worker 與主程序隔離；候選研究見 [19](19_architecture_candidate_experiments.md)，正式方案仍須核對故障記錄能力，本節不代表已決定將呼叫搬入主程序。結果仍被保存方使用時，不得提前釋放或覆寫；上述流程不是正式完成通知／回收協議。

- **平台（D30）**：首版 Linux／WSL，不以原生 Windows 作本版驗收；C++ 核心避免不必要的平台耦合。
- **人工停止（D31）**：不內建單 task 停止命令；研究者使用外部工具處理後，系統依已觀察事實記錄。退出分類及後續處置依既有政策與待議架構細化，不預設自動重跑或中途恢復，也不新增自動超時。
- **呼叫粒度（D32）**：Python 正式 API 只需完整求解及結果，不要求公開 C++ 算法物件或逐步操作函數。逐模組測試仍須做，可在原生測試或 oracle 完成。
- **重跑（D33）**：透過 Python 命令單獨從頭重跑即可，不要求 Python-free 的原生入口；依 D48–D49 由人查閱保存輸入、維護或重建指定設定，不由命令自動載入歷史值。一般入口與固定設定依 D65–D67，輸入保存格式及正式交接仍待細化。
- **保存（D34）**：worker 同步保存完本題才接下一題，主程序只收摘要／路徑。文件 I/O 屬實驗／輸出責任；此流程沿用 Python 輸出器舊基線，C++ 獨立輸出候選與 D18 邊界差異依 07 待確認，不由算法或 addAct 寫檔。
- **錯誤範圍（D35、D79–D80）**：原生崩潰可連帶終止 Python worker；算法錯誤改為停止整場，不再以其他工作不中斷作選型硬限制。已保存結果與已知事實須保留，安全收尾機制尚未選定。

控制原型透過 pybind11 執行；C++ 仍是編譯後的原生運算，不是轉成 Python 迴圈。正式入口名稱、binding／建置細節、資料型別與所有權仍待定；採擴充模組不等於自動零複製。C++ 核心與 Python 接線應分開，算法內部不依賴 Python 型別。

正常時重用健康程序，每題狀態獨立；算法錯誤發生後停止整場，不再要求換 worker 後接新 task。D36–D38 的實際對應與通知原則保留於既有方案，D40 的保存錯誤政策不擴大。現有程序池連帶報錯不能代替原因分類、保存已知事實及安全停止的正式驗證。

### 當時比較未採用：B｜獨立 C++ 求解程序

B 可由 Python 呼叫者啟動可重用的 C++ 子程序。C++ 崩潰時，Python 呼叫者通常仍存活；但需要程序間輸入／輸出與結果生命週期協議，並非只有寫 JSON 文件一種做法。

本輪配合 worker 保存路徑，另比較了「Python worker＋獨立 C++」的管線複製與共享記憶體配置。共享記憶體配置可避免兩邊各持有完整結果，不能把複製版本的成本當成獨立程序的必然成本；也不能用這個特定拓撲概括所有 B 設計。當時 B 與 A 都依同樣的程序重用、輸入保留及單工作故障隔離要求測量；這是歷史條件，不是 D79–D80 的停止驗收。

B 的額外隔離可讓 Python 呼叫者在 C++ 終止後仍存活；當時需求允許替換 worker，不要求這項保障或脫離 Python 重跑，因此看過對照後選 A。這是歷史選型依據，不代表 B 必定較慢，也不取代依三個維度重新評估架構組合。

### 決策沿革與證據

先前以「符合現有 worker 流程」或「較早驗證完整契約」優先 A 的理由仍然撤回，不作這次選型依據。程序生命週期實驗使用獨立執行檔，也沒有自行選定 B；舊核心未清理好的記憶體增長不作選型理由。

後續先確認 D30–D34，再做同一 C++ 合成工作、同一 Python 保存函數的對照；完整內容、RNG、例外、寫檔錯誤及八 worker 中的單程序終止均有控制證據。使用者據此確認 D35，詳見 [17 呼叫方式對照](17_invocation_comparison_experiment.md)。這不是宣稱正式算法、任意外部結構、資料交接及整套恢復流程已驗收。

## 四、錯誤類型、故障隔離與恢復策略要分開

| 情境 | 程序可能發生什麼 | 不可混淆的地方 |
| --- | --- | --- |
| 非預期 C++ 例外可被轉換、捕捉 | worker 可能仍存活，不等於原生崩潰。 | C++ 算法非預期錯誤依 D39、D79–D80 保存輸入與已知錯誤、停止整場；輸入預檢及正常不可行不混入。 |
| A 中的 C++ 非法記憶體存取等原生崩潰 | 該 Python worker 可能直接終止，不能再接新工作。 | 不是只把當前函數當成失敗後，原程序照常繼續。 |
| B 中的 C++ 子程序非預期終止 | Python 呼叫者通常仍可觀察到子程序未正常結束。 | 已知為算法錯誤時記錄並觸發整場停止；僅有未知退出則保留已知事實，原因判定與處置待議，不自動重跑。 |
| Python 輸出軟體流程出錯 | 可能可捕捉例外，求解已完成但保存未完成。 | D40 留原因與 task 對應；清理成功且環境可信才重用，否則不再使用該不可信環境。候選的實體替換範圍／時機依 [名詞表](#執行名詞與替換範圍) 待確認，不一律全場停。 |

磁碟滿、磁碟故障等硬體／資源層異常不納入本版專用恢復或錯誤留存保證，亦不以相同磁碟的另一個資料夾宣稱完成跨媒介備援。

候選 C++ 輸出元件的例外須按業務階段分類，不能僅因例外來自 C++ 就當成算法錯誤停整場；相對 D25／D40 的錯誤映射差異依 [07](07_history_return_and_storage.md#已確認交付需求與保存基線) 列出待確認，不自動改動現行 Python 保存政策。

已確認的原則與待設計的機制要分開：

1. **執行架構**：D35 曾選定的方案是重新評估基線；依 [三個比較維度](#架構狀態與比較維度) 檢查各種組合，仍需保留可取得的輸入及故障記錄能力，不以程序邊界本身代替驗證。
2. **停止／恢復策略**：算法錯誤依 D79–D80 停止整場；Python 保存錯誤依 D40，不自動重試。停止時點、安全收尾與未知退出判定仍待設計，不是語言或整池關閉自動保證。
3. **診斷與重跑**：保存哪些輸入及已知異常資訊，供人工調查。

最新 D79–D80 取代先前算法錯誤後其他工作必須繼續的策略；算法錯誤停止整場，但不自動重跑。不能遺漏異常紀錄，亦不能把每個因連帶停止而報錯的 task 都當成算法自身崩潰。實際執行對應與交付未確認按 D36–D38 記錄；具體保存格式與通訊機制仍待細化。

Python 算法也需要這套任務追蹤與錯誤保存。純 Python 的一般錯誤通常較容易以例外定位，但原生依賴（例如 NumPy／Numba）崩潰仍可能使 worker 死亡；不能把這項責任視為只有 C++ 才需要，也不能因觀察到 worker 消失就斷言根因。

## 五、現有專案的實際影響範圍

以下是依目前程式推導「若接入原生 C++」的影響，不表示正式 C++ 模組已存在或目前派工流程已通過原生崩潰測試；另做的臨時對照見 [16](16_process_lifecycle_experiment.md) 與 [17](17_invocation_comparison_experiment.md)。

- [machine/core.py](../../../machine/core.py) 的單 worker 路徑直接執行 `machine.run()`，沒有獨立求解 worker；若在此程序直接載入 C++，原生崩潰可能使實驗主程序一起終止。
- 多 worker 使用 `ProcessPoolExecutor`；收到任務例外後，現有程式會取消能取消的未完成工作、關閉程序池並向外拋錯，不會自動補 worker 繼續整場實驗。
- worker 突然死亡可使程序池成為 `BrokenProcessPool`，原程序池不能繼續接新工作。重建程序池是建立新的執行環境，不是把死亡程序復活。
- 目前有 `future → task` 對應及 `_add_task_context_note()`，但程序池整體失效時，多個 future 可能一起報錯；不能只看第一個報錯 future，就認定它是造成崩潰的 task。
- [cli/run/support.py](../../../cli/run/support.py) 通常等整批完成才寫正式結果；目前不保證已算完的任務或終端錯誤訊息已永久保存。

既有候選方案選擇主程序與載入 C++ 的 Python worker 隔離；本輪未改程式或決定新拓撲。實際執行追蹤、退出觀察及通知未達的政策已由 D36–D40 確認，正式機制仍待細化／驗收，不能把政策定案當成程式已實作。

RNG 隔離與程序池是否連帶中止是兩件事。目前 `Machine.expand_tasks()` 在分派前決定各 task 的 seed；`_run_task_process()` 每題建立自己的 RNG，CDELS 也依本次 seed 建立自己的 MSVC 相容 RNG。失敗工作多抽亂數，不代表其他工作會共用或接續那份亂數狀態。這不等於所有算法都已完成重現性驗證；新 C++ 任務也必須遵守每題狀態隔離，固定迭代時再核對其他工作初始化、過程與結果不變。

## 六、失敗任務至少要能重建哪些輸入

| 資訊 | 保存目的 | 限制 |
| --- | --- | --- |
| task 與實驗關聯 | 找出哪份工作未正常完成。 | 正式 ID 格式未定。 |
| 問題類型、題目與實際數值 | 重建當時求解的同一道題。 | 不能只保留之後可能改變的來源路徑。 |
| 算法選擇與完整有效參數 | 重建本次真正使用的搜尋設定。 | 依 D50 保存明列的實際數值，不自動補預設值，也不能只保存參數組索引。 |
| seed 與相關初始化輸入 | 從相同起點重新開始。 | 若算法允許額外初始解等輸入，也必須保留。 |
| 群組停止設定、紀錄設定與其他 task 選項 | 避免重跑時不小心改成不同工作。 | 保存主要方式／數值、達標開關及無改善輪數，含明列的 false 或 null；固定迭代與按時間停止不是相同重現保證。 |
| 執行關聯與已知異常資訊 | 知道哪個執行單元在處理它，以及如何未正常結束。 | 不強制一定能取得原生 C++ 堆疊或根因。 |

大份題目數據可保存一次，各 task 引用同一份保存內容，不要求每次複製。共享記憶體名稱、暫時指標或會消失的暫存位置，不能單獨充當日後重跑的問題數值來源。

具體檔案格式、索引、保存期限及正式回報協議尚未決定；本輪不強制加入一套版本／digest／資料庫或完整環境快照系統。

依 D48–D49，以上紀錄責任不等於重跑必須自動從紀錄取值。研究者可查閱紀錄，人工維護或重建指定設定；正式執行仍讀這次設定指定的檔案。設定已改時，記錄新實際值，不以歷史差異自動拒絕或恢復舊值，也不改寫原紀錄。

D50–D64 進一步確認：算法參數明寫，停止設定由群組唯一提供，C++ 正常執行；初始化不計迭代，可指定 0 次只初始化，達標於初始化後及整輪後檢查，另可啟用連續無改善停止。不支援選定方式、零次用途或已啟用選項，或開啟達標卻缺少目標時，啟動前報錯、整場不啟動。時間判斷可能因完成當前整輪而超過秒數，不是卡住後強制中止。D47 不把停止設定加入判重鍵；停止子欄位、計數規則及 21 項模型限制見 [18](18_experiment_configuration_and_task_expansion.md)。正式 C++ 支援查詢與多條件結果表示仍待對應單元，不在本章補定。

## 七、已確認的主程序派工與通知（D36–D40）

下列沿用舊 Python 保存基線敘述已確認的控制通知；輸出器語言、完整資料進入 Python 的方式或交付邊界改變，須依 [07](07_history_return_and_storage.md#已確認交付需求與保存基線) 列差異待確認，不在此先定候選的替代協議。

### 主程序先保留，再指定一題（D36）

管理端在派工前保留實際輸入與 task 的執行關聯，再向可用邏輯執行單元指派一題；D35 基線中就是一個 Python worker 程序。每條工作鏈同時只負責一題，完成同步保存、交接與清理，且環境可信、整場未停止後才接下一題，不自行取走未登記的工作。需替換時按 [D40 作用範圍](#執行名詞與替換範圍) 處理；不能在新拓撲未確認實體影響前，假設換一個 worker 物件便可接新題。

管理端等待 worker 訊息及程序退出事件，有事發生才處理，不用迴圈反覆掃描所有 worker。這是事件驅動方向，不在本單元指定 IPC 工具、檔案格式或監督器實作，也不新增自動超時。

### 兩種階段通知不代替最終回報（D37）

| 收到的通知 | 管理端可以記錄 | 不能推論 |
| --- | --- | --- |
| worker 已接收任務 | 該 worker 已接收被指派的 task。 | 不代表 C++ 已開始或已完成。 |
| C++ 已正常返回 | 該 task 的 C++ 呼叫已正常返回 worker。 | 不代表 Python 已保存完成、主程序已收到最終結果，亦不代替結果中的可行性。 |
| 完整成功最終回報 | worker 回報保存完成，交付該題的摘要與檔案位置。 | 不代表該 worker 之後不會退出；不要求主程序重新做數學驗證或讀檔驗收。 |
| 完整錯誤最終回報 | 回報中實際已知的錯誤、task 對應及可取得原因。 | 不將未知階段或 C++ 根因補成確定事實。 |

只記實際收到的事實。沒收到某種階段通知，不代表該階段沒發生；也不因缺少前一階段通知推翻完整最終回報。但收到保存錯誤通知，不自動證明原因已持久保存、事後可查；D25 強需求及未定留存時點依 [15](15_task_failures_and_result_storage.md#保存錯誤原因的留存界線)，D38 不替代留因機制。正式訊息欄位／順序仍待細化，本表不是 wire schema。

正常路徑為：

```text
主程序保留輸入與 worker／task 對應，再指派一題
  → worker 通知「已接收任務」
  → C++ 完整求解、最終驗證，一次返回結果及全部歷史
  → worker 通知「C++ 已正常返回」
  → Python worker 同步保存本題
  → worker 交付完整最終回報，主程序只收摘要與檔案位置
  → 正確清理，整場未停止時健康 worker 才接下一個新 task
```

這些是任務邊界上的小型控制通知，不是逐代回呼 Python，不攜帶全部歷史，不要求 addAct 寫檔或讓 C++ 分批返回。

### task 結果與執行環境健康分開（D38–D40）

- 觀察到實體求解程序退出時，先按執行關聯處理其各 task 已交付的通知，再逐題判定是否缺少完整最終回報；D35 基線是一個 worker 程序。不能因先看到 host 退出就忽略已交付回報。
- 沒有完整最終回報：記「交付未確認」，保留輸入、現有文件及最後已知事實；不自動掃檔、讀完成記錄、補登成功或重跑。
- 已收到完整成功回報：該題已確認交付；host 後續退出影響執行環境，不把該題改成失敗。同 host 其他題另按各自回報判定。
- 已收到完整錯誤回報：保留該 task 已知的錯誤與原因；host 後續退出不把它降回只有「交付未確認」，同 host 其他題另判。
- 非預期 C++ 算法錯誤：即使已捕捉而程序仍在，也保存可取得錯誤與輸入，停止整場（D39、D79–D80）。正常不可行、輸入預檢及 Python 保存錯誤不因此混入算法錯誤。
- Python 保存錯誤：留原因與 task 對應；清理成功且環境可信才重用，否則不再重用該不可信環境。舊基線可替換程序，新拓撲按 [名詞表與例子](#執行名詞與替換範圍) 確認實體範圍／時機（D40），不默選立即或排空後退休。清理不刪既有／部分結果，不自動重試保存。

完整 [十個事件案例](15_task_failures_and_result_storage.md#十個事件案例) 已按新政策改寫預期，另有 [七個算法錯誤停止情境](15_task_failures_and_result_storage.md#算法錯誤停止整場情境核對)。舊事件推演與 D79–D80 確認時的文件核對不是正式驗收；其後 [19](19_architecture_candidate_experiments.md) 雖有故障候選實測，正式通訊與安全停止仍待確認、整合及驗證，不默默重派失敗工作。

本節沒有選定正式通訊格式、狀態保存格式、資料所有權或監督機制。異常輸入保存也不能與較晚處理的「整場重啟後自動跳過完成任務」混成同一個延後功能。

## 八、保存異常資訊，不等於一定知道 C++ 根因

最低目標是能記錄：

> 這份 task 收到以下輸入，執行過程未正常完成；當時能取得的錯誤資訊如下。

求解異常若能取得例外訊息、標準錯誤輸出或退出狀態，可作輔助資訊，但不把 C++ 根因／完整堆疊當必要回報。Python 的一般 traceback 不等於完整原生 C++ 堆疊；`BrokenProcessPool` 本身也未必指出真正出事的 task 或原因。

Python 軟體保存失敗不同：實際原因與 task 必須事後可查，不能套用「不需要 C++ 根因」而省略或只記失敗。產生原因、通知及持久保存不同，正式誰／何時／何處保存及完成判定未定；通知截斷、錯誤紀錄再失敗或留存前退出的界線依 [15 權威小節](15_task_failures_and_result_storage.md#保存錯誤原因的留存界線)，不降成最佳努力、不默選 worker-first artifact，也不宣稱任意 kill／原生損壞都保證。

實體 host 退出後按 D38 逐 task 處理已交付回報；缺完整回報就保留其輸入、文件及已知事實，不讀檔補登／重試，同 host 已交付題目不撤銷。錯誤 artifact 存在不等於結果成功交付，也不能刪文件假裝從未保存。這些紀錄原則不免除 D25；D40 替換與算法錯誤停止政策不變。

開發期可考慮帶除錯資訊的建置、faulthandler、AddressSanitizer 等，但不是已選好的正式診斷方案，也不保證所有非預期終止都能留下完整線索。

若只是因其他 worker 出事而被中斷，應和「已確認在該 worker 執行時非預期終止」區分；不能把所有受影響 task 都記成算法自身崩潰。具體狀態名稱待定。

## 九、日後如何單獨重跑

目標操作是「實驗人員選定題目、算法參數組與 seed，必要時查閱原輸入紀錄人工重建設定 → 讀取實驗設定指定的檔案 → 呼叫單任務求解入口 → 從頭再跑一次」，不需要重跑整個題庫或所有 seed。

D33 已確認透過 Python 命令完成即可，不要求 Python-free 的原生重跑入口。D65–D67 已定從專案根目錄執行 .venv/bin/python -m mkp.cli.run，固定讀 cli/run/run_cfg.yaml；研究者將該檔改成只包含要重跑的配對，不另加歷史 task 選取命令。現有入口尚未改成此讀檔流程，本文件的命令是目標操作，不是宣稱現在已可如此重跑。

D41–D47 補入 [一般實驗設定與 task 展開](18_experiment_configuration_and_task_expansion.md)：整批實驗與指定配對重跑使用同一種 YAML 安排格式，不另設原 task 編號選取格式。可用不同組綁定要重跑的題目、算法參數組及 seeds，不重新把兩份獨立題目／seed 清單交叉展開。D48–D49 已選讀指定檔案，不自動引用歷史副本；不同原實驗的失敗 task 可彙整在同一份設定，不按原實驗拆開，也不新增歷史來源欄位。重複檢查限本次設定，不跨歷史實驗阻擋人工重跑。

題目數值、有效算法參數、停止條件及其他初始化輸入是否仍與原 task 一致，由實驗人員維護。只對上題名、參數索引與 seed，不代表系統已認證數值一致；即使固定 seed 與迭代數，重現仍以實際輸入一致及適當的確定性執行條件為前提。基本預檢、D46–D47 與求解任務最終數學驗證不取消。四種讀取情境見 [18](18_experiment_configuration_and_task_expansion.md#四種重跑讀取情境核對)。

需要盡量使用相同算法實作與執行條件；程式、依賴、硬體、執行緒或資料準備方式改變，都可能影響重現。是否記錄額外環境資訊留待細化，不以保存輸入就宣稱已封存全部環境。

**能重建同一份工作，不保證每次必定再次崩潰。**競態、未初始化記憶體、資源不足等情況可能不是每次都發生。

## 十、與 addAct、checkpoint、續跑的差別

| 功能 | 本輪定位 |
| --- | --- |
| 保存失敗 task 輸入 | 本輪必要需求；支持人工定位與單獨從頭重跑。 |
| 全部 addAct 歷史 | 正常完成後一次回傳；回傳前程序崩潰，尚在記憶體的歷史可能失去。 |
| 事後單 task 重跑 | 從保存的起始輸入重新執行，不恢復崩潰前進度。 |
| 算法錯誤與保存錯誤分開處置 | D79–D80 算法錯誤停止整場，不自動重跑；Python 保存錯誤仍依 D40，正常不可行不阻擋。 |
| 整場實驗重啟後跳過完成 task | 後續持久化與續跑設計，不因本需求自動完成。 |
| 算法內 checkpoint | 仍不納入本版；addAct 不保證包含完整工作緩存與 RNG 狀態。 |

保存輸入與少量異常資訊，不等於改採逐代寫入完整求解歷史。算法及 addAct 不負責文件 I/O；C++ 獨立輸出元件仍可屬實驗／輸出責任，候選與 D18–D19／D34 的差異依 [07](07_history_return_and_storage.md#已確認交付需求與保存基線) 待確認。

## 十一、修改 C++ 後如何開發測試

既有 A 方案的開發流程需要編譯；以下 B 保留作比較說明，不是本輪新選型：

- A：修改 C++ → 重建擴充模組 → 在新測試程序載入並測試。
- B（當時未採用）：修改 C++ → 重建執行檔 → 啟動執行檔並測試。

兩者都可設計成一個命令完成必要的增量編譯與小型測試，不必每次重新部署整套系統；D32 不要求 Python 提供逐步算法 API，但不省略逐模組原生測試。增量建置也可能因共用標頭或依賴變更而重編多個檔案，不能承諾固定耗時。

不能因 B 要執行編譯好的程式，就認定算法開發完不能快速測試；A 也不是改完 `.cpp` 就自動讓已載入的 worker 使用新版本。如何避免測到舊產物，是原型應核對的事。

重用健康程序是同一版程式處理多個 task 的正常生命週期，不是要求修改 C++ 後仍沿用已載入舊產物的程序。開發測試須載入新建置產物，具體建置與重載命令另議。

原型驗收應包含：

1. 正常完整回傳；一般 C++ 例外和原生程序終止分開測。
2. 單求解 worker 和多 worker 都能保留必要的管理／診斷能力。
3. 程序池整體失效，不誤把第一個報錯 future 指定為真正元兇。
4. 任務失敗前已保留實際輸入，不依賴 C++ 成功返回。
5. 原始來源檔修改或 SHM 釋放後，實際輸入紀錄仍可查閱、供人工重建設定；不自動以紀錄取代本次指定檔案，不只留可變路徑或暫時 SHM 名稱。
6. 能只重跑一個 task；當人維護相同有效參數、seed、初始輸入與紀錄設定時，核對相應重現條件。指定檔案已變時，驗證讀取與記錄其實際值、不自動採用歷史值，不宣稱仍還原原 task。
7. 開發修改確實觸發必要重建，新測試不是跑舊模組／舊執行檔。
8. 分開量測編譯、啟動、輸入交接、搜尋／紀錄、完整回傳與 Python 保存成本。
9. 非預期算法例外及原生致命崩潰觸發整場停止，必要紀錄可查，不再啟動新 task；已保存結果不被清除，不自動重跑。
10. 保存原因與 task 事後可查，不只驗證通知有送到；先按 [15 留存界線](15_task_failures_and_result_storage.md#保存錯誤原因的留存界線) 確認正式機制及二次失敗／退出保障，再安排驗收。D38 不自動讀檔補登或重試、已交付不撤銷，artifact 不是結果交付；D26 硬體／資源排除不擴大。
11. 同一健康程序依序處理不同 seed／題目，再回到原題與 seed，初始化、過程、RNG 與結果不受前題污染；算法錯誤依 D39、D79–D80 停止整場；Python 保存例外依 D40 測清理成功／失敗。
12. 多算法同時執行時，一個發生算法錯誤就觸發整場停止，包括其他正在求解 task；不把連帶停止冒充算法自身錯誤。未知原因退出只記已知事實，判定與安全處置在架構細化後驗證。
13. Python 接收／保存方仍持有的結果不被下一題清理或覆寫；不以每題重開的 OS 回收掩蓋未完成的資料生命週期。
14. 將 [15 的十個事件案例](15_task_failures_and_result_storage.md#十個事件案例) 落實為正式訊息／退出交錯測試；算法錯誤須停止整場，Python 保存錯誤仍分清理成功／失敗，不能只測正常路徑或宣稱停止已可立即安全完成。
