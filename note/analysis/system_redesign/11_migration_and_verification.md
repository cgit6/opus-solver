# 11｜遷移順序與驗證關卡

狀態：小步驗證、固定迭代、健康程序重用、單 task 故障不影響健康工作，以及 D30–D40 的呼叫／保存／通知政策已確認；以下正式遷移順序仍是待批准草案，不因寫文件就開始執行。對應 D16、D21–D40、P08–P10。

## 設計和實作的順序

先用傳統問題與 AI 情境檢查共同責任，再集中做傳統問題；不是完全不想 AI，也不是先做一個涵蓋所有未來情境的大平台。

目前五項進度見 [總索引](README.md)。同程序擴充模組、worker 保存及 D36–D40 的 task 對應／通知／異常政策已定；下一單元預定討論固定問題數值如何交付與共享（Q3.2）。正式通訊／監督、狀態保存格式及所有權仍待細化，不跳過未定內容直接大規模移植。

## G0｜文件收斂

- 產出已確認決策、主題文件及待議清單。
- 對照現有入口，區分現況與目標。
- 已確認同程序擴充模組與 worker 同步保存；不能把原型 pybind11 版本、SHM、資料庫、背景寫入等都寫成正式規格。

停止點：使用者審閱分類與內容後再進下一單元。本次只更新文件與十個事件案例的規則核對，研究附件未更動；已做的控制實驗見 [16](16_process_lifecycle_experiment.md)、[17](17_invocation_comparison_experiment.md)，不能算作下列正式整合關卡已通過。

## G1｜單任務契約的最小測試

在選定的實作路線中，用少量人工案例檢查：

- 輸入能表達問題、算法、參數、seed、固定迭代與紀錄設定。
- 可行、不可行、輸入錯誤及核對失敗分開。
- 完整解可重建，不只是分數相同。
- addAct 外部參數為 nil 時不會壞。

是否先以既有 Python 任務包一層作契約原型，是可選遷移手段，不表示最終要維護 Python／C++ 兩套正式求解模組。

停止點：先報告小案例證據，不連帶修改算法內容。

## G2｜C++ 呼叫與資料最小原型

傳統題以一個小型案例測呼叫、輸入交接、錯誤與完整結果／歷史返回。SCVRP＋CDELS 可作候選，是否選它應在實作開始前確認。

本輪新增的重要驗收是：非預期結束時仍有可重建的實際輸入，能事後單獨從頭重跑 task。這須與呼叫原型一起驗證，不延至整場實驗自動續跑。單 worker 的隔離、程序池連帶錯誤與真正出事 task 的對應，見 [14](14_python_cpp_invocation_and_failure_replay.md)。

同時驗證單一 task 的軟體異常不終止整場：普通例外或原生終止後，必要時恢復執行單元，下一個新 task 能執行。不能只測 C++ 函數成功返回，也不能只捕捉 broken pool 的第一個 future 就宣稱已隔離根因。

D27–D29 已確定驗收方向：健康求解程序重用，每題 RNG、算法狀態與歷史獨立；一個 task 出錯只替換必要單元，其他正常 task 不取消、不重跑。同一程序在不同題目／seed 後回到原題／seed，也要符合初始化、過程與結果基準；結果仍被接收方引用時不得提前釋放。呼叫方向後續由 D35 選定，正式入口／所有權及跨任務工作緩存池仍未定。

D36–D40 的 [十個事件案例](15_task_failures_and_result_storage.md#十個事件案例) 只做記憶體內規則一致性推演，尚未測正式 IPC、退出時先處理已交付通知或真實恢復。正式 G2 須逐項落實：非預期 C++ 例外即使已捕捉也替換該 worker，Python 保存錯誤分清理成功／失敗，已收到的完整回報不被後續退出覆蓋；其他正常工作不取消、不重跑。

[16](16_process_lifecycle_experiment.md) 與 [17](17_invocation_comparison_experiment.md) 只提供前期控制證據；後者有已知尺寸 SHM 與合成資料的 Python 保存，不代表已接入正式算法、問題資料 SHM 或真實輸出器，不能宣稱 G2 完成。本版不把卡住後自動超時中止列為驗收項，這也不同於算法的正常停止條件。

需要量測：

- 啟動／載入成本。
- 問題資料準備、傳遞／複製及附接成本。
- 真正搜尋、紀錄與最終驗證耗時。
- C++ 轉 Python、worker 交付、序列化及文件保存耗時。
- 各階段記憶體尖峰。

不能用 C++ 只算搜尋的時間，直接對比 Python 從啟動到寫完報告的時間。Numba 若作比較，首次編譯與暖機後時間分開。

停止點：依已選的 D35 方向確認正式入口、必要資料契約與恢復／交付規則，小案例驗證後才擴大實作，不重選 A／B。

## G3｜一條完整傳統問題流程

先接通：

```text
Python 安排 task
  → C++ 問題／算法／狀態紀錄／最終驗證
  → 一次完整回傳
  → 該 Python worker 同步保存本題
  → 主程序接收摘要與檔案位置
```

既有 Python 與舊 C++ oracle 用於開發比對，不在正式熱路徑偷偷執行。

驗證至少包括相同題目數值、固定 seed 與固定迭代下：

1. 初始化編碼、適應值、必要容量及可行性相同。
2. 逐模組、逐階段、逐代的搜尋狀態相同。
3. RNG 類型、初始狀態、抽取次數與必要順序相同。
4. SA 判斷、溫度與終止步數相同。
5. 最終完整解、真實目標、可行性相同；legacy search score 另外對照。
6. 記錄開關不改變以上結果；舊快照不隨後續狀態覆寫。
7. Python 輸出格式、路徑或個別權限錯誤可留下原因與 task 對應，必要時恢復後繼續新 task；其他已保存結果保留。
8. 依 D34 測 worker 保存、主程序只收摘要與位置；保存完成但通知未達時，不偽造成功／失敗，按 D38 保留現況、記交付未確認，不自動核對文件、補登或重跑。
9. 同一健康程序反覆處理不同 task，前題的 RNG、世代計數、工作狀態或歷史不污染後題；下一題也不能覆寫仍被使用的前題結果。
10. 一個原生求解程序終止時，其他正常 task 的初始化、過程、RNG 與結果仍符合基準，沒有被取消或從頭重跑；只替換必要單元後繼續新工作。

若新舊文字狀態標籤不同，需定義相同邏輯時點的對照；不能只比較最後分數就宣稱過程 1:1。

停止點：小案例過關後才擴到代表題、更多 seed 與長迭代。使用者指定自行執行的全題長測，不擅自啟動。

磁碟滿、磁碟故障、跨媒介錯誤備援不列為本版驗收；單任務完整歷史 RAM 風險仍按既定範圍延後。異常案例、已選保存路徑、已確認通知政策及待細化機制見 [15](15_task_failures_and_result_storage.md)。

## G4｜實驗安排與統計遷移

在第四項規則確認後，測多問題／多題／參數組／seed 的任務展開、相容性與統計分組。

逐個調整既有入口，而非一次刪改 engine、machine、simulator、problem 與所有 solver。若 writer 會重設目錄，必須先確保不會刪除新保存資料。

停止點：驗證任務數、對應關係、成功／不可行／失敗／未確認及報告，再移下一個單元；異常後不漏派，也不默默自動重試原 task。

## G5｜後續能力

等核心路徑穩定，再分別討論：

- 整場重啟後辨識／跳過已完成任務；核心路徑必要的單次保存與交付確認不能全部延後。
- 整場中斷後自動辨識未完成任務並從頭重跑；不恢復算法中間狀態。人工單 task 診斷重跑與輸入保存已屬 G2 需求。
- 完整歷史的記憶體改善。
- 新問題、新算法與 AI 評估整合。
- 目錄整理、舊設定遷移與確認不用的程式淘汰。
- Legacy bug 修正版與算法優化，各建立可辨識 baseline。

完整 addAct 歷史不是可恢復 checkpoint；不能沿用先前「每 60 秒保存全算法＋RNG 中間狀態」的提案當作這次義務。

## 每個小單元的工作紀律

- 修改前先保存／定位要比對的基線與範圍。
- 只動該單元，不混入修 bug、換 RNG 或改數學定義。
- 執行針對性測試，檢查證據後才做下一單元。
- 初始／過程／結果或效能量測有差異時，先定位，不用最終分數巧合相同帶過。
- 有明確審閱停止點就停下；不得因前一項通過而自動執行後續全部工作。
