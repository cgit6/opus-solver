目前七個討論單元進度見 [總索引](README.md)。第 1／2／4 單元已有 [19 的候選證據](19_architecture_candidate_experiments.md)，未選型；第 3 單元設定政策已定，正式 API、預處理／求解交付與 schema 待細化；第 5／6／7 單元仍待討論。D41–D78 的已定規則保留，不自動切換架構，不跳過未定內容大規模移植。下列 G0–G5 是未來正式實作驗收關卡；研究資料夾的 gate1／gate2 只是當時批次名稱，不等於此處 G1／G2。

## G1｜單任務契約的最小測試

在選定的實作路線中，用少量人工案例檢查：

- 輸入能表達問題、算法、參數、seed、固定迭代與紀錄設定。
- 可行、不可行、輸入錯誤及核對失敗分開。
- 完整解可重建，不只是分數相同。
- addAct 外部參數為 nil 時不會壞。

是否先以既有 Python 任務包一層作契約原型，是可選遷移手段，不表示最終要維護 Python／C++ 兩套正式求解模組。

停止點：先報告小案例證據，不連帶修改算法內容。

## G2｜C++ 呼叫與資料最小原型

傳統題以一個小型案例測呼叫、輸入交接、錯誤與完整結果／歷史返回。SCVRP＋CDELS 可作候選，是否選它應在實作開始前確認。

已確認的重要驗收是：非預期結束時仍有實際輸入紀錄供追查／人工重建，能事後從頭單獨重跑 task；依 D48–D49 讀指定檔案，由人維護一致，不自動用歷史值替換。這須與呼叫原型一起驗證，不延至整場續跑。邏輯單元、實體 host／thread、程序隔離與 task 執行關聯依 [14 名詞表](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍) 核對，不能把 thread／worker 物件當隔離程序。

須驗證算法錯誤停止整場：可捕捉錯誤與原生致命崩潰都不再派新 task，包含其他算法及正在求解的 task；已保存結果保留，不自動重跑。不能把 broken pool 第一個報錯 future 當根因，也不能把連帶中止冒充成功或算法自身錯誤。

D27–D29 的有效方向依 D79–D80 更新：正常運行重用健康程序，每題 RNG、算法狀態與歷史獨立；算法錯誤停止整場，不要求只換單元後繼續。同一程序在不同題目／seed 後回到原題／seed，也要符合初始化、過程與結果基準；結果仍被接收方引用時不得提前釋放。D35 曾選定的完整方案現在是比較基線，依 [14 的比較維度](14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度) 重新評估，正式入口／所有權與工作緩存池仍未定。

[十個事件案例](15_task_failures_and_result_storage.md#十個事件案例) 的歷史模型測的是舊隔離政策；本輪已改寫預期，不能宣稱舊推演驗證 D79–D80。正式 G2 須落實：可捕捉算法錯誤也停止整場，Python 保存錯誤仍分清理成功／失敗，完整回報不被後續退出覆蓋。停止時點、安全收尾及未知退出判定須先細化再驗證，不承諾立即安全中止。

[16](16_process_lifecycle_experiment.md) 與 [17](17_invocation_comparison_experiment.md) 只提供前期控制證據；後者有已知尺寸 SHM 與合成資料的 Python 保存，不代表已接入正式算法、問題資料 SHM 或真實輸出器，不能宣稱 G2 完成。本版不把卡住後自動超時中止列為驗收項，這也不同於算法的正常停止條件。

[19](19_architecture_candidate_experiments.md) 新增正常／故障／效能候選控制、真 CDELS fresh-process oracle 對照與共享可行性探針；沒有正式 solver／scheduler／IPC／所有權整合，不能據此宣稱 G2 或 G3 完成，更不能宣稱真 CDELS threaded port 已驗收。cleanup 退休與 worker-first 留因仍是未定提案。

需要量測：

- 啟動／載入成本。
- 問題資料準備、傳遞／複製及附接成本。
- 真正搜尋、紀錄與最終驗證耗時。
- 完整交接（舊保存基線含 C++ 轉 Python）、worker 交付、序列化及文件保存耗時。
- 各階段記憶體尖峰。

不能用 C++ 只算搜尋的時間，直接對比 Python 從啟動到寫完報告的時間。Numba 若作比較，首次編譯與暖機後時間分開。

停止點：依候選證據確認架構差異與方案，再細化正式入口、資料契約、停止／交付規則；小案例正式驗證後才擴大，不把已做候選比較當成這道驗收已過。

## G3｜一條完整傳統問題流程

以下沿用舊 Python 保存基線；候選若改輸出器語言、完整歷史轉入 Python 的方式或返回邊界，須先依 [07](07_history_return_and_storage.md#已確認交付需求與保存基線) 列差異待確認，再安排驗收。D34 同步保存位置及主管只收摘要／路徑不變。

```text
Python 安排 task
  → C++ 問題／算法／狀態紀錄／最終驗證
  → 一次完整回傳
  → 該 Python worker 同步保存本題
  → 主程序接收摘要與檔案位置
```

既有 Python 與舊 C++ oracle 用於開發比對，不在正式熱路徑偷偷執行。

驗證至少包括相同題目數值、固定 seed 與固定迭代下：

1. 初始化編碼、適應值、必要容量及可行性相同。
2. 逐模組、逐階段、逐代的搜尋狀態相同。
3. RNG 類型、初始狀態、抽取次數與必要順序相同。
4. SA 判斷、溫度與終止步數相同。
5. 最終完整解、真實目標、可行性相同；legacy search score 另外對照。
6. 記錄開關不改變以上結果；舊快照不隨後續狀態覆寫。
7. Python 輸出格式、路徑或個別權限錯誤留下原因與 task 對應；D40 清理成功且可信才重用，否則不再用不可信環境。先確認新拓撲的替換範圍／時機與同 host 同伴影響，再驗收，不能只重開 thread／物件當恢復，也不把普通保存錯誤全場停。
8. 依 D34 測同鏈同步保存／交接及清理後才接新題、主程序只收摘要／位置；不強迫同 host 所有鏈等保存。實體 host 退出按 D38 逐 task 處理已交付通知／完整回報，不撤銷已交付，缺回報者未確認，不掃檔補登或重跑。
9. 同一健康程序反覆處理不同 task，前題的 RNG、世代計數、工作狀態或歷史不污染後題；下一題也不能覆寫仍被使用的前題結果。
10. 算法錯誤觸發整場停止，包含其他算法；不啟動新 task，不自動重跑。保留已交付結果，未知退出、連帶停止與算法自身錯誤分開記錄；安全停止及清理在選定架構後驗證。

上述邏輯鏈不預設永久綁 thread／程序，不增正式識別欄位。D40 在舊多程序基線可替換程序；新拓撲須先依 [14 的例子](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍) 確認實體範圍、連帶影響與時機，再安排驗收。立即退休或先完成健康同伴仍是 [19](19_architecture_candidate_experiments.md) 已測未選提案，不因列入清單就默選。

保存原因的正式驗收不能只測「通知成功」：D25 要求原因與 task 事後可查；正式誰／何時／何處保存、完成判定及二次失敗／退出保障須先依 [15 留存界線](15_task_failures_and_result_storage.md#保存錯誤原因的留存界線) 確認，再安排對應測試。該節六種情境目前只是文件靜態核對，19 的 artifact 候選只支持特定 TypeError 加通知截斷，不代表任意 kill、錯誤紀錄本身再失敗或原生損壞已驗收。D38 不掃檔／補登／重試，D26 硬體／資源排除不擴大，D40／D79–D80 不變。

若新舊文字狀態標籤不同，需定義相同邏輯時點的對照；不能只比較最後分數就宣稱過程 1:1。

D58–D64 不授權為統一計數而更改算法索引、公式、運算子或 RNG 順序。但新政策把達標檢查移至初始化後／整輪後，可能與舊算法個體更新後就停的時點不同。對照須使用可比的實際更新輪數與停止設定；舊 oracle 若無對應方式，先定位、說明或建立可比較的開發基準，不能以最終分數巧合相同宣稱軌跡一致。這是後續驗收要求，不是在本輪修改算法。

停止點：小案例過關後才擴到代表題、更多 seed 與長迭代。使用者指定自行執行的全題長測，不擅自啟動。

磁碟滿、磁碟故障、跨媒介錯誤備援不列為本版驗收；單任務完整歷史 RAM 風險仍按既定範圍延後。異常案例、已選保存路徑、已確認通知政策及待細化機制見 [15](15_task_failures_and_result_storage.md)。

## G4｜實驗安排與統計遷移

任務展開依已確認的 D41–D47 測試；算法支援查詢與統計分組仍須依各自細化後的契約驗收。一般入口採 YAML、精確配對與一般批次同格式、組內 seeds 取代全場值、不跨組配對、all 展開、參數組實際值保存，以及不支援／重複時整場不啟動，都需落實為正式測試。

[18](18_experiment_configuration_and_task_expansion.md) 的 80／2／122 筆推演只支持設定語意，不能當作正式讀取器、C++ 支援查詢、完整重跑或統計已完成。cli/exp 的 seed 收集用途不得隨一般入口重構被移除。另依 D48–D49 驗證讀指定參數與題庫檔案、記錄實際值、歷史紀錄保留；指定檔案已改時，不因歷史差異自動拒絕或恢復舊值。重現仍須人維護實際輸入一致，不把記錄供人工重建誤作自動恢復驗收。

D50–D64 的正式驗收須在後續整合時另做：參數不補值、群組唯一提供停止設定、型別／衝突與不支援預檢、零次初始化、整輪計數及時間／達標檢查、無改善旗標與獨立計數。須測本輪門檻前有改善時歸零、同分及單純重啟不歸零、重啟確有改善才歸零，並驗證停止判斷不額外 evaluate 或消耗 RNG。D47 的判重、D57 的原始目標達標比較及 addAct 責任不變。T01–T21 只是獨立候選模型，不是上述實作驗收；多條件結果表示仍留對應單元，不先定原因優先順序。

逐個調整既有入口，而非一次刪改 engine、machine、simulator、problem 與所有 solver。若 writer 會重設目錄，必須先確保不會刪除新保存資料。

停止點：驗證任務數、對應關係、成功／不可行／失敗／未確認及報告，再移下一個單元；算法錯誤後不再派工，也不默默自動重試；保留未啟動與連帶停止的真實範圍。

## G5｜後續能力

等核心路徑穩定，再分別討論：

- 整場重啟後辨識／跳過已完成任務；核心路徑必要的單次保存與交付確認不能全部延後。
- 整場中斷後自動辨識未完成任務並從頭重跑；不恢復算法中間狀態。人工單 task 診斷重跑與輸入保存已屬 G2 需求。
- 完整歷史的記憶體改善。
- 新問題、新算法與 AI 評估整合。
- 目錄整理、舊設定遷移與確認不用的程式淘汰。
- Legacy bug 修正版與算法優化，各建立可辨識 baseline。

完整 addAct 歷史不是可恢復 checkpoint；不能沿用先前「每 60 秒保存全算法＋RNG 中間狀態」的提案當作這次義務。

## 每個小單元的工作紀律

- 修改前先保存／定位要比對的基線與範圍。
- 只動該單元，不混入修 bug、換 RNG 或改數學定義。
- 執行針對性測試，檢查證據後才做下一單元。
- 初始／過程／結果或效能量測有差異時，先定位，不用最終分數巧合相同帶過。
- 有明確審閱停止點就停下；不得因前一項通過而自動執行後續全部工作。
