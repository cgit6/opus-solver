# 17｜C++ 呼叫方式與 worker 保存的對照實驗

實驗與整理日期：2026-10-21。

狀態：控制原型已執行，使用者看過證據後選定 **Python worker 內同程序呼叫 C++ 擴充模組**，並由該 worker 同步保存，主程序只接收摘要與檔案位置（D34–D35）。本次僅整理文件與封存研究證據，沒有重跑大型測試、修改正式算法、registry、CLI、派工或輸出器。

## 一、問題與已確認決議

本輪先確認保存路徑，再在同樣路徑下比較呼叫方式：

```text
Python 實驗主程序安排 task
  → 隔離的 Python worker 呼叫 C++，完成整題及最終驗證
  → 完整結果與全部歷史一次返回該 worker
  → worker 呼叫共用 Python 輸出器，同步保存這一題
  → 主程序接收摘要及檔案位置
  → 不再需要的本題資料正確釋放，健康 worker 接下一個新 task
```

這是責任與資料路徑，不是完成通知、所有權移交與回收先後的正式協議；尚未有人接收／保存完的資料不得提前釋放。

本單元的 D30–D35：

- **D30**：首版支援 Linux／WSL，不以原生 Windows 作驗收平台；C++ 核心仍應避免不必要的平台耦合。
- **D31**：本版不內建單 task 停止命令，研究者使用外部工具人工處理；系統依觀察到的程序終止等事實記錄，不新增自動超時。
- **D32**：Python 正式介面只需完整求解及結果，不要求公開算法物件或逐步執行函數。逐模組測試仍須做，可使用原生測試或 oracle。
- **D33**：失敗 task 能透過 Python 命令單獨從頭重跑即可，不要求脫離 Python 的獨立原生重跑入口；正式命令尚未實作。
- **D34**：Python worker 保存完這題才接下一題；主程序只收統計所需摘要與檔案位置，不累積整場完整歷史。
- **D35**：首版採同程序 C++ 擴充模組。C++ 原生崩潰可連帶終止該 worker；主程序記錄並只替換它，其他健康工作不取消、不重跑。

D35 是依保存路徑、故障要求與本輪對照後的使用者決策，不恢復先前「因為符合現有程序池，所以優先 A」的理由。C++ 核心與 Python 接線應分開，算法內部不依賴 Python 型別；正式函式簽章、資料表示、建置方式與監督協議仍待議。

## 二、可追查的證據與測試環境

- [原型來源、依賴版本與暫存重跑說明](evidence/invocation_comparison/README.md)。
- [原始結果 JSON](evidence/invocation_comparison/experiment_results.json)：本頁數字直接由其中的樣本計算，文字表格四捨五入至小數六位。

- 共同 C++ 旗標為 `-std=c++17 -O2 -Wall -Wextra -pthread`；擴充模組另加共享庫及 binding 旗標，見建置程式。
- pybind11 只安裝在暫存目錄，沒有新增至專案依賴。原型不載入現有 CDELS 或整套實驗模組，不能把薄 worker 的基礎記憶體當成現有專案固定成本。

此附件保留來源與 JSON，不納入執行檔、共享庫、依賴套件或約 10.526 GiB 的生成輸出。實驗期間的絕對路徑、PID 與 traceback 是當次證據，不是正式系統欄位。

## 三、如何公平比較

### 共同的合成工作

三種配置使用同一段 C++ 計算，依每題 seed 產生完整 `uint64_t` 數值緩存與校驗值；計算沒有 Python callback，也不寫實驗結果文件。

RNG 為每題重新設定的 64-bit LCG：`state = state * 6364136223846793005 + 1442695040888963407`，依無號 64-bit 溢位。輸出字另混入位置值，並保留最後 RNG 狀態及校驗和；它不是替正式算法選定的新 RNG。

所有計算完成後，才一次交付整份結果。三種配置都由同一套 Python 函數將已完成的結果同步寫成二進位文件，使用小型 memoryview 切片寫入並呼叫 `fsync`，不壓縮、不先轉為巨大 JSON／Python list。完整文件的 SHA-256 在計時後核對。

切片保存或逐段讀取一份已完成回應，不是算法迭代中分批返回，不是 addAct I/O，也不是背景 writer。測試採用 `fsync` 不表示正式保存格式、完成標記或持久化保證已定案。

### 三種配置

| 原始模式名 | 配置 | 完整結果的交接 |
| --- | --- | --- |
| binding | A：Python worker 載入 C++ 擴充模組。 | 原生結果物件暴露唯讀 buffer；Python 保存期間持有結果，不額外建立完整 Python 資料副本。 |
| ipc_copy | B：每個 Python worker 配一個可重用的獨立 C++ 程序。 | 用 Unix stream socket 的管線式傳輸，把完整資料讀入 Python bytearray；交接時兩邊可能各持有一份。 |
| ipc_shared | B：同樣的程序隔離，改用共享記憶體。 | Python 預先建立已知尺寸的 memfd／映射，交付描述元，C++ 直接填入；完成後 Python 持有映射並保存。 |

B 配置不是聲稱所有獨立程序設計都必須多一層 Python worker，而是配合已選定的「worker 保存、主程序只收摘要」條件作對照。A／B 都重用健康執行環境、逐題重設 RNG，不以每題啟動成本偏袒任一方。

共享記憶體配置預先知道輸出大小；真實 addAct 歷史未必如此。因此本輪沒有選定正式的歷史容量估算、配置、擴充或映射方案。

## 四、正確性、重用與異常測試

三種配置均通過：

1. 小資料五組輸入（含同題／seed 再次執行）與獨立 Python 參考計算比較完整 bytes 的 SHA-256、最後 RNG 與校驗值。
2. 一般 C++ 例外及之後的新題、錯誤輸出路徑及之後的新題，共同形成 JSON 所記每案 9 個檢查；健康 Python／C++ 程序身分不因這些可恢復錯誤更換。
3. 寫到目錄而非結果檔案時，實際產生 `IsADirectoryError`。Python 留下 task、輸入、路徑、失敗階段與 traceback，再執行新題；不是測試磁碟滿或硬體故障。
4. 另外保留前題完整結果，再執行不同 seed 的下一題，前題內容不變；這個檢查不另計入 JSON 的 9 個檢查數。
5. 45 次單 worker 正式計量的完整輸出，按尺寸核對 SHA-256、最後 RNG 與校驗值一致；不是只看分數或資料長度。

`live_bytes` 清理檢查只涵蓋測試原生結果儲存，不代表整個程序／配置器沒有其他記憶體。共享記憶體案的 C++ 映射可以先釋放，但 Python 仍持有有效映射直到保存完畢；不能因原生計數為 0 就宣稱完整結果已不占 RAM。

2026-10-22 政策補充：上列一般例外後重用是 10-21 原型的實際行為，不是 D39 的正式驗收。後續 D39 已確認「非預期 C++ 錯誤即使已捕捉也替換該 worker」，D40 則依 Python 保存錯誤後的清理結果決定重用／替換；本次沒有修改原型或重跑測試，不能把既有通過旗標視為這兩項政策已實作。

### 八 worker 中一個 C++ 程序終止

三種配置各做一組：8 個工作同時開始，指定其中一個 C++ 執行 `SIGABRT`，其餘七個工作正常完成；故障測試的短暫延遲只用於協調重疊，不混入效能樣本。

- 實驗側在分派前保存合成工作的實際輸入，不依賴崩潰方返回。
- A 的該 Python worker 隨原生程序一起退出，觀察到退出碼 -6；控制器只替換該 worker。
- B 的 Python worker 仍在，觀察到原生子程序退出碼 -6，記錄後只替換該 C++ 子程序。
- 其他七個工作的 Python／C++ PID 不變，不取消、不重跑，完整結果相符。
- 隨後八個執行單元都可執行下一個新 task，不自動重試失敗 task。

這證明控制原型在所測時點可隔離單一原生程序退出，不表示正式程序池已有此能力，也不是所有記憶體破壞、通知中斷時點或根因定位的完整驗收。

## 五、單 worker 耗時與記憶體

尺寸為 4／64／256 MiB，每種配置先各暖機一次，再以交錯次序量測五輪，共 **45 次正式計量**；暖機、編譯、首次啟動及文件雜湊核對不列入下表。

口徑：

- `compute_s`：C++ 結果儲存配置／映射、數值填入及校驗的秒數，不是實際優化算法搜尋時間。
- `boundary_s`：Python 求解呼叫到完整可用結果的時間，減去 C++ 計量區間；含必要的 Python 配置、映射／描述元操作、傳輸、封裝與交接清理，不是純 FFI 指令時間。表中轉成毫秒。
- `save_s`：同一套 Python 保存函數的寫入、同步及關檔耗時。
- `worker_s`：worker 從求解開始到保存與本題清理的計量區間，含測試取樣點等額外工作；不是整場實驗耗時。

此批主程序 PSS 約 11.680–12.162 MiB，成功摘要訊息最多 527 bytes；這個薄控制器沒有保存全部大型歷史，不代表未來正式實驗主程序只會用這些記憶體。

## 六、八 worker 同時保存

每種配置三批，每批 8 worker、每題 64 MiB，共 **9 個並行批次**。執行次序交錯；量測包含分派到這八題全部保存及回報的時間，不含先前的 worker 啟動／暖機或之後的完整文件雜湊核對。

| 配置 | 批次數 | 批次秒中位數 | 批次秒最小–最大 | 執行單元合計 PSS 抽樣最高 MiB |
| --- | --- | --- | --- | --- |
| A 同程序 | 3 | 2.321765 | 0.769562–2.807145 | 601.575195 |
| B 管線複製 | 3 | 2.660951 | 2.339594–3.877400 | 979.017578 |
| B 共享記憶體 | 3 | 2.369371 | 2.210719–3.736364 | 538.303711 |

主程序 PSS 約 11.639–11.731 MiB，成功摘要訊息最多 530 bytes。並行記憶體值受各題交接、保存完成時點影響，並非強制所有題同時持有完整結果的等長狀態比較；不能只依最高值判斷單題儲存表示更省。

磁碟保存及批次時間波動明顯，僅三批，區間亦有重疊，**不足以支持正式系統吞吐排名或固定加速百分比**。尤其不能把交接的微秒／毫秒差，改寫成算法搜尋本身快幾倍。

## 七、為何選同程序，以及沒有選定什麼

使用者接受 C++ 原生崩潰可能帶走該 worker，只要求主程序及其他健康 task 繼續。在此保障範圍下：

- A 可在被隔離的 Python worker 內直接交付完整結果，再同步保存，不必為這條結果路徑維護獨立原生程序及跨程序協議。
- B 共享案同樣可行，且不必多一份完整結果；它的額外隔離是讓該 Python worker 仍存活，但這不是本版必須增加的保障。
- 因此選 A 是符合需求的結構取捨及使用者明確確認，不是宣稱實測證明 A 在所有負載最快，亦不是沿用現有程序池。

正式實作仍須做到 C++ 核心／Python 接線分離、每題資料獨立及所有權正確。不能把原型唯讀 buffer、固定長度二進位協議、memfd 或 `fsync` 直接當成正式 DTO／保存規格。

尚未定案：正式函式／型別、問題資料 SHM、任意外部結構的表示與所有權、正式通訊／監督及狀態保存格式、建置／載入新版本與重跑命令。2026-10-22 的 D36–D40 已補足 task／worker 對應、通知未達及替換政策，見 [15](15_task_failures_and_result_storage.md)；正常可行／不可行解、正式算法初始化／逐代狀態、最終驗證及新政策的實作，均不能由此合成測試宣稱已驗收。
