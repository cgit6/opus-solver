# 16｜求解程序重用的對照實驗與決策

實驗與整理日期：2026-10-21。

狀態：本份生命週期對照已執行，使用者已選「重用健康的求解程序」。2026-10-24 補充：D79–D80 已將算法錯誤改為停止整場；下列隔離故障、替換後繼續的觀察及 D27／D29 原始表述保留為當時條件，不作現行繼續派工要求。當時後續 D34–D35 選定 worker 同步保存與同程序擴充模組，證據另見 [17](17_invocation_comparison_experiment.md)；D35 現在是重新評估基線，架構狀態與比較維度見 [14](14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度)。正式函式、所有權與監督實作仍待細化，沒有據此修改算法或派工程式。2026-10-22 補充：D36–D40 已確認派工／通知與錯誤處置政策，見 [15](15_task_failures_and_result_storage.md)；本份實驗數字未變，也未重跑。

## 一、這次要回答什麼

程序正常完成一題後，應繼續接下一題，還是每題重新啟動？比較前先區分三件事：

- **程序重用**：保留執行環境，減少反覆啟動與載入。
- **任務資料生命週期**：每題有自己的 RNG、工作資料與歷史，不能延續上一題的搜尋狀態。
- **結果資料交接**：資料仍被 Python 或保存流程使用時，不能提前釋放；正式所有權與轉換方式尚未定案。

程序可以繼續存在，但上一題的任務資料不必一直存在。這次不修改算法策略，也不把狀態清理變成每代重新配置工作緩存。

## 二、為什麼不使用舊核心的記憶體增長選型

第一輪沿用封存的 SCVRP C++ 核心，經臨時外殼在同一程序重複呼叫。它不是依新任務生命週期整理好的實作：

- [舊核心的世代計數](../../../solver/native/scvrp_legacy/metaheuristic/differential_evolution.cpp:16) 是程序內的靜態變數；只重設 seed，後一題的世代編號仍會累加。臨時外殼重設這個計數後，所測案例才與各自新程序的完整輸出一致。這不是已修改正式算法。
- 連跑 256 個 P-n16 小任務、穿插 8 個 A-n80 任務後，觀察到 RSS 約由 3.75 增至 9.25 MiB。使用者指出舊實作的狀態緩存沒有整理好；本輪沒有完整定位這筆增長，也不能只憑 RSS 判定它全部是洩漏或全部是可用緩存。
- A-n80、111 次迭代的計時期間另有高 CPU 負載，樣本波動很大，不據此判斷哪案比較快。

**舊核心的記憶體增長不作為程序生命週期的選型依據；先前用它支持每題重開的理由已撤回。**因此另做下列每題清理正確的控制實驗，而不是順便修正 legacy bug。

Python 啟動成本也曾分開量測：8 個超短任務、3 輪，含目前 `mkp.machine.core` 及其依賴模組載入，重用 Python 的批次中位數為 0.967439 秒，每題重開 Python 為 7.183589 秒。兩案都在每題啟動新的 C++ 程序；未涵蓋完整 worker 初始化、SHM 附接或 JIT。這只能說明「重開 C++」不能與「連 Python 也重開」混算，不能當成未來精簡 worker 的固定成本。

## 三、乾淨對照程式如何運作

### 環境與兩種生命週期

- Linux 本機，Python 3.12.3，g++ 13.3.0；編譯旗標為 `-std=c++17 -O2 -Wall -Wextra`。
- 同一份臨時 C++ 程式、相同輸入、相同結果協議；沒有使用 SCVRP 算法或 pybind11。
- 重用案：一個批次啟動一個 C++ 程序，逐題處理，批次結束才退出。
- 重開案：每題啟動同一個 C++ 執行檔，收到該題完整回應後讓程序退出。
- 兩案的 Python 控制端都保持運行；按輪交替兩案的測量順序。

### 單一任務的資料與清理

1. 輸入是 seed、工作區字數、歷史字數及合成計算輪數；每字為 8 bytes。
2. 在該題內建立私有 RNG、工作區與歷史兩個 `vector<uint64_t>`，由 C++ 作用域生命週期管理並追蹤兩個陣列的持有量。
3. 以確定性的數值產生流程填滿工作區，再產生歷史。這只是合成工作，不是優化問題的求解迭代。
4. 所有計算完成後，才送出該題的回應標頭與完整歷史。Python 逐段讀取這一份回應並計算 SHA-256；不是在算法迭代中分批提交。
5. 結束該題的作用域，銷毀兩個資料陣列，再回報清理後的計數及記憶體資訊；不呼叫 `malloc_trim` 強制把配置器保留空間退還作業系統。

實驗 RNG 是每題重新設定的 64-bit 無號 LCG：`state = state * 6364136223846793005 + 1442695040888963407`，按 64-bit 溢位；它不是正式算法應選用的 RNG。工作區另有確定性指紋，歷史則對全部傳回 bytes 計算 SHA-256。

所有成功回應的 `live_owned_bytes`、`live_owned_buffers` 都必須為 0。這兩個計數**只涵蓋這兩個任務陣列**，不是宣稱 C++ runtime、輸入輸出串流、配置器或整個程序沒有其他記憶體。

## 四、時間測量

下表是整個批次的秒數，不是單題秒數。包含該批次的 C++ 程序啟動、資料配置、合成計算、完整歷史傳輸、Python 摘要核對及正常程序退出；不含編譯、外層 Python 啟動、正式題庫載入、SHM 與文件保存。

所有計時任務的合成計算輪數為 1，seed 依批次內順序循環使用 1、2、3、4。兩種生命週期分別執行表列輪數，結果及完整歷史摘要均一致。

| 每題工作區／歷史 | 每批任務數 | 每案測量輪數 | 重用中位數（秒） | 重用最小–最大（秒） | 重開中位數（秒） | 重開最小–最大（秒） |
| --- | --- | --- | --- | --- | --- | --- |
| 4 KiB／4 KiB | 128 | 7 | 0.013501 | 0.011394–0.016936 | 0.306876 | 0.298589–0.385077 |
| 4 MiB／1 MiB | 16 | 5 | 0.043410 | 0.040833–0.044798 | 0.109553 | 0.108863–0.113169 |
| 64 MiB／8 MiB | 4 | 5 | 0.211240 | 0.208989–0.230443 | 0.222027 | 0.217546–0.233218 |

以兩案批次中位數相減，再除以任務數，重開案分別多約 2.292、4.134、2.697 毫秒／題。這不是純粹的 OS 啟動時間，也不代表所有算法固定多這些毫秒；配置器重用、頁面配置與傳輸等成本都可能包含其中。

這次控制測試看到重用較低的批次中位數，尤其是極短任務；最大資料組的時間區間仍有重疊。不宣稱有統計顯著的固定加速率，更不能把它寫成 CDELS、其他算法或整場實驗的加速倍數。

## 五、記憶體與清理測量

### 連續 136 個任務

在同一個 C++ 程序執行 128 個小任務，每完成 16 個小任務，穿插 1 個大任務，共 8 個大任務：

- 小任務：1 MiB 工作區、64 KiB 歷史；seed 循環使用 1、2、3。
- 大任務：64 MiB 工作區、8 MiB 歷史；seed 為 2。
- 每個任務的結果與各自新程序基準一致；下表列在該檢查點全部任務完成、陣列清理後的值。

| 已完成小／大任務 | 清理後任務陣列 bytes／個數 | 程序 RSS（KiB） | 程序累計 VmHWM（KiB） |
| --- | --- | --- | --- |
| 1／0 | 0／0 | 3484 | 4480 |
| 16／1 | 0／0 | 4508 | 78236 |
| 32／2 | 0／0 | 11676 | 78236 |
| 64／4 | 0／0 | 11676 | 78236 |
| 96／6 | 0／0 | 11676 | 78236 |
| 128／8 | 0／0 | 11676 | 78236 |

RSS 後期停在約 11.4 MiB，沒有在這 136 個任務中持續上升。後期 `mallinfo2` 回報 heap 在用量為 83,312 bytes、heap 可用量為 8,596,112 bytes，兩個任務陣列持有量則為 0；這些是不同的統計口徑。程序仍佔有一些配置器可再利用的空間，不等於上一題的工作區或歷史仍被任務持有。

這只支持本次控制程式的清理行為，不能證明正式求解模組沒有洩漏，亦沒有驗證大型單任務全歷史不會 OOM。

### 計時批次的取樣不冒充峰值

64 MiB 工作區／8 MiB 歷史的計時組，在合成計算完成時取樣 RSS，重用案最大約 75.340 MiB，重開案約 75.250 MiB；清理後仍在程序內取樣的最大 RSS 則分別約 11.340、3.340 MiB。重開案的程序隨後退出，不能把退出前取樣值當成仍有一個常駐程序。

**先前聊天簡稱的「約 75 MiB 峰值」，精確說是計算完成時的 RSS 取樣，不是連續量測的嚴格峰值。**另一次 136 任務試驗的程序 `VmHWM` 為 78,236 KiB，約 76.4 MiB；不能把不同批次數字合成「兩案嚴格峰值完全相同」的結論。

以上都不是 Python 加 C++ 的整個系統峰值，也不是八個求解程序加總的峰值。

## 六、正確性與單程序故障測試

### 正常資料與任務順序

- 先做 5 個小案例，以獨立 Python 計算核對 RNG 最終狀態、工作區指紋及完整歷史 bytes；包含同 seed 在其他任務前後重複執行。輸入依序為 `(seed, 工作字數, 歷史字數, 輪數)`：`(1,16,32,1)`、`(2,128,64,3)`、`(1,16,32,1)`、`(123,513,101,2)`、`(1,16,32,1)`。
- 計時及連跑測試核對有效輸入、RNG 最終狀態、工作區指紋與全部歷史的 SHA-256；計時資料不包含在語意一致性比較內。
- 兩種生命週期皆通過上述範圍內的比對，不是只比較一個最終分數。

### 八個程序中終止一個

重用案與重開案各測一次：

1. 使用 Python 測試控制器及 8 個彼此獨立的原生程序。
2. 第 1 個程序收到故障注入訊息後，以 `SIGKILL` 強制結束；其他 7 個執行 seed 2–8 的正常任務。
3. 只替換死亡程序，不把失敗的工作自動重試；各執行單元繼續 seed 11–18 的下一個新任務。
4. 正常任務各使用 64 MiB 工作區、8 MiB 歷史；其他 7 個任務及後續 8 個任務的輸入、RNG、工作區指紋與完整歷史摘要均符合各自基準，回應後的兩個任務陣列持有量皆為 0。
5. 重用案另外確認健康程序的 PID 不變；只替換死亡程序。

兩案皆通過。這是刻意的原生程序終止測試，不是已重現某個 C++ 越界根因，也不是目前正式 `ProcessPoolExecutor` 已具備這項能力。

## 七、當時已確認的決議（歷史背景）

使用者在看過乾淨補測後選擇「重用健康的求解程序」：

- **D27**：一個 task 出錯，不取消、不重跑其他正常 task；固定 seed、固定迭代下仍須驗證其他任務的過程及結果不變。
- **D28**：本版不加入卡住後自動超時中止；沒有完成但也沒有明確錯誤／程序終止的工作，暫由研究者人工處理。這不同於算法本身的正常停止條件。
- **D29**：健康的求解程序繼續接新 task；每題的 RNG、算法狀態及歷史獨立初始化、交付後正確清理。崩潰或狀態不可信時替換該執行單元，不連帶取消健康工作，不默認重試失敗 task。

重用程序不等於沿用上一題的搜尋狀態；同一題的工作空間仍可在求解期間重複使用。結果或歷史若仍被接收／保存方引用，必須先確保正確交接，不能為了接下一題就提前釋放或覆寫。正式呼叫方向後續由 D35 確認，見 [17](17_invocation_comparison_experiment.md)；函式與所有權細節仍待討論。

## 八、證據限制與後續驗收

- 這份實驗本身只比較生命週期及控制資料交接，不決定擴充模組／獨立執行檔。後續使用者是在另一輪呼叫對照後選 D35（見 [17](17_invocation_comparison_experiment.md)），不是因本份實驗採獨立程序就選 B。
- 合成歷史不是正式 addAct 實作；Python 計算摘要後不保留整個大回應，也沒有寫正式結果文件，不能據此估算完整保存流程的總記憶體或吞吐。
- 未涵蓋 SHM 的附接／清理、完整題庫載入、正式算法、輸出器失敗原因留存、交付完成確認或整場續跑；沒有完成 G2／G3 驗收。
- 控制程式由記憶體編譯到 `/tmp`，未加入專案測試／CLI。這份文件保留方法與本次輸出摘要，沒有已納入專案的固定重跑命令，也不保證暫存建置產物長期存在。本次文件更新沒有重新執行這些實驗。
- 正式實作仍須比對同題、固定 seed、固定迭代下的初始化、逐階段／逐代狀態、RNG 與完整解；任務順序改變、重複執行及其他程序故障，也不能污染正常任務。
