# Task 異常紀錄與結果保存

算法執行出現非預期錯誤時，依 D79–D80 停止整場實驗，包含可捕捉錯誤、原生致命崩潰、其他算法與正在求解的 task；不再啟動新 task，已成功保存結果保留，不自動重跑。這不代表目前已能立即、安全地中止所有工作。

正常不可行解不是算法錯誤。Python 保存錯誤仍依 D40 留存原因及清理／重用規則；輸入預檢及硬體／資源故障的範圍不擴大。實際輸入、已收到通知及交付事實仍保留，不猜未知根因。

D34 的同步 task 保存位置及主管只收摘要／路徑保留；舊 Python 保存基線、候選語言與 D18 返回／所有權差異見 [07](07_history_return_and_storage.md#已確認交付需求與保存基線)。D35 曾選定的 Python worker 內同程序 C++ 呼叫及完整拓撲，現在作為重新評估基線；三個比較維度見 [14](14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度)，本輪不自動改架構。歷史實驗與限制見 [16](16_process_lifecycle_experiment.md)、[17](17_invocation_comparison_experiment.md)。

較新的正常／故障／保存候選實驗已封存於 [19](19_architecture_candidate_experiments.md)，尚未選架構、輸出器或正式留因／退休機制；不是正式 G2／G3 驗收。該章區分當時原稽核與本次只讀封存核對，不重寫本章 D38／D40 政策。

## 快速檢索卡

- 核心問題：算法錯誤停止整場時，如何留下實際輸入、已知錯誤、已交付結果與連帶停止的事實？
- 當前結論：算法錯誤停止整場；Python 保存錯誤仍分開處理，正常不可行不阻擋。
- 已確認：不自動重跑；已收到完整成功／錯誤回報不能被之後退出覆蓋；缺少完整最終回報依 D38 記交付未確認，不自動核對文件或補登成功。
- 關鍵待議：併發架構比較、停止時點、安全收尾、未知原因退出判定，以及正式通訊、DTO、所有權與保存格式。
- 適用於：本機傳統優化實驗的求解與 Python 輸出；不是硬體／資源層備援或算法中途 checkpoint。
- 待驗證：新政策下正式停止、紀錄、清理與結果交付；舊隔離控制實驗不等於新方案驗收。

## 核心問題

「算法已算完」「結果已寫好」「主程序知道結果已交付」是不同事實。任務在其中一段出錯，不能全部記成算法失敗，也不能因為 C++ 正常返回就宣稱結果已保存。

task、邏輯工作鏈、實體求解程序（host）、執行緒及 worker 的單一說明見 [14 名詞表與替換範圍](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍)。D35 舊基線一個 Python worker 對應一個程序與工作鏈；候選同 host 多 threads 時不能照搬一對一關係。保存仍屬實驗／輸出責任，不是算法責任，也不由本章選新拓撲。

## 形成的知識

### 已確認的異常處理要求

1. 非預期算法執行錯誤，包括可捕捉錯誤與原生致命崩潰，均觸發停止（D79）。
2. 停止範圍為整場實驗，涵蓋其他算法及正在求解的 task；不再啟動新 task，已成功保存結果保留，不自動重跑（D80）。
3. 實際輸入須在派工前保留；錯誤後保存可取得的資訊，不要求 Python 查明 C++ 根因。
4. 正常不可行解是正常結果，不觸發上述停止。
5. Python 保存錯誤須保留原因及 task 對應；清理成功且環境可信才可重用，否則不再重用該不可信環境（D40）。舊基線可替換其程序，新拓撲的實體範圍／時機按 [14](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍) 待確認，不自動重求解／重試，也不一律全場停；接新 task 仍須滿足健康及整場未停止條件。
6. 不因本輪把輸入預檢、Python 寫檔錯誤或排除的硬體／資源故障一律視為算法錯誤。
7. 只記收到的通知與實際交付事實；未知退出原因不得猜成算法錯誤，被連帶中止的 task 也不能記成成功或算法自身錯誤。
8. 已交付結果不因後續退出而失效；未確認的工作按 D38 保留輸入、現有文件與已知事實，不自動核對、補登或重跑。
9. 正常運行重用健康程序，每 task 的 RNG、算法狀態與歷史獨立；同一邏輯工作鏈同步保存／交接及清理後才接新題，不要求同 host 所有其他鏈一起等保存。仍有人使用的結果／共享題目不得提前釋放或覆寫。
10. 本版仍不加入卡住後自動超時、內建單 task 人工停止命令或中途續算。D79–D80 是算法錯誤停止整場的政策，不是這些功能。

D24、D27、D29、D35、D39 已依 D79–D80 更新有效描述。正式執行架構、停止時點、正在運行工作如何安全收尾，以及未知原因退出如何判定仍待細化；不把「停止整場」寫成已實作的立即強制終止機制。

### 求解異常與寫檔異常需要不同紀錄

| 情況 | 需要保留的資訊 | 不應聲稱的事 |
| --- | --- | --- |
| 求解未正常完成 | 實際題目數值或可重建的已保存引用、算法與完整有效參數、seed、停止／紀錄設定、其他初始化輸入及 task 關聯。 | 不要求 Python 一定有 C++ 根因、堆疊或出錯行號。 |
| Python 寫檔失敗 | task 關聯、寫入目標、失敗動作與實際取得的錯誤原因。可用的錯誤類型、作業系統錯誤碼及訊息應保留。 | 不能用「寫檔失敗」四個字代替可取得的原因；也不能宣稱只用相同 seed 就能重現檔案權限等環境問題。 |
| worker 未正常回報 | 已保留的實際輸入、執行關聯與最後已知事實。 | 不能單憑沒收到回報，就斷定 C++ 根因、寫檔是否完成或是哪一步失敗。 |

求解輸入須在開始執行前由實驗側保留，不能依賴崩潰 worker 返回後才第一次保存。大份固定題目可以保存一次供多個 task 引用；可變來源路徑、暫時 SHM 名稱或裸指標不足以支持日後重跑。詳見 [14 的輸入要求](14_python_cpp_invocation_and_failure_replay.md)。

D48–D49 不取消上述紀錄責任，但重跑讀本次設定指定的參數與題庫檔案，一致性由人維護。原實際值供追查或人工重建，不自動套用、比對、鎖定或修正；指定檔案若已變，讀取並記錄新實際值，不改寫原紀錄。這不取消必要輸入預檢、D46–D47 或求解任務的最終驗證。

表內是所需資訊，不是已定的欄位 schema。寫檔錯誤也可能發生於開檔、資料轉換、序列化、寫入或關檔；記錄應反映實際發生的軟體流程階段，而非先猜原因。

### 保存錯誤原因的留存界線

D25 的強需求保留：範圍內的 Python 軟體保存失敗，實際失敗原因與 task 對應必須能事後查得，不能只留下「保存失敗」，也不能擅自降成最佳努力或容許原因遺失。這不同於求解異常只須保留實際輸入及已知事實、不要求取得 C++ 內部根因。

產生／捕捉錯誤原因、通知管理端、將原因持久保存，是不同時點。原因只在記憶體或 IPC 訊息中，不等於已持久留存；通知成功本身也不證明原因已持久保存、日後可查。若原因只隨截斷 IPC 傳送，可能遺失，[19](19_architecture_candidate_experiments.md#補充故障與未決政策) 已有特定 TypeError 加通知截斷的負例。它指出單靠通知的缺口，不是接受原因遺失。

正式由誰、何時、何處保存原因，以及何時算留存完成，尚未確認。worker 先用獨立、JSON-safe 的錯誤格式寫 artifact，再通知管理端，只是 19 測過的候選；不因測過就成為正式規則、schema 或新服務需求。該候選僅支持當時特定案例，不保證任意 kill、錯誤檔本身再次發生軟體錯誤，或任意原生狀態損壞時仍成功留因。

二次軟體失敗、留存前突然退出等情境的保障範圍與機制，仍須與使用者確認；不能悄悄歸入 D26 已排除情境，也不能宣稱所有軟體情境已保證。D25 的強需求不因此取消；D38 的「只記收到的事實」亦不能代替正式留因機制。D26 仍只排除磁碟滿、磁碟故障等硬體／資源層情境，包括由此造成的整個儲存不可寫，不另開硬體／跨媒介備援；路徑、權限、序列化等軟體問題不因影響範圍大就自動排除。

以下只做文件靜態對照，不是新故障實測，不定正式 enum／schema 或恢復狀態框架。

| 情境 | 已知事實與要求／待確認 | 不能宣稱 |
| --- | --- | --- |
| 一般可捕捉的 Python 保存錯誤 | 已產生實際原因；D25 要求原因與 task 事後可查，正式保存時點／責任方／位置仍待確認。 | 捕捉到例外或通知成功就等於已持久留存；只記「失敗」便達標。 |
| 原因只靠通知傳送，而通知被截斷 | 19 的負例顯示原因可能遺失；正式機制須補足此缺口，不能把負例當允許遺失。 | 只靠該通知已滿足 D25，或主管可猜回原原因。 |
| 候選錯誤 artifact 已完整保存，但通知未達 | 該候選案例可人工查得原因；管理端仍只按實際收到的回報判定。缺完整最終回報依 D38 保留現況，不自動讀檔／補登／重試。 | artifact 存在等於結果成功交付，或 worker-first 已成正式留因規則。 |
| 錯誤紀錄本身再次發生軟體錯誤 | 不能假設原原因已保存；此二次失敗的保障範圍與機制待使用者確認，不自動列入 D26 排除。 | 候選已涵蓋所有錯誤格式／序列化失敗，或此類失敗可不留原因。 |
| 原因落盤前實體程序突然退出 | 只能按實際輸入／通知／文件及退出事件記已知事實；留因保障及退出處置仍待確認，不能以 D38 免除 D25 要求。 | 尚未持久保存的原因必定可找回，或未知退出已確定屬算法／硬體錯誤。 |
| 磁碟滿、磁碟壞等硬體／資源故障，或由此造成整個儲存不可寫 | 依 D26 排除專用保障，不要求另一媒介／服務保存原因；路徑／權限／序列化等軟體問題不因全域影響就自動排除。 | 已提供硬體備援，或可用此排除概括所有不可寫原因／二次軟體失敗。 |

原因可追查與結果交付是不同要求：錯誤 artifact 不替代完整最終回報，D38 仍不掃檔、補登或重試。D40 的清理／不可信環境與新拓撲替換範圍仍依 [14](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍)，D79–D80 的算法錯誤停止整場不變；本節不選留因時序或退休策略。

### 已確認的派工、通知與異常政策（D36–D40）

以下保留既有 Python 派工方案的資料路徑，並套用 D79–D80；不是本輪已選定新併發架構：

```text
主程序先保留實際輸入與 worker／task 對應，再指派一題
  → worker 通知「已接收任務」
  → C++ 完整求解並一次返回結果與全部歷史
      → 算法錯誤：保留已知錯誤與輸入，觸發整場停止；不再派新 task
  → 正常返回才通知「C++ 已正常返回」
  → Python worker 同步保存結果
      → 正常交付：回報完整摘要與位置
      → 保存錯誤：記實際原因，依 D40 清理／重用或替換
      → worker 退出：先處理已交付通知，再依已知事實記錄
  → 結果仍被使用時維持其有效性；整場未進入停止才可派下一題
```

D36 的先登記再指定與事件等待、D37 的兩種通知及 D38 的已知事實原則保留。候選須能辨識 task 與實際執行關聯，不只知道 host 而混淆其內多題；具體映射／識別及 IPC 格式未定。收到任務不代表 C++ 開始，返回不代表已保存；缺通知不能反推階段沒發生。同步節奏與層級依 [14 名詞表](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍)，不以沿用舊流程作選型理由。

圖內「記實際原因」列的是責任，不指定原因持久保存與通知的先後、位置或完成判定；收到錯誤回報亦不自動證明持久留因完成，依 [上述界線](#保存錯誤原因的留存界線) 細化。

**task 結果與執行環境健康分開。**退出指實體求解程序退出，舊基線就是 worker 程序；同 host 多題須逐 task 先處理已交付通知，再按各題完整回報判定。已收到完整成功／錯誤回報不因 host 退出改寫；缺完整回報者保留文件與已知事實、記交付未確認，不自動讀檔核對、補登或重跑。已保存但未確認的文件也保留，不能僅憑存在宣稱交付。

D39 的算法錯誤依 D79–D80 停止整場。D40 不再重用不可信執行環境；原多程序基線可替換其程序，新拓撲的連帶範圍／時機依 [14 對照](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍) 待確認，不能只換 thread／物件就算恢復，也不默選立即或排空後退休。普通保存錯誤不一律全場停；若已有整場停止觸發，不能因一條鏈清理成功就接新題。清理不刪既有／部分結果，也不提前回收仍使用的資料。

C++ 獨立輸出候選拋出的例外，須按實際業務階段區分，不能僅憑 C++ 語言歸為算法錯誤。候選如何映射 D25／D40 的保存錯誤，依 [07](07_history_return_and_storage.md#已確認交付需求與保存基線) 列差異待確認；不自動擴大現行 Python 保存政策或新增恢復策略。

未知原因退出不直接推定算法根因。D38 決定如何記錄已知交付事實；它本身不決定未知退出是否觸發 D79，也不保證可立即安全中止正在運行的工作。這些判斷與停止收尾交由新執行架構細化。

異常、連帶停止與未確認工作應如實出現在報告，不偽造零分、空解或成功樣本。統計分類、平均值與成功率分母仍在 [09](09_experiment_planning_and_statistics.md) 收斂。

### 十個事件案例

本表是預期行為，不是正式 enum／訊息 schema。退出均指實體求解程序（舊基線 worker 程序）退出，同 host 多 task 各按其完整回報判定；未知退出處置不在此擅定。表中的「收到原因」只代表管理端取得資訊，不證明原因已持久留存，另依 [留存界線](#保存錯誤原因的留存界線) 核對。E04／E05 按 [14 的 D40 範圍](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍) 解讀，不保證換 worker 只影響一題，亦不擴大普通保存錯誤政策。

| 案例 | 管理端已取得的事件／事實 | task 如何記錄 | 執行環境／整場如何處理 |
| --- | --- | --- | --- |
| E01 | 收到完整成功回報，最終解可行。 | 確認已交付，保留摘要與檔案位置。 | 清理後可重用；僅整場未停止時接新 task。 |
| E02 | 收到完整成功回報，最終解不可行。 | 正常交付，標示不可行，不當作算法錯誤。 | 不觸發 D79；正常清理與重用。 |
| E03 | 收到非預期 C++ 算法例外的完整錯誤回報，host 仍存活。 | 記算法錯誤，保留輸入與可取得錯誤。 | 依 D79–D80 停止整場，不再派新 task；不是替換後繼續。 |
| E04 | Python 保存出錯，收到原因，且本題清理成功、執行環境可信。 | 記保存失敗及 task／原因，不重求解或重試保存。 | D40 可重用該健康環境；同鏈完成處理且整場未停止後才接新題，不要求其他健康鏈等它保存。 |
| E05 | Python 保存出錯，收到原因與清理失敗回報，或執行環境不可信。 | 記保存失敗及可取得的清理錯誤。 | 不再重用不可信環境；舊基線替換其程序。候選 host 的替換範圍／時機及同伴影響待確認，不默選兩個退休提案、不一律全場停。 |
| E06 | 已指派但未收到接收通知，實體 host 退出，該 task 無完整最終回報。 | 交付未確認；保留輸入與指派事實，不推定 C++ 有無開始。 | 同 host 其他 task 各按回報判定；退出原因、停止及替換處置待細化。 |
| E07 | 某 task 已有 C++ 正常返回通知，host 之後退出，該題無完整最終回報。 | 該題交付未確認；保留返回事實及文件，不猜保存是否完成，不自動核對。 | 不推定算法錯誤；同 host 其他題分別判定，未知退出處置待議。 |
| E08 | 某 task 已有完整成功回報，host 之後退出。 | 該題維持已交付，不改成失敗或未確認。 | 不因 host 退出撤銷結果；其他 task 各按回報判定，退出原因未知時不猜。 |
| E09 | 先觀察 host 退出，但尚未讀取的已交付通知有某 task 完整成功回報。 | 先處理通知，該題維持已交付；不靠讀文件補登。 | 同 host 各 task 分別處理，已交付者不撤銷；退出原因及處置另判。 |
| E10 | 某 task 已有保存失敗完整回報及原因，host 之後退出。 | 該題維持保存失敗與已知原因，不覆蓋成只有未確認。 | 已知保存／清理錯誤依 D40；同 host 其他題另判，未知退出不冒充算法根因。 |

**證據界線：**原先十個案例曾在「出錯後其他工作繼續」政策下做記憶體內事件推演及斷言核對，沒有正式 IPC／故障恢復驗收。本輪改寫表內預期並做文件情境核對，未重跑舊模型；歷史推演不代表新停止方案已通過。E09 的通知處理仍是正式機制應驗證的要求，不能保證找回從未交付的訊息。

### 明確排除的故障範圍

使用者已明確排除磁碟滿、磁碟故障等硬體／資源層非預期行為的專門處理；由這些已排除故障造成整個結果儲存空間無法寫入，不納入原因留存保證。不能不問原因，就把任何全域不可寫都排除；路徑／權限／序列化等軟體保存錯誤仍依 D25。

- 不增加另一顆磁碟、另一台機器或獨立錯誤保存服務。
- 不設計跨儲存媒介備援，也不要求因上述硬體／資源故障使整個儲存不可寫時仍保證留下故障文件。
- 不把上述情境重新列為本輪待選方案或待補的錯誤留存需求。

這是硬體／資源層的明確排除，不表示已解決此類故障。權限、錯誤路徑、輸出格式及資料轉換等軟體保存失敗仍屬 D25 要求；錯誤紀錄再次失敗或留存前退出的保障範圍依 [留存界線](#保存錯誤原因的留存界線) 待確認，不自動排除或宣稱全涵蓋。單 task 完整歷史 RAM 風險也未因此解決或改成截斷。

### 已確認同步保存位置與舊 Python 保存基線（D34）

```text
主程序保留輸入並分派 task
  → Python worker 內的 C++ 擴充模組完整求解、驗證、一次返回
  → 該 worker 呼叫共用 Python 輸出器，同步保存本題
  → 主程序只收摘要與檔案位置，彙整索引與統計
  → 本題資料按生命週期清理，整場未停止時健康 worker 再接下一題
```

這是沿用 D18–D19、D34 舊 Python 保存基線與 D35 比較基線描述資料路徑；輸出器語言、完整歷史轉入 Python 及所有權差異依 [07](07_history_return_and_storage.md#已確認交付需求與保存基線) 待確認，D34 的保存位置不重開。上述流程不是正式完成／回收協議；不能先清掉尚被使用的結果，也不能把 C++ 正常返回當成保存成功。

使用者接受同步保存占用同一條邏輯工作鏈，不讓它在前題未保存完就接下一題、產生新巨大結果；同 host 其他健康鏈不因此一律停等，仍須滿足整場未停止及環境可信條件。這不保證單題不 OOM 或並行寫檔必然較快，名詞見 [14](14_python_cpp_invocation_and_failure_replay.md#執行名詞與替換範圍)。

舊保存基線的「共用輸出器」是同一套 Python 程式，不是共享可變 writer 或多單元同寫一檔。該基線一個 worker 是一個程序，先呼叫 C++ 求解再呼叫 Python 輸出器；此一對一不套到候選多 threads host。C++ 獨立輸出也可屬實驗／輸出責任，不因此讓算法或 addAct 承擔文件 I/O；語言仍依 07 待確認。

尚須細化：

- 每個 task 的獨立文件／目錄與最終格式，不把完整歷史塞進彙整用 CSV。
- 摘要中的 task 對應及統計所需數值，不只返回檔名；正式 schema 待議。
- 未完成文件、錯誤與最終回報的正式欄位／格式；D38 的交付未確認政策已定，不加入自動檔案核對。
- 錯誤原因保存、暫存／發佈方式與資料回收時序；不預設一套完成標記或通知確認協議。
- 正式輸出器避免為轉換而建立多份完整資料，分開量測求解、交接及保存成本。

主程序保存是本輪比較後未採用的路徑，不再列為有效待選方案。它也能用限制待存結果數、逐題保存後釋放來控制跨題積壓，但保存跟不上時仍須讓生產方等待；不能把「主程序保存必定 OOM」當成選 worker 的理由。既有整批保存全部 SolveResult 的流程也不是本版目標。

同程序／獨立程序的控制對照與限制見 [17](17_invocation_comparison_experiment.md)：所有案都採 worker 保存，因此不是 worker 與主程序保存的實測排名，也不是正式任意外部結構或輸出器已完成驗收。單任務全歷史 RAM、資料轉換及多 worker 磁碟競爭的風險仍在；通知未達已有 D38 政策，正式通訊實作尚未驗證。

## 討論的演化

以下 1–9 項保留各輪當時的決定；其中算法錯誤後繼續的政策已由第 10 項更新，不作現行要求。

1. 最初偏向 A（擴充模組）的理由是配合現有 Python worker、較容易先驗證；經公平拓撲比較後，這些優先理由已撤回，不能恢復成既定選型。
2. B（獨立執行檔）可提供正常執行與事後單 task 重跑共用的原生入口；使用者並未要求必須脫離 Python 重跑，因此這項優點沒有單獨決定 B 優先。
3. 比較完整歷史交付時，發現 Python 保存不等於主程序必須收到全部歷史；由 worker 呼叫 Python 輸出器因而成為候選。
4. 區分求解、保存與完成回報後，釐清「檔案可能已完成但沒有通知」不能被直接記成算法失敗。
5. 使用者明確要求 task 異常後繼續新 task、必要時重啟 worker；求解異常保存輸入，寫檔異常保存原因。這取代較早的任務失敗即停止整場實驗要求。
6. 對共用磁碟失效的反例，使用者明確選擇不處理硬體／資源層異常，不要求另一顆磁碟或另一台機器備援。不能把先前的廣泛可靠性討論當成新的實作義務。
7. 後續確認其他正常 task 不取消、不重跑，本版不做卡住後自動超時中止；看過清理正確的控制實驗後，選擇重用健康求解程序。未整理好的舊核心記憶體增長不作程序選型依據，早先據此偏向每題重開的理由已撤回。
8. 再逐題確認平台、人工停止、完整呼叫及 Python 重跑範圍；選擇 worker 同步保存後，以相同保存路徑比較同程序、管線複製及共享記憶體交接。看過控制證據後，使用者確認 D34–D35；這是新的決策依據，不恢復最初配合舊流程的理由。
9. 後續確認 D36–D40：主程序指定工作並等待事件、兩種階段通知、退出時先處理已交付通知；缺少完整最終回報就保留現況，不自動核對文件、補登或重跑。非預期 C++ 錯誤一律替換該 worker，Python 保存錯誤則依清理結果決定重用或替換。

10. 2026-10-24 使用者確認 D79–D80：可捕捉算法錯誤與原生致命崩潰都停止整場，包括其他算法正在運行的 task；已保存結果保留、不自動重跑。移除算法錯誤後必須繼續的架構硬限制，D35 轉為重新評估基線；比較維度見 [14](14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度)。當時先改文件並核對情境，不是安全停止驗收。
11. 其後完成 [19 的候選研究](19_architecture_candidate_experiments.md)，含歷史 gate2 的 72 故障案例與後續 48 補充案例。已測的兩個 cleanup 退休提案及 worker-first 錯誤 artifact 尚未定案；本次只封存原證據與核對摘要，不因原型改變 D40、正式錯誤時序或未知退出政策。

## 邊界與未解問題

- 依 [14 的比較維度](14_python_cpp_invocation_and_failure_replay.md#架構狀態與比較維度) 與 [19 的候選證據](19_architecture_candidate_experiments.md) 確認架構組合及其差異；有型別題庫、RNG、交付及故障記錄仍須正式整合，不自動搬移排程。
- 共用輸出器、結果 DTO、摘要、異常紀錄的正式欄位及檔案格式；worker 同步保存已定案。
- D36–D38 的通知與退出交錯如何在正式 IPC 中實現，如何保存已知事實；不自動核對文件、補登成功或重跑已定案。

- 成功結果保存後，整場實驗重啟時如何跳過完成 task；這仍是後續功能，不等同本輪算法錯誤停止政策。
