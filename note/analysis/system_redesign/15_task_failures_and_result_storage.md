# Task 異常紀錄與結果保存

單一 task 發生系統軟體流程異常時，實驗須留下紀錄，必要時替換出問題的執行單元，再執行下一個新 task；其他正常 task 不取消、不重跑。健康程序重用，每題狀態獨立，求解異常保留實際輸入，Python 寫檔異常保留原因。已選隔離 Python worker 內同程序 C++ 擴充模組，及 worker 同步保存、主程序只收摘要與位置；D36–D40 已確認派工、通知、交付未確認及替換政策；正式函式、通訊／監督實作、狀態保存格式與所有權仍待細化。本版不做自動超時或內建單 task 停止。

結果由 Python worker 同步保存、主程序只收摘要與檔案位置，已由使用者確認為 D34；D35 選同程序 C++ 擴充模組。呼叫方式見 [14](14_python_cpp_invocation_and_failure_replay.md)，實測與限制見 [17](17_invocation_comparison_experiment.md)。這是已確認設計，不是正式實作完成報告。

## 快速檢索卡

- 核心問題：如何在單一 task 出錯後繼續實驗，同時保留足以事後追查與重跑的資料？
- 當前結論：求解異常保留輸入，寫檔異常保留原因；重用健康程序，只替換必要的執行單元，其他正常 task 照常執行。
- 已確認：主程序先保留輸入及 worker／task 對應再派工，接收兩種階段通知；退出又缺少完整最終回報就保留現況，記交付未確認，不自動核對或重跑。
- 關鍵待議：正式通訊／監督機制、狀態保存格式、結果 DTO 與所有權；不再重選保存位置、A／B 或通知未達的政策。
- 適用於：本機傳統優化實驗的任務執行、Python 結果輸出與系統軟體流程異常。
- 不適用於：磁碟滿、磁碟故障等硬體／資源層異常的專用處理；跨媒介備援；算法中途 checkpoint。
- 待驗證：正式單 worker／多 worker 的隔離、任務狀態清理、異常紀錄及保存成本；控制證據範圍見 [16](16_process_lifecycle_experiment.md) 與 [17](17_invocation_comparison_experiment.md)。

## 核心問題

「算法已算完」「結果已寫好」「主程序知道結果已交付」是不同事實。任務在其中一段出錯，不能全部記成算法失敗，也不能因為 C++ 正常返回就宣稱結果已保存。

本章的 worker 指執行 task 的 Python 執行單元，不是 C++ 算法本身。已選同程序擴充模組，C++ 在該 Python worker 內執行；比較過的獨立執行檔則有額外程序邊界。不能把語言邊界、程序邊界及業務責任混為一談。

## 形成的知識

### 已確認的異常處理要求

1. 單一 task 發生系統軟體流程異常，不因此終止整場實驗。
2. 實驗側記下該 task 的工作與實際輸入，讓研究者日後可單獨從頭重跑。
3. Python 不需要查明 C++ 求解過程的具體根因；需要知道哪份工作未正常完成。
4. Python 寫檔異常必須保留原因及該 task 的對應資訊，不能只記「失敗」。
5. worker 崩潰或狀態不可信時，須能恢復必要的執行能力，再處理下一個新 task。非預期 C++ 錯誤即使已捕捉也替換該 worker；Python 保存錯誤清理成功後可重用，清理失敗或狀態不可信才替換。
6. 「繼續下一個新 task」不等於自動重試同一個失敗 task，不等於重啟整個實驗，也不等於從算法中途續算。
7. 正常跑到停止條件但最終解不可行，仍是正常求解結果，不觸發 worker 故障恢復。
8. 一個 task 出錯，不取消、不重跑其他正常 task；只替換必要的執行單元，不以重建整池為由中斷健康工作。
9. 健康求解程序完成正確交接與任務清理後，繼續接下一題；每題的 RNG、算法狀態、工作資料與歷史獨立。交付結果若仍被其他使用方引用，不得提前釋放或覆寫。
10. 本版不加入卡住後自動超時中止；一直未完成、但沒有明確錯誤或程序終止的工作，暫由研究者人工處理。

以上依據使用者明確要求及 D27–D29、D36–D40；處置政策已定，正式恢復機制與狀態名稱仍待設計。程序重用與每題狀態獨立可以同時成立，不代表把所有任務的歷史永久累積在同一個程序內。交接方式及所有權規則見 [14](14_python_cpp_invocation_and_failure_replay.md)，實驗限制見 [16](16_process_lifecycle_experiment.md)。

### 求解異常與寫檔異常需要不同紀錄

| 情況 | 需要保留的資訊 | 不應聲稱的事 |
| --- | --- | --- |
| 求解未正常完成 | 實際題目數值或可重建的已保存引用、算法與完整有效參數、seed、停止／紀錄設定、其他初始化輸入及 task 關聯。 | 不要求 Python 一定有 C++ 根因、堆疊或出錯行號。 |
| Python 寫檔失敗 | task 關聯、寫入目標、失敗動作與實際取得的錯誤原因。可用的錯誤類型、作業系統錯誤碼及訊息應保留。 | 不能用「寫檔失敗」四個字代替可取得的原因；也不能宣稱只用相同 seed 就能重現檔案權限等環境問題。 |
| worker 未正常回報 | 已保留的實際輸入、執行關聯與最後已知事實。 | 不能單憑沒收到回報，就斷定 C++ 根因、寫檔是否完成或是哪一步失敗。 |

求解輸入須在開始執行前由實驗側保留，不能依賴崩潰 worker 返回後才第一次保存。大份固定題目可以保存一次供多個 task 引用；可變來源路徑、暫時 SHM 名稱或裸指標不足以支持日後重跑。詳見 [14 的輸入要求](14_python_cpp_invocation_and_failure_replay.md)。

表內是所需資訊，不是已定的欄位 schema。寫檔錯誤也可能發生於開檔、資料轉換、序列化、寫入或關檔；記錄應反映實際發生的軟體流程階段，而非先猜原因。

### 已確認的派工、通知與異常政策（D36–D40）

符合新需求的概念流程為：

```text
主程序先保留實際輸入與 worker／task 對應，再指派一題
  → worker 通知「已接收任務」
  → C++ 完整求解並一次返回結果與全部歷史
  → worker 通知「C++ 已正常返回」
  → Python worker 同步保存結果
      → 正常交付：回報完整摘要與位置
      → task 異常：回報已知原因，依錯誤種類清理／替換
      → worker 退出：先處理已交付通知，再判斷是否缺少最終回報
  → 正確清理本題資料，結果仍被使用時維持其有效性
  → 健康程序繼續接下一個新 task，其他正常 task 照常執行
```

故障隔離必須讓管理程序有能力記錄異常及恢復派工。D35 已選主程序外的 Python worker 載入 C++；即使只同時跑一題，也不在主程序直接求解。D36 確認由主程序逐題指定，先保留輸入及 worker／task 對應；管理端等待訊息與程序退出事件，不反覆掃描。正式通訊、監督與狀態保存機制待細化，不再把同程序／獨立程序當成未決選型。

D37 確認 worker 回報「已接收任務」及「C++ 已正常返回」，最終另有完整成功或錯誤回報。收到任務不代表 C++ 已開始，C++ 返回不代表 Python 已保存；沒收到某通知也不證明該階段沒發生。只記實際收到的事實，不讓缺少前一階段通知推翻已收到的完整最終回報。

D38 確認：worker 退出時先處理已交付通知；若仍缺少完整最終回報，記「交付未確認」，保留實際輸入、現有文件（包括部分文件）及最後已知事實。不自動核對文件、讀完成記錄、補登成功或重跑。未通知不等於求解失敗或保存一定失敗，本版也不新增完成記錄核對功能。

**task 結果與 worker 健康是兩件事。**完整成功回報一旦收到，worker 後來退出不能把該題改成失敗；完整錯誤回報一旦收到，其實際原因也不能被後來的退出覆蓋成只有「交付未確認」。退出仍須替換該 worker，繼續下一個新 task。

D39 確認非預期 C++ 錯誤即使已捕捉也替換該 worker；只保留可取得錯誤與輸入，不要求 Python 查明原生根因。正常不可行或已知輸入錯誤不混入此類。D40 確認 Python 保存錯誤須保留實際原因與 task 對應：本題資源清理成功後重用，清理失敗或狀態不可信才替換；不自動重求解或重試保存。清理是釋放本題資源，不是刪除現有結果／部分文件。

其他正常 task 不中斷已是確定要求，不再是「可以一起取消後重跑」的待選策略。目前共用程序池可能連帶報錯，既不符合目標，也不能把每個報錯 future 都當成算法自身崩潰。如何只替換出問題的單元、保存實際執行對應、保留已完成結果及避免漏派／重複執行，仍是待實作驗收項。

不加入自動超時機制，表示本版不承諾自行識別或排除所有永不返回的工作；這不放寬已觀察到的普通例外或程序終止所需的記錄與恢復責任，也不改寫算法的正常停止條件。

異常及未確認工作應如實出現在實驗報告，不偽造零分、空解或成功樣本。失敗數、未確認數、正常不可行結果、平均值與成功率分母的具體規則，仍在 [09](09_experiment_planning_and_statistics.md) 收斂。

### 十個事件案例

本表從管理端「實際收到什麼」判定，不是正式狀態 enum 或訊息 schema。「完整最終回報」指該題的完整成功或錯誤回報，不是前述兩種階段通知；主程序仍不接收全部歷史。task 結果與 worker 健康分欄，所有案例都不取消／重跑其他正常 task，替換後只接新 task。

| 案例 | 管理端已取得的事件／事實 | task 如何記錄 | worker 如何處理 |
| --- | --- | --- | --- |
| E01 | 收到完整成功回報，最終解可行。 | 確認該題已交付，保留摘要與檔案位置。 | 本題資源正確清理後重用。 |
| E02 | 收到完整成功回報，最終解不可行。 | 正常交付，標示不可行；不當作執行錯誤。 | 本題資源正確清理後重用。 |
| E03 | 收到非預期 C++ 例外的完整錯誤回報，worker 仍存活。 | 記求解異常，保留實際輸入與可取得錯誤。 | 即使已捕捉，也替換該 worker（D39）。 |
| E04 | Python 保存出錯，收到實際原因與本題清理成功的回報。 | 記保存失敗及 task／原因；不重求解或重試保存。 | 清理成功且狀態可信，重用該 worker。 |
| E05 | Python 保存出錯，收到實際原因與清理失敗的回報。 | 記保存失敗，另留可取得的清理錯誤／不可信事實。 | 替換該 worker（D40）。 |
| E06 | 已指派，但尚未收到「已接收任務」，worker 即退出，亦無完整最終回報。 | 記交付未確認；保留輸入與指派事實，不推論 C++ 一定沒開始。 | 替換該 worker。 |
| E07 | 已收到「C++ 已正常返回」，之後 worker 退出，無完整最終回報。 | 記交付未確認，保留返回事實、輸入及現有文件；不推論保存是否完成，不自動核對／補登／重跑。 | 替換該 worker。 |
| E08 | 已收到完整成功回報，worker 之後退出。 | 維持已交付結果，不改成失敗或交付未確認。 | 只替換已退出的 worker。 |
| E09 | 先觀察到退出事件，但尚未讀取的通知中已有完整成功回報。 | 先處理已交付通知，確認該題已交付；不靠讀結果文件補登。 | 替換已退出的 worker，不撤銷該題結果。 |
| E10 | 已收到保存失敗的完整錯誤回報及原因，worker 之後退出。 | 維持已知保存失敗與原因，不覆蓋成交付未確認。 | 替換已退出的 worker。 |

**驗證範圍：**十個案例已以記憶體內事件序列推演及斷言核對規則一致性，沒有啟動正式 worker、使用正式 IPC、注入原生崩潰或測試真正檔案／恢復流程。E09 的「先處理已交付通知」是正式通訊／監督機制必須滿足的設計要求，不表示這項處理已實作，也不保證在通道或程序失效時找回從未交付的訊息。正式回報格式、通知完整性判斷與退出處理仍須後續實測；不以本表宣稱完成故障恢復。

### 明確排除的故障範圍

使用者已明確排除磁碟滿、磁碟故障等硬體／資源層非預期行為的專門處理；「寫檔失敗原因必須保留」不包含整個結果儲存空間無法寫入的情境。

- 不增加另一顆磁碟、另一台機器或獨立錯誤保存服務。
- 不設計跨儲存媒介備援，也不要求在整個儲存空間不可寫時仍保證留下故障文件。
- 不把上述情境重新列為本輪待選方案或待補的錯誤留存需求。

這是本版保障範圍，不表示已解決硬體／資源故障。權限、錯誤路徑、輸出格式與資料轉換等系統軟體流程問題，仍屬處理範圍。先前完整單任務歷史可能耗盡 RAM 的已知風險，也沒有因此獲得解決或改成截斷紀錄。

### 已選定：Python worker 同步保存（D34）

```text
主程序保留輸入並分派 task
  → Python worker 內的 C++ 擴充模組完整求解、驗證、一次返回
  → 該 worker 呼叫共用 Python 輸出器，同步保存本題
  → 主程序只收摘要與檔案位置，彙整索引與統計
  → 本題資料按生命週期清理，健康 worker 再接下一題
```

這是責任與資料路徑，不是保存完成、通知、接收確認與記憶體回收的正式協議。不能先清掉尚被使用的結果，也不能把 C++ 正常返回當成保存成功。

使用者接受同步保存占用該 worker，讓它不在前題尚未保存時繼續產生下一份巨大結果；其他 worker 仍可求解或保存。這不保證單題不會 OOM，也不表示多 worker 寫檔必然較快。

「共用輸出器」是同一套 Python 程式，不是共享可變 writer 或讓多個 worker 同寫同一檔案。worker 是執行程序，不是 C++ 求解模組的同義詞；同一 worker 可先呼叫 C++ 求解，再呼叫 Python 實驗側輸出器，C++ 仍不負責結果文件。

尚須細化：

- 每個 task 的獨立文件／目錄與最終格式，不把完整歷史塞進彙整用 CSV。
- 摘要中的 task 對應及統計所需數值，不只返回檔名；正式 schema 待議。
- 未完成文件、錯誤與最終回報的正式欄位／格式；D38 的交付未確認政策已定，不加入自動檔案核對。
- 錯誤原因保存、暫存／發佈方式與資料回收時序；不預設一套完成標記或通知確認協議。
- 正式輸出器避免為轉換而建立多份完整資料，分開量測求解、交接及保存成本。

主程序保存是本輪比較後未採用的路徑，不再列為有效待選方案。它也能用限制待存結果數、逐題保存後釋放來控制跨題積壓，但保存跟不上時仍須讓生產方等待；不能把「主程序保存必定 OOM」當成選 worker 的理由。既有整批保存全部 SolveResult 的流程也不是本版目標。

同程序／獨立程序的控制對照與限制見 [17](17_invocation_comparison_experiment.md)：所有案都採 worker 保存，因此不是 worker 與主程序保存的實測排名，也不是正式任意外部結構或輸出器已完成驗收。單任務全歷史 RAM、資料轉換及多 worker 磁碟競爭的風險仍在；通知未達已有 D38 政策，正式通訊實作尚未驗證。

### Problab 的 DTO 分層可參考但不照搬

DTO 是準備對外交付的結果資料結構，不等於 JSON 字串，也不是 Web 專用。可以分開討論結果內容、跨語言交接、輸出格式與保存位置。

## 討論的演化

1. 最初偏向 A（擴充模組）的理由是配合現有 Python worker、較容易先驗證；經公平拓撲比較後，這些優先理由已撤回，不能恢復成既定選型。
2. B（獨立執行檔）可提供正常執行與事後單 task 重跑共用的原生入口；使用者並未要求必須脫離 Python 重跑，因此這項優點沒有單獨決定 B 優先。
3. 比較完整歷史交付時，發現 Python 保存不等於主程序必須收到全部歷史；由 worker 呼叫 Python 輸出器因而成為候選。
4. 區分求解、保存與完成回報後，釐清「檔案可能已完成但沒有通知」不能被直接記成算法失敗。
5. 使用者明確要求 task 異常後繼續新 task、必要時重啟 worker；求解異常保存輸入，寫檔異常保存原因。這取代較早的任務失敗即停止整場實驗要求。
6. 對共用磁碟失效的反例，使用者明確選擇不處理硬體／資源層異常，不要求另一顆磁碟或另一台機器備援。不能把先前的廣泛可靠性討論當成新的實作義務。
7. 後續確認其他正常 task 不取消、不重跑，本版不做卡住後自動超時中止；看過清理正確的控制實驗後，選擇重用健康求解程序。未整理好的舊核心記憶體增長不作程序選型依據，早先據此偏向每題重開的理由已撤回。
8. 再逐題確認平台、人工停止、完整呼叫及 Python 重跑範圍；選擇 worker 同步保存後，以相同保存路徑比較同程序、管線複製及共享記憶體交接。看過控制證據後，使用者確認 D34–D35；這是新的決策依據，不恢復最初配合舊流程的理由。
9. 後續確認 D36–D40：主程序指定工作並等待事件、兩種階段通知、退出時先處理已交付通知；缺少完整最終回報就保留現況，不自動核對文件、補登或重跑。非預期 C++ 錯誤一律替換該 worker，Python 保存錯誤則依清理結果決定重用或替換。

## 邊界與未解問題

- 同程序 C++ 擴充模組的正式函式、單／多 worker 的監督及單一 Python worker 替換機制；呼叫方向與健康程序重用已定案。
- 共用輸出器、結果 DTO、摘要、異常紀錄的正式欄位及檔案格式；worker 同步保存已定案。
- D36–D38 的通知與退出交錯如何在正式 IPC 中實現，如何保存已知事實；不自動核對文件、補登成功或重跑已定案。
- 避免漏派／重複執行、清理與可用狀態交接的實作、完整實驗的統計與退出碼；task 結果和 worker 健康分開、其他正常 task 不取消／不重跑已定案。
- 成功結果保存後，整場實驗重啟時如何跳過完成 task；這仍是後續功能，不等同本輪已確認的異常後繼續派工。
- 相同輸入與 seed 可重建求解工作，不保證再次觸發原生崩潰或檔案環境錯誤。寫檔原因與上下文是追查線索，不是完整環境快照。

[16](16_process_lifecycle_experiment.md) 與 [17](17_invocation_comparison_experiment.md) 有程序重用、呼叫／保存及故障注入的控制證據；正式函式、任意結果表示、交付確認及整合故障處理仍待驗證，不能用控制數據代替。
