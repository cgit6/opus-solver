# 06｜addAct、分數同步與快照

狀態：提交責任與不干擾原則已確認；綁定方式及資料布局待定。對應 D13–D17、P06–P07。

## 已接受的概念介面

```text
addAct(文字狀態, 編碼, 外部結構或 nil)
```

- 文字狀態：算法作者定義的名稱，例如「初始化完成」「移除物品」「local search 完成」。
- 編碼：單一解算法提交該解；種群算法提交當次全部個體的編碼狀態。
- 外部結構：本次允許暴露的自訂狀態；可以是 nil。

紀錄同時必須包含和編碼對應的真實適應值。可由與提交器綁定的主解狀態取得，但如何綁定是實作細節；不擅自把已討論的三參數介面改成必須多傳一個分數參數。

## 它只提交，不更新求解狀態

允許：

- 讀取當次狀態並保存快照。
- 維護紀錄自己的順序與儲存資訊。

不允許：

- 呼叫目標函數、constraints 或訓練模型。
- 修復、local search、更新分數、替算法選最佳解。
- 消耗搜尋／評估 RNG，或修改算法迭代／接受判斷。
- 因 isSim 或紀錄開關改變算法原本應更新的工作狀態。

紀錄可以更新自己的筆數，不表示可以更新算法迭代數；兩者不是同一個計數器。

## 任意時點提交，和完整操作不衝突

算法可以自行安排提交點，不限制只能在整代結束提交；也不自動加「未評估」標記。

但一個小邏輯操作應先完成自身更新。例如：

```text
移除物品：改編碼 + 扣價值 + 改負載 + 更新可行性
    ↓
addAct("移除物品", 當次編碼, 外部狀態)
```

不能在「只改了編碼、還沒扣分」的半途提交，再把問題交給狀態模組。若需要看每次修復進度，就讓每次移除都成為完整小操作後再提交。

這是算法作者的開發契約，不由實驗管理逐次重算檢查。

## 開發上的兩項原則

1. **同次提交要對齊**：編碼、真實適應值、外部個體可行性等，屬於同一時點、同一批個體、相同順序。
2. **已提交的內容不能跟著改**：算法之後重用工作緩存，不會改寫先前紀錄。

初始化可做結構檢查；操作正確性由測試確認。不新增主系統逐筆掃描或隱含 evaluator。

## 快照的實數例子

提交時溫度是 1.0、編碼是 `[1, 0, 1]`、真實分數是 21。之後算法把溫度改成 0.95、編碼改成 `[0, 0, 1]`。

舊紀錄仍應顯示 1.0、`[1, 0, 1]`、21。只保存指向同一個可寫陣列的引用，做不到這件事。

因此會需要某種快照資料保存，但不是每次深度複製整個算法、問題數據、RNG、查表與工作空間。只保存實際提交的資料；是否用集中陣列、複製或其他可完整重建表示，尚未選型。

全量保留不允許使用環形緩存覆蓋舊快照。算法工作緩存的重用和完整歷史的保留，是不同生命週期。

## RNG 與可重現性

驗收目標是同題、同算法參數、同 seed、固定迭代數下：

```text
紀錄開啟／關閉 → 搜尋狀態、RNG 軌跡、最終結果相同
```

這裡的關閉可用於開發對照，不表示正式實驗改成只保留少數任務歷史。當外部狀態傳 nil 時也要測相同原則。

固定迭代下，記錄可以讓牆鐘時間變長，但不應改變完成的搜尋步數。不對依秒數停止的結果提出相同承諾；AI 的多執行緒／GPU／訓練非確定性仍需問題專屬驗證。

## 與 Problab 的異同

可參考其「工作狀態與提交快照分離」「緩存重用」「對外 DTO」概念。

但 Problab 的 `AddAct` 還會累加分數、推進 act／step／round 並清理暫存。這些行為不能原封不動搬入本設計，因為本設計已決定 addAct 不更新求解狀態。來源與限制見 [12](12_prior_work_and_references.md)。
