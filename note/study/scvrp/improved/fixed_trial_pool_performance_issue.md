# CDELS 固定 Trial Pool 的效能與記憶體問題

更新日期：2026-10-04

## 文件目的

本文件記錄 `CDELS_workspace` 實驗版採用「固定長度 trial Pool」後觀察到的成本，以及之後要如何處理。

目前只記錄問題與驗證門檻，不修改正式算法。正式入口 `solver/CDELS.py` 仍維持原狀；實驗內容位於 `solver/CDELS_workspace.py`。

## 先說結論

固定配置 `P` 個 trial Buffer 並不保證比較快或比較省記憶體。

它的主要優點是：求解開始前一次配置好空間，之後不需要為每個 trial 反覆建立底層數值陣列，記憶體需求也比較可預測。

它目前的主要問題是：即使一代只有少數 trial 被接受，仍會在整個求解期間保留完整的 `P` 個 trial Buffer。相較之下，原始 `CDELS.py` 只會讓被接受的新解進入下一代；被拒絕時可直接沿用舊解，因此通常不需要同時保留完整的兩代資料。

所以目前實驗版得到的是「較固定的配置行為」，不是已經證明的效能改善。現有測量甚至顯示，完整求解熱路徑可能略慢且常駐記憶體較高。

## 實際流程範例

假設種群大小 `P = 100`，這一代依序產生 100 個 trial，但最後只有 20 個被接受。

原始實作的概念是：

- 100 個上一代個體在整代內保持可讀。
- 被拒絕的 80 個 trial 不需要留到下一代；下一代直接引用對應的舊個體。
- 只有被接受的 20 個新個體需要被保留。
- 因此活著的完整個體數量會跟接受數量有關，通常明顯少於兩個完整種群。

固定 trial Pool 的概念是：

- 100 個上一代個體保持可讀。
- 求解開始前另外準備 100 個 trial Buffer。
- 不論最後接受 20 個或 100 個，都會保留這 100 個 trial Buffer。
- 世代結束後只交換「哪一組參照代表目前種群」，不對整個種群做深度複製。

因此，固定 Pool 確實避免反覆配置，但它用「長期保留最壞情況需要的全部空間」交換這個優點。

## 目前實驗版已做的事情

`solver/CDELS_workspace.py` 目前包含：

- 求解開始前建立 Workspace。
- 固定配置 `P` 個 trial Buffer。
- 固定配置 mutant 與 elite Buffer。
- 世代完成後交換目前種群與下一代的參照，不深度複製整個種群。
- `positions` 使用 `uint16`，可表示 0 到 65,535，足以涵蓋目前預估最多約 2,000 個點位。
- `transfer_mask` 使用 `uint8`。
- `positions` 與 `transfer_mask` 使用連續的底層 NumPy 儲存空間，再切成各個個體的 view。

尚未完成：

- `routes` 仍是 Python `list[list[int]]`，還不是固定長度的連續儲存。
- 固定 trial Pool 尚未證明在完整熱路徑中比正式版快或省記憶體。
- 尚未決定固定 trial Pool 是否應保留到正式版。

## 已有正確性證據

目前實驗修改沒有改變已檢查的算法結果：

- 小題目逐步結果可與 C++ oracle 對上。
- 111 次 transition、包含降溫邊界的驗證通過。
- 相關非慢速測試結果為 `63 passed, 7 deselected`。
- 最佳成本、RNG 消耗與 generation digest 在已檢查案例中一致。

這些證據只代表目前已測案例沒有改動算法邏輯，不代表固定 Pool 已有更好的效能。

## 已有量測結果

以下數字來自開發過程中的樣本，主要用來判斷方向；Python 執行時間有雜訊，不能把單次結果當成最後結論。

### 固定 Pool 的整體影響

- P-n16、100 generations：實驗版約慢 `1.36%`。
- A-n80、1 generation：不同輪測量曾約慢 `0.79%` 到 `2.06%`。
- 另一輪完整比較中：正式版中位數約 `7.419 秒`，實驗版約 `7.601 秒`，實驗版約慢 `2.46%`。
- 曾有單次組合結果顯示實驗版快約 `3.36%`，表示差距很小且容易被執行雜訊影響，目前不能宣稱加速。

### Python 配置追蹤

P-n16、單一 generation 的 `tracemalloc` 樣本：

- 正式版：目前約 `208 KiB`，峰值約 `297 KiB`。
- 固定 Pool 實驗版：目前約 `314 KiB`，峰值約 `315 KiB`。

這表示固定 Pool 降低了「目前值與尖峰值的差距」，但因為所有 trial Buffer 都長期存在，常駐的 Python 配置反而較高。這不是整個程序的 RSS，只是 Python 配置追蹤結果。

### 資料型別壓縮

A-n80 的 population 主要數值狀態若全部使用 `int64`，估算為 `925,440 bytes`；改用 `uint16` 與 `uint8` 後約為 `192,800 bytes`，減少約 `79.17%`。

這項改善本身值得保留研究，因為它直接減少數值資料大小；但它和「是否保留完整 `P` 個 trial」是兩個不同決策。

### 連續底層儲存

只比較相同 Workspace 邏輯下的配置方式：

- 多個獨立 array：中位數約 `7.397 秒`。
- 一整塊連續 backing storage：中位數約 `7.340 秒`。
- 樣本差距約 `0.77%`，幅度很小，需要更多重複量測。

連續儲存可減少底層資料區塊數量與碎片風險，但每個個體目前仍有 NumPy view 物件，所以不會讓整體 Python 物件數歸零，也不會自動抵銷固定 `P` 個 trial 的成本。

## 為什麼目前可能變慢

1. **保留了原本不一定需要的完整 trial 空間**

   接受率低時，正式版能直接沿用大部分舊個體；固定 Pool 還是維護 `P` 個 trial Buffer。

2. **Python 層仍要管理很多個體與 view**

   即使底層數值資料連續，每個個體的 Python 物件、routes、NumPy view 和參照清單仍然存在。

3. **複製資料的工作沒有完全消失**

   固定 Pool 避免的是重新配置空間，不是所有資料寫入。每個 trial 開始前仍須把來源狀態寫入可修改的 Buffer，否則會破壞上一代資料並改變算法結果。

4. **原始 NumPy 複製本來就很快**

   把少量向量複製到預配置 Buffer，未必比 NumPy 建立小型新 array 明顯快；多出的 Python Pool 管理可能抵銷收益。

## 不能直接省略的限制

為了維持與 C++ 相同的世代流程，處理本代第 `i` 個 target 時，mutation 仍可能讀取上一代任何個體。因此不能產生一個新解後立刻原地覆寫上一代對應個體。

也就是說：

- 上一代必須在整個 generation 中維持唯讀且完整可用。
- 下一代可以用參照沿用未被替換的舊解。
- 若要求「最壞情況 100% trial 都被接受」且「熱路徑完全不動態配置」，就必須預先準備足以保存 `P` 個新解的空間。

這是固定 Pool 的根本取捨，不是單純調整清空時機就能消除。

## 後續可評估的方案

### 方案 A：取消完整固定 trial Pool

保留 `uint16`／`uint8`、距離矩陣無複製讀取等獨立改善，但恢復接受數量導向的新解保存方式。

優點：接受率低時，常駐記憶體通常較少，也比較接近目前正式版的實際需求。

缺點：仍會產生與回收 trial 物件，配置行為不固定。

### 方案 B：有限容量的可重用 Pool

預先準備少於 `P` 的 Buffer，只有不足時才擴充，並在不再被任何種群參照後歸還 Pool。

優點：可減少一般情況的配置次數，也不必永久承擔完整 `P` 的空間。

缺點：遇到高接受率仍可能動態擴充；管理引用生命週期較複雜，而且必須證明不會過早覆寫仍在使用的個體。

### 方案 C：先完成 routes 固定儲存，再重新量測完整固定 Pool

目前最大的 Python 動態結構之一仍是 `routes`。可以先設計固定容量的 route backing storage、route 長度與分隔資訊，再逐操作驗證 swap、insert、remove、transfer 的結果。

優點：才能比較完整的「固定 Workspace」是否真正降低熱路徑配置。

缺點：這會改變核心資料表示，風險高，必須分模組驗證；即使完成，也不保證純 Python 會更快。

### 方案 D：保留固定 Pool，只把目標定義為記憶體可預測

若產品需求更重視避免執行中配置與控制最壞情況，而不是最小常駐空間或純 Python 速度，可以接受固定 Pool 的額外成本。

這時應明確把它當成「可預測性方案」，不能宣稱它已經是效能優化。

## 下一步與停止門檻

目前不把 `CDELS_workspace` 切換成正式入口，也不修改 `solver/CDELS.py`。

若繼續處理，建議下一個獨立工作單元是「routes 固定儲存設計與單模組原型」，不要同時改 Pool 策略。完成後依序通過：

1. 每種 route 操作的輸入／輸出與正式 Python 版完全一致。
2. RNG 呼叫次數與順序完全一致。
3. 小題目逐步 trace 與 C++ oracle 完全一致。
4. 111 次 transition 與降溫邊界一致。
5. 在固定 CPU 條件、暖機後至少重複 5 次，比較中位執行時間。
6. 同時量測 RSS／峰值記憶體與 Python 配置，不能只看 `tracemalloc` 或單次秒數。

只有在完整端到端測量顯示固定 Pool 的速度或尖峰記憶體有明確收益，或需求明確選擇「最壞情況記憶體可預測」時，才保留完整固定 Pool。否則應撤回固定 Pool，只保留已個別證明有益且不改變結果的改善。

目前階段不考慮 Numba；先把純 Python 的資料生命週期、記憶體表示與 C++ 一致性處理清楚。
